# 용어집 — 문서를 읽기 전에

> **이 문서가 있는 이유**: 설계 문서가 결정을 내릴 때 쓴 용어를, 그 결정을
> 읽는 사람이 모르면 **결정을 검토할 수 없다.** 특히 협업 동기화
> ([`27-sync-model.md`](../04-extensions/collaboration/27-sync-model.md))
> 는 CRDT 를 안다는 전제로 쓰여 있다.
>
> 사업계획서 요건이기도 하다 — 전문용어는 주석을, 약어는 풀네임을 병기해야 한다.
>
> 작성: 2026-08-20

## 1. 협업·동기화

### CRDT (Conflict-free Replicated Data Type, 충돌 없는 복제 데이터 타입)

여러 사람이 같은 데이터를 동시에 고쳐도 **어떤 순서로 합쳐지든 모두가 같은
결과에 도달하도록** 설계된 자료구조.

데이터를 "최종 값"이 아니라 **변경 조각들의 모음**으로 들고, 각 조각에
누가·언제 만들었는지를 붙인다.

```
노드 텍스트 "회의 준비"

A: 앞에 "긴급 " 삽입        B: 뒤에 " 완료" 삽입   (동시에)

LWW  → "회의 준비 완료"      A 가 친 글자가 경고 없이 사라진다
CRDT → "긴급 회의 준비 완료"  둘 다 남는다
```

**CRDT 가 보장하는 것은 "모두가 같은 결과"뿐이고, 그 결과가 사용자가 원한
것인지는 별개다.** 트리 순환·삭제된 부모 같은 의미 규칙은 우리가 지킨다
(`27-sync-model.md` §4).

### LWW (Last-Write-Wins, 마지막 쓰기 우선)

타임스탬프를 비교해 늦게 온 쪽이 이기는 충돌 해소 방식. 값 하나짜리
필드(색·접힘)에는 충분하지만 **텍스트와 트리 구조에서 진다.**
`25-map-collaboration.md` 의 원래 전제였고, `27-sync-model.md` §2 에서 버렸다.

### OT (Operational Transformation)

CRDT 이전에 쓰이던 충돌 해소 방식. 서버가 모든 히스토리를 들고 순서를
잡아야 한다. **쓰지 않기로 했다** (`27-sync-model.md` §11).

### Yjs

CRDT 를 구현한 자바스크립트 라이브러리. **CRDT 는 개념이고 Yjs 는 구현체다.**
경쟁자는 Automerge · Loro.

`Y.Map` · `Y.Text` · `Y.Array` 에 값을 넣으면 병합은 라이브러리가 한다.
개발자가 타임스탬프를 비교하지 않는다.

Automerge 대신 고른 이유는 성능이 아니라 **awareness 가 같은 라이브러리에
있다**는 점이다 (`27-sync-model.md` §2.2).

| 용어 | 뜻 |
|---|---|
| **Y.Doc** | CRDT 문서 하나. 우리는 **맵 하나 = Y.Doc 하나** |
| **update** | 변경 조각(바이너리). 이걸 WebSocket 으로 주고받는다 |
| **awareness** | 데이터가 아닌 **일시적 상태** — 접속자·커서·"○○ 편집 중". 저장되지 않고 연결이 끊기면 사라진다. Soft Lock 에 DB·Redis 가 필요 없는 이유 |
| **origin** | 그 변경을 누가 만들었는지. `UndoManager` 를 자기 origin 으로 한정해 **내가 한 것만 되돌린다** (§8) |
| **tombstone (묘비)** | 지운 조각을 실제로 지우지 않고 "삭제됨"으로 남긴 것. 늦게 도착한 옛 메시지가 지운 것을 되살리는 걸 막는다. **이미지 바이트를 CRDT 에 넣으면 안 되는 이유** (§3) |

### 물질화 (materialize)

편집 중의 `Y.Doc` 을 **기존 `map_documents.doc` JSON 스냅샷으로 변환해
저장**하는 것. CRDT 는 편집 중의 표현일 뿐이고 **정본은 그대로 `doc` 이다**
(§6). 실측 15ms / 1만 노드.

### compaction (로그 접기)

물질화한 시점 이전의 update 로그를 접어 정리하는 것. 접지 않으면 오래된
맵일수록 여는 데 오래 걸린다.

### Soft Lock

노드 단위 "○○ 편집 중" 표시. **막는 잠금이 아니다.** TTL 5초, awareness 로
흐른다.

### 편집 잠금 (`map_edit_locks`)

이것은 **진짜 막는 잠금**이다. 맵당 한 세션, TTL 60초. 단독맵(`kind='solo'`)
에서 다른 세션이 열면 읽기 전용이 된다. **협업맵(`kind='collab'`)에서는
비켜 준다** (§7, 완료).

## 2. 배포·오프라인
### PWA (Progressive Web App)

한 줄: 웹사이트에 설치·오프라인 기능을 붙여서 앱처럼 쓰게 만드는 웹 표준.

지금 easymindmap은 브라우저에서 mindmap.ai.kr을 열어야 쓸 수 있습니다. PWA를 적용하면 주소창 옆에 "설치" 버튼이 뜨고, 누르면 바탕화면에 아이콘이 생기며, 실행하면 주소창 없는 창으로 뜹니다. 사용자는 앱을 설치했다고 느끼지만 실체는 그대로 웹입니다.

구성 요소는 두 개뿐입니다.

① Web App Manifest — 앱 이름, 아이콘, 시작 URL, 창 모양을 적은 JSON 파일 하나. 이게 "설치" 버튼이 뜨는 조건입니다.

② Service Worker — 이게 핵심입니다. 브라우저와 네트워크 사이에 끼어드는 자바스크립트로 만든 중간 계층입니다.

[일반 웹]    브라우저 ──────────────▶ 서버      (끊기면 끝)

[PWA]        브라우저 ──▶ Service Worker ──▶ 서버
                              │
                              └─▶ 캐시 (끊기면 여기서 응답)

서버가 안 잡히면 Service Worker가 캐시에 저장해 둔 HTML·JS·CSS를 대신 내줍니다. 그래서 인터넷 없이도 앱 화면 자체는 뜹니다.

다만 중요한 한계가 있습니다. Service Worker는 "앱 껍데기"를 캐시할 뿐, 사용자의 맵 데이터를 자동으로 챙겨주지 않습니다. 맵 데이터는 별도로 브라우저 안의 저장소(IndexedDB)에 넣어야 하고, 그건 직접 만들어야 합니다. 지난번에 "PWA 씌워도 오프라인은 안 된다"고 말씀드린 게 이 부분입니다.

|PWA로 되는 것|안 되는 것|
|설치 아이콘, 전체화면 실행|	.emm 파일 더블클릭 연결|
|앱 화면 오프라인 로딩	|네이티브 메뉴바 / 트레이|
|푸시 알림	|로컬 파일 자유 접근|
|비용 거의 0, 배포·서명 불필요	|맥 App Store 등재|

### Electron / Tauri

웹앱을 Windows·macOS·Linux 실행 파일로 감싸는 도구. Electron 은 Chromium 을
같이 담고(120~180MB), Tauri 는 OS 웹뷰를 빌린다(8~15MB). PWA 와 달리
**`.emm` 파일 연결·네이티브 메뉴·코드 서명**이 가능하다.

### IndexedDB

브라우저 안의 데이터베이스. 로컬 우선(local-first) 저장의 자리.
PWA·Electron·Tauri 가 **같은 코드 경로**를 쓸 수 있다.

## 3. 이 프로젝트 고유어

### EMM (EasyMindMap Markdown)

본문 100% CommonMark/GFM + 파일 끝 메타데이터 주석 1줄.

```
<!-- easymindmap:v1:BASE64(JSON) -->
```

스펙은 [`emm-spec.md`](../04-extensions/emm-spec.md), 변환 규칙은
[`markdown-export.md`](../04-extensions/markdown-export.md).
레퍼런스 파서는 `packages/emm-parser` — **공개다.**

### open-core (오픈 코어)

코어는 공개하고 일부 기능만 유료로 두는 구조. 경계는
[`open-core-boundary.md`](../04-extensions/open-core-boundary.md).

- **이음매는 공개** — `apps/frontend/src/pro/contract.ts`, `apps/api/src/pro/`
- **알맹이는 비공개** — `okpojung/easymindmap-pro`
- 유료 모듈이 없는 배포에서는 `stub` 이 자리를 그린다
- `GET /v1/features` 가 **무엇이 켜졌고 왜 꺼졌는지**를 답한다

> 서버에 못 물었을 때 "꺼졌다"고 단정하지 않는다 — 단정하면 백엔드가 잠깐
> 죽은 것을 "유료 기능을 안 샀다"로 보여 주게 된다.

### 물질화 / 정본

`map_documents.doc` (JSONB) 이 **정본**이다. 협업맵이라고 저장 형식을 갈아
치우지 않는다 — 그러면 내보내기·버전 히스토리·문서함이 두 벌이 된다.

### ltree · `move_node_subtree`

PostgreSQL 의 계층 경로 타입. `root.n_a1b2c3d4.n_e5f6a7b8` 형태로 노드
경로를 들고, 서브트리 이동을 경로 치환 한 번으로 처리한다.
순환은 `new_base_path <@ old_path` 로 막는다.

### 트리 규칙 (`packages/emm-parser/src/tree-rules.ts`)

순환 금지·고아 판정의 **단일 원본**. 정규화 경로·협업 경로·화면이 같은
판정을 쓰게 하려고 순수 함수로 뺐다.

- `wouldCreateCycle(parentOf, nodeId, newParentId)` — 옮기면 순환이 생기는가
- `findOrphans(ids, parentOf, rootId)` — 뿌리에 닿지 못하는 노드.
  **지우지 말고 뿌리로 올리라**는 뜻이다

### 5-Store → 8-Store

에디터 상태 분리 구조. 코어 5개(document · editorUi · viewport · interaction ·
autosave) + 연동 3개(cloud · auth · aiSettings).
[`state-architecture.md`](../03-editor-core/state-architecture.md) 참조.

### 콘텐츠 영구 보존 (content permanence)

내보낸 파일 하나가 **서버 없이도 온전히 열려야 한다**는 약속.
사진을 서버 저장소로 옮기면서 내보내기가 깨지지 않게 하려고
`export/serverImages.ts` 를 **먼저** 깐 이유다.
[`content-permanence.md`](../04-extensions/content-permanence.md)

## 4. 인프라·운영

> `90-architecture/infra-architecture.md` §18(유료 사용자 수용량 & 이중화)을
> 읽기 위한 용어. 백업·복구 쪽은 **말이 어려운 게 아니라 순서가 헷갈리는**
> 분야라, 각 항목에 "왜 그게 필요한가"를 같이 적는다.

### RPO / RTO — 목표를 재는 두 자

백업 이야기는 전부 이 둘로 환산된다.

| | 뜻 | 질문 |
|---|---|---|
| **RPO** (Recovery **Point** Objective) | **얼마나 잃어도 되는가** | "사고가 나면 몇 분 치 작업이 사라지나" |
| **RTO** (Recovery **Time** Objective) | **얼마나 빨리 돌아와야 하는가** | "서비스가 몇 시간 멈춰도 되나" |

```
현재(일일 pg_dump)   RPO 최대 24시간 · RTO 수 시간
PITR 도입 후          RPO 분 단위    · RTO 1~3시간
스트리밍 복제 추가    RPO 초 단위    · RTO 5~15분(수동 승격)
```

> 둘은 **따로 움직인다.** 백업이 아무리 촘촘해도(RPO↓) 복구 절차가 없으면
> RTO 는 그대로다. §18.8.5 의 복구 리허설이 재는 것이 RTO 다.

### WAL (Write-Ahead Log, 미리 쓰기 로그)

PostgreSQL 은 데이터 파일을 고치기 **전에** "무엇을 바꿀 것인지"를 먼저
로그에 적는다. 그래서 이름이 Write-**Ahead** 다.

```
UPDATE users SET plan='pro' …
  ① WAL 에 기록   "이 행을 이렇게 바꾼다"    ← 먼저
  ② 데이터 파일 수정                          ← 나중
```

원래 목적은 크래시 대비다 — ② 중에 정전이 나도 재시작할 때 WAL 을 읽어
마무리한다. **켜고 끄는 기능이 아니라 PostgreSQL 이 늘 하고 있는 일이다.**

WAL 은 16MB 세그먼트 파일로 쌓이고, 다 쓰면 **재활용되어 덮어써진다.**
이 점이 다음 항목의 전제다.

### WAL 아카이빙

**WAL 세그먼트가 덮어써지기 전에 다른 곳으로 복사해 두는 것.**
PITR 의 재료를 모으는 작업이고, 설정은 사실상 두 줄이다.

```conf
archive_mode = on
archive_command = 'pgbackrest --stanza=easymindmap archive-push %p'
```

> ⚠️ **가장 흔한 장애가 여기서 난다.** PostgreSQL 은 아카이브에 **성공할
> 때까지 그 WAL 을 지우지 않는다.** 백업 호스트가 죽거나 차면 WAL 이
> VM-03 에 계속 쌓이고, 결국 **디스크가 꽉 차서 DB 가 멈춘다.**
> `pg_wal` 사용량 감시를 §16.2 디스크 알림에 반드시 함께 넣는다.

### PITR (Point-In-Time Recovery, 특정 시점 복구)

**전체 백업 + 그 뒤의 WAL** 을 갖고 있으면, 그 사이 **아무 시각으로나**
되돌릴 수 있다.

```
[베이스 백업]        [WAL 아카이브 — 끊김 없이]
    ●──────────────────────────────────────────▶
  일 03:00                        수 14:30    수 14:35
   전체 사본                      돌아갈 시점   사고 발견

  ① 전체 사본을 푼다
  ② WAL 을 순서대로 재생(replay)한다
  ③ recovery_target_time 에서 멈춘다
```

**pg_dump 와의 차이**: pg_dump 는 사진 한 장이라 **찍은 시각으로만** 갈 수
있다. PITR 은 **사고 1초 전**으로 갈 수 있다.

이것이 §18.8.2 에서 복제(B)보다 PITR(A)을 먼저 두는 이유다 — 아래
「논리적 손상」 참조.

> **재생 시간이 곧 RTO 다.** 전체 백업이 오래됐을수록 재생할 WAL 이 많다.
> 그래서 전체 주 1회 + 증분 일 1회로 재생 구간을 짧게 유지한다.

### 베이스 백업 / 증분 백업

- **베이스 백업**: 데이터 디렉터리 전체 사본. PITR 의 출발점
- **증분 백업**: 지난 백업 이후 바뀐 블록만. 짧고 가볍다

`pg_dump` 와 다르다. `pg_dump` 는 **논리 백업**(SQL 문장)이고 베이스 백업은
**물리 백업**(파일 그대로)이다. **둘을 다 유지한다** — 형식이 달라서 함께
망가질 확률이 낮다. 주간 `pg_dump` 는 PITR 저장소가 통째로 깨졌을 때의
마지막 보루다.

### pgBackRest

전체·증분 백업, WAL 아카이빙, 보관 정책, 검증을 **한 도구가 다 하는** 백업
도구. `archive_command` 에 `cp` 를 직접 쓰는 방식은 실패 처리와 검증을
스스로 만들어야 해서 결국 더 복잡해진다. 대안은 `wal-g`.

### 물리적 장애 vs 논리적 손상 — 대응이 다르다

| | 예 | 무엇이 막아 주나 |
|---|---|---|
| **물리적 장애** | NVMe 사망, ESXi 호스트 다운 | 복제 · 이중화 |
| **논리적 손상** | `DROP TABLE`, 잘못된 `UPDATE`, 마이그레이션 오작동 | **PITR 만** |

**복제는 논리적 손상을 막지 못한다.** `DROP TABLE` 도 standby 로 그대로
복제된다. 1인 운영에서 실제로 일어나는 사고는 하드웨어 고장보다 **사람의
실수**이므로 PITR 이 먼저다.

### 스트리밍 복제 / primary / standby

primary 의 WAL 을 standby 가 실시간으로 받아 계속 재생하는 구조.
standby 는 읽기만 가능하며 이를 **hot standby** 라 한다.

```
VM-03 primary (ESXi .11) ──streaming──▶ VM-06 standby (ESXi .81)
```

**반드시 다른 ESXi 호스트에 둔다.** 같은 호스트면 호스트가 죽을 때 둘 다
죽어 이중화가 아니다.

> ⚠️ **복제되는 것은 PostgreSQL 뿐이다.** Supabase 의 GoTrue(9999)·
> Storage(9000)·Realtime(4000) 은 별도 컨테이너이고, 첨부 파일은 VM-02 에
> 있다. **standby 승격 = DB 만 살아난 상태**다.

### 승격 (promote)

standby 를 primary 로 바꾸는 것. 승격 후에는 앱이 바라보는 주소를 바꿔야
한다. 우리는 **Coolify 에서 `DATABASE_URL` 을 바꾸고 재배포**하는 방식을
택했다(§18.8.4) — 자동은 아니지만 5분이고, 절차서만 있으면 된다.

### split-brain (분열 뇌)

**primary 가 둘이 되는 상태.** 네트워크가 끊긴 사이 standby 가 자기를
primary 로 승격했는데 원래 primary 도 살아 있으면, 양쪽에 서로 다른 데이터가
쌓이고 **합칠 방법이 없다.**

자동 failover(Patroni 등)를 1인 운영에서 권하지 않는 이유다 — **자동
failover 자체가 새로운 장애 원인**이 된다.

### 오프사이트 백업 / 3-2-1 규칙

**사본 3벌 · 매체 2종 · 그중 1벌은 다른 장소.** IDC 안에만 백업이 있으면
화재·침수·랜섬웨어에 함께 사라진다.

> ⚠️ `rsync --delete` 는 오프사이트 백업이 아니라 **미러**다. 원본에서
> 사라진 파일이 백업에서도 지워지므로 **랜섬웨어와 실수가 그대로 전파된다.**
> §15.2 의 `--delete` 를 제거해야 하는 이유(§18.8.1 ③).

### 복구 리허설

백업이 **있는 것**과 **복구되는 것**은 다르다. 분기 1회 실제로 복구해 본다.

```
① 임시 VM 에 복구 (운영을 건드리지 않는다)
② 특정 시각으로 PITR
③ API 를 그 DB 로 띄우고 맵을 연다 — **사진까지 보이는가**
④ 걸린 시간을 잰다. 그것이 실제 RTO 다
⑤ 절차서를 고친다
```

**리허설의 산출물은 복구된 DB 가 아니라 고쳐진 절차서다.**
그리고 ③ 에서 사진을 확인하지 않으면 리허설이 아니다 — DB 만 살아나고
사진이 전부 깨진 상태는 사용자에게 "복구됨"이 아니다.

### TOAST / 압축 착시

PostgreSQL 이 큰 값(JSONB 등)을 별도 영역에 **압축해서** 저장하는 방식.

우리 쿼터는 `octet_length(doc::text)` = **비압축 텍스트 길이**로 잰다.
마인드맵 JSON 은 반복이 많아 3~5배 압축되므로 **사용자에게 청구하는 것보다
실제 디스크는 적게 쓴다.** 산정에 유리한 착시이니, 계획에서는 압축을
기대하지 말고 계산하되 실측으로 확인한다(§18.3).

### quota_bytes / plan_quotas

- `plan_quotas` — 요금제별 용량·요금의 **유일한 기준 표**. 관리자 콘솔에서 고친다
- `users.quota_bytes` — 그 사용자의 한도. `users_sync_quota` 트리거가 `plan` 과 묶는다
- 직접 `UPDATE` 하면 그대로 남는다 → **특별 계약용 escape hatch**

용량 = `map_documents.doc` + `map_document_versions.doc` + `attachments.size_bytes`.
**개인별 한도이며 서버 총량 한도는 없다**(§18.7 ③).

### vDisk / 데이터스토어 (ESXi)

- **데이터스토어** — ESXi 호스트가 인식하는 저장 공간(NVMe·SSD·HDD 단위)
- **vDisk** — VM 에 붙이는 가상 디스크. **어느 데이터스토어에 둘지 고를 수 있다**

첨부를 VM-02 OS 디스크에서 떼어 **HDD 데이터스토어의 vDisk** 로 옮기라는
것이 §18.7 ①②다. 지금은 첨부가 차면 API 서버가 통째로 멈춘다.

### 5.1 회사 구조

**SF (San Francisco)**
미국 캘리포니아의 도시. Y Combinator 배치가 이곳에서 3개월간 열린다.
**"SF 상주"는 오가는 것이 아니라 거기 사는 것**이고, 그동안 국내 과제 수행과
영업이 사실상 정지된다. YC 트랙을 실질적으로 결정하는 조건.

**델라웨어 C-Corp**
미국은 회사를 주(state) 단위로 세운다. 사무실이 어디든 **법인 등록은
델라웨어**에 하는 것이 관행인데, 회사법 전문 법원(Court of Chancery)과 100년치
판례가 있어 분쟁 결과를 예측할 수 있기 때문이다.

`C-Corp` 은 세금 유형이다. 핵심은 **주주 국적 제한이 없고 우선주를 발행할 수
있다**는 것 — 벤처투자는 우선주로 이뤄지므로 LLC·S-Corp 으로는 못 받는다.

**flip (플립)**
한국 법인 위에 미국 법인을 얹어 구조를 뒤집는 것.

```
[전]  주주 → 한국법인
[후]  주주 + 투자자 → 미국법인(델라웨어) → 한국법인(자회사)
```

한국 법인이 없어지는 게 아니라 **미국 모회사의 100% 자회사가 된다.**
비용은 법률·회계로 보통 수천만원, 이후 한미 양쪽 회계·세무가 매년 든다.

> ⚠️ **NIPA 와 충돌한다.** 국가연구개발사업 주관기관은 국내 법인이어야 하는데
> flip 후에는 그 법인이 미국 회사의 자회사가 된다. 신청이 원천 봉쇄되는 것은
> 아니나 "정부 지원금 성과의 국외 이전" 지적을 받는다.
> **국내 SI 투자는 이 문제가 없다** — 한국 법인 그대로, IP 도 국내에 남는다.

**SAFE (Simple Agreement for Future Equity)**
지금 지분을 정하지 않고 **다음 투자 때의 가격으로 정산하는** 투자 계약.
초기에는 회사 가치를 매기기 어려워서 쓴다.

YC 표준 딜은 두 장으로 나뉜다 — **$125,000 을 post-money SAFE 로 지분 7%,
$375,000 을 밸류 상한 없는 MFN SAFE 로.** 합쳐 $500,000.

- `post-money` : 투자금이 들어온 뒤 기준으로 지분을 계산 (창업자가 더 희석된다)
- `MFN` (Most Favored Nation) : 나중에 더 좋은 조건이 나오면 그 조건을 소급 적용

**시드 / 시리즈 A**
`시드`는 제품과 초기 사용자를 만드는 첫 라운드, `시리즈 A`는 검증된 모델을
키우는 라운드. **금액이 아니라 단계가 이름을 정한다.**

**SI (Strategic Investor, 전략적 투자자)**
재무 수익이 아니라 **사업 시너지**를 목적으로 투자하는 사업회사.
VC 와 달리 **유통 채널·고객 레퍼런스·업계 신뢰**를 함께 준다.

우리 상황에서 VC 보다 SI 가 맞는 이유 — 국내 공공·금융 온프레미스가 목표
시장인데, 그 시장은 돈이 아니라 **레퍼런스와 조달 경험**으로 뚫린다.

**희석 (dilution)**
새 주식이 발행되면 기존 주주 지분율이 줄어드는 것. **주식 수는 그대로인데
비율이 준다.** 투자를 받을 때마다 일어나는 정상적인 일이지만, 라운드가 쌓이면
창업자 지분이 빠르게 깎인다.

**캡테이블 (cap table)**
누가 몇 주를 갖고 있는지 적은 표. 투자 협상의 실체는 결국 이 표를 어떻게
바꿀 것인가다.

### 5.2 투자 계약에서 다치는 조항

> 인맥으로 들어간 투자일수록 조건을 꼼꼼히 못 따진다. **관계가 좋을 때
> 조항을 정확히 하는 것이 관계를 지키는 방법이다.**

**독점 조항 (exclusivity)**
특정 파트너에게만 판매권을 주는 것. **가장 흔한 사고**가 여기서 난다 —
국내 독점을 줬는데 그 회사가 안 팔면 **다른 채널까지 함께 막힌다.**

굳이 준다면 세 가지를 반드시 붙인다:
`기간 한정(1년)` + `분야 한정(공공만)` + **`최소 구매 수량 미달 시 자동 해제`**

**시그널링 리스크 (signaling risk)**
특정 회사가 주주로 있으면 **그 경쟁사는 고객으로도 투자자로도 오지 않는다.**
SI 투자의 숨은 비용이며, 업계가 좁을수록 크다.

**우선매수권 (ROFR, Right of First Refusal)**
주식을 팔 때 그 투자자가 **먼저 살 권리**. 나중에 다른 인수자가 나타나도
협상이 한 번 더 걸린다.

**동반매도청구권 (drag-along) / 동반매도참여권 (tag-along)**
- `drag-along` : 다수 주주가 팔면 **소수 주주도 끌려 나간다**
- `tag-along` : 다수 주주가 팔 때 **소수 주주도 같이 팔 수 있다**

창업자에게 drag-along 은 위험, tag-along 은 보호 장치다.

### 5.3 제품 지표

**DAU / WAU / MAU**
최근 1일 / 7일 / 30일 안에 실제로 쓴 고유 사용자 수.

| 창 | 맞는 제품 | 이유 |
|---|---|---|
| DAU | 메신저·SNS·게임 | 매일 여는 게 정상 |
| **WAU** | **마인드맵·지식 도구·협업 툴** | 매주는 여는 게 정상 |
| MAU | 세금 신고·여행 예약 | 가끔 쓰는 게 정상 |

**우리는 WAU 를 쓴다.** 마인드맵을 매일 여는 사람은 드물지만, 한 주 내내 한 번도
안 열었다면 사실상 떠난 것이다.

> `90-architecture/infra-architecture.md` §4 는 **DAU** 기준으로 서버 스펙을
> 잡는다. 서버 부하는 동시 접속이 정하므로 그쪽은 DAU 가 맞다.
> **인프라는 DAU, 제품 건강도는 WAU** — 목적이 다른 다른 자다.

**활성(active)의 정의 — 미리 못 박는다**

```
활성 = 그 주에 맵을 열고 저장까지 한 고유 사용자

제외: 로그인만 한 사람 / 공유 링크만 본 사람 / 개발자 본인 계정
```

**로그인을 활성으로 세면 안 된다.** 자동 로그인 때문에 숫자가 부풀고,
그러면 자기 자신을 속이게 된다. 투자자와 심사위원은 정의부터 묻는다.

**D30 잔존율 (retention)**
가입 30일 뒤에도 남아 있는 비율. **WAU 보다 중요하다.**

```
WAU 300 · D30  5%  → 매주 새 사람을 밀어 넣고 있다. 유입을 끊으면 0
WAU 100 · D30 40%  → 진짜 제품이다
```

밑 빠진 독에 물을 붓는지 아닌지를 이 숫자 하나가 말해 준다. 목표 **25% 이상.**

**WAU/MAU 비율 (stickiness)**
월간 사용자 중 매주 오는 비율. 지식 도구는 **20% 이상**이면 건강하다.

**처닝 (churn)**
이탈률. 유료 고객이 매달 몇 %씩 떠나는가. **월 5% 이탈 = 연 46% 손실**이라
신규 유치가 그만큼 없으면 매출이 줄어든다.

**CAC / LTV**
- `CAC` (Customer Acquisition Cost) : 고객 한 명을 데려오는 데 든 비용
- `LTV` (Lifetime Value) : 그 고객이 떠날 때까지 낸 총액

`LTV / CAC ≥ 3` 이 통상 기준. **오픈소스와 콘텐츠 유입은 CAC 를 낮추는 전략**이고,
그것이 개인 무료 티어를 두는 이유다.

**MRR / ARR**
- `MRR` (Monthly Recurring Revenue) : 월 반복 매출
- `ARR` (Annual Recurring Revenue) : MRR × 12

**일회성 구축비는 여기에 넣지 않는다.** 온프레미스 초기 도입비는 MRR 이
아니고, **연 유지보수료가 MRR 이다.** 투자자는 이 구분을 반드시 확인한다.

**실사용률 (storage utilization)**
약속한 용량 대비 실제로 쓰는 비율. 클라우드 스토리지 업계 평균 5~15%.
**유료 사용자 수용량 산정의 핵심 가정**이다
(`90-architecture/infra-architecture.md` §18.4).

### 5.4 국내 제도

**NIPA (정보통신산업진흥원)**
오픈소스 AI·SW 개발 지원 사업의 전담기관. **개발 지원은 민간부담금 면제,
정부지원금 100%, 지분 요구 없음.** 대신 결과물을 오픈소스로 공개해야 하고
사업비 집행에 규제가 따른다.

**TIPS (민간투자주도형 기술창업지원)**
**운영사(엔젤·액셀러레이터)가 먼저 소액 투자를 결정해야** 지원 자격이 생기는
제도. R&D 자금에 창업사업화·마케팅 자금이 더해진다.

NIPA 와 달리 **오픈소스 공개가 조건이 아니라 유료화에 자유롭고**, YC 와 달리
**국내에 남는다.** 우리 상황에서 NIPA 와 YC 의 중간 선택지.

**GS인증 (Good Software 인증)**
TTA 등 공인시험기관이 소프트웨어 품질을 시험해 주는 국가 인증. 1~2등급.

**공공 조달의 입장권이다.** 그리고 NIPA 사업비의 "외부 공인인증기관
시험인증비"가 이 비용이다 — **정부 지원금으로 인증을 받고, 그 인증으로 공공
시장에 들어가는** 경로가 이미 계획에 들어 있다.

**전자정부 표준프레임워크**
행정안전부가 정한 공공 정보화 사업의 개발 표준. **호환성 인증**이 있으면
공공 사업 참여가 수월해진다.

**조달청 / 나라장터 / 디지털서비스 전용몰**
공공기관이 물건과 서비스를 사는 통로. **한 번 등록되면 반복 매출이 되지만
진입 절차가 길다.** SI 파트너의 실질적 가치가 여기 있다 — 그들은 이 길을
수십 번 지나갔다.

**국가연구개발혁신법**
국가 R&D 의 성과 관리를 정한 법. **연구개발성과의 국외 이전에 승인 절차**가
있어 flip 과 얽힌다. 다만 결과물을 Apache-2.0 으로 전체 공개하면 이 논점이
약해진다(이미 전 세계에 공개된 것을 이전한다고 보기 어렵다).

### 5.5 사업 모델

**오픈코어 (open-core)**
코어는 공개하고 일부 기능만 유료로 두는 구조. 우리가 고른 방식이며
경계는 [`../04-extensions/open-core-boundary.md`](../04-extensions/open-core-boundary.md).

**화이트라벨 (white-label)**
파트너가 **자기 브랜드로** 우리 제품을 파는 것. 로고·도메인이 그들 것이 된다.
**셀프호스트 Docker 구성이 이것을 가능하게 한다.**

**총판 / 리셀러 / OEM**
| | 관계 |
|---|---|
| 리셀러 | 우리 제품을 그대로 되판다 |
| 총판 | 특정 지역·분야의 판매를 대행한다 |
| OEM | 그들 제품 안에 우리 것이 부품으로 들어간다 |

> **투자보다 먼저 여기부터 해본다.** 지분 없이 채널이 작동하는지 검증되고,
> 매출 실적이 생기면 투자 협상의 조건이 완전히 달라진다.
> "잠재력"으로 말하는 것과 "이 채널로 2억 팔았다"로 말하는 것은 다른 대화다.

**PoC (Proof of Concept)**
본계약 전에 소규모로 실제 환경에 넣어 보는 것. **B2B 온프레미스 영업의
표준 관문**이며, 통과 못 하면 계약은 없다.

**LOI (Letter of Intent, 의향서)**
법적 구속력은 약하지만 **"도입할 의사가 있다"는 문서**. 계약이 아니어도
NIPA 평가의 '활용성' 항목과 투자 협상에서 실제로 값어치가 있다.
