# 13a. 버전 보관 정책 — 자동 정리와 영구보관

> **이 절이 정하는 것**: `map_document_versions` 를 언제 어떻게 솎아내는가,
> 그리고 사용자가 "이건 남겨야 한다"고 표시하는 수단.
>
> **왜 필요한가**: 지금은 정리 로직이 **없다.** 저장할 때마다 문서 전체
> 스냅샷이 1건씩 영구히 쌓인다. 표준 사용자 1인 용량의 **98.4% 가 버전
> 히스토리**이며, 유료 10,000명 기준 DB 소요가 2.35TB 와 508GB 로 갈린다
> (`../../90-architecture/infra-architecture.md` §18.5).
>
> 작성: 2026-09-02
>
> | 함께 보는 문서 | |
> |---|---|
> | 버전 기록의 동작 정의 | [`13-version-history.md`](13-version-history.md) |
> | 사용자 화면 설명 | [`../../user-guide/11-버전기록.md`](../../user-guide/11-버전기록.md) |
> | 저장·자동저장 | [`../save/14-save.md`](../save/14-save.md) |

## 1. 두 종류의 버전

```
자동 버전(auto)      저장할 때마다 시스템이 만든다. 시스템이 알아서 솎아낸다.
                    사용자는 신경 쓰지 않는다.

영구보관(pinned)     사용자가 "이건 남긴다"고 표시한 것.
                    기간·개수 정리에서 **완전히 제외**된다.
```

**이 구분이 이 설계의 전부다.** 자동은 사용자가 몰라도 되고, 영구보관은
사용자가 의미를 부여한 것이므로 시스템이 절대 손대지 않는다.

---

## 2. 자동 버전 — 시간이 지날수록 성기게

개수만 걸면 사용 패턴에 따라 결과가 극단적으로 갈린다.

```
하루 50번 저장하는 사람 → 20개 상한이면 오늘 오전 것도 이미 없다
한 달 2번 저장하는 사람 → 20개 상한이면 10개월치가 남는다
```

그래서 **간격 기반 솎아내기**를 쓴다. 백업 도구(Time Machine · borg · restic)가
수십 년 써 온 방식이다.

| 구간 | 남기는 밀도 |
|---|---|
| 최근 24시간 | 전부 (최대 20개) |
| 최근 7일 | 하루 3개 |
| 최근 30일 | 하루 1개 |
| 그 이후 | 주 1개 |

**어제 것은 촘촘하고 석 달 전 것은 성기다.** 실제 복구 요청 분포와 일치한다 —
방금 실수를 되돌리는 일이 압도적으로 많고, 3개월 전 특정 시각을 찾는 일은 드물다.

부수 효과로 **개수가 저절로 수렴한다.** 상한을 따로 걸지 않아도 예측 가능하다.

```
Basic 90일  →  20 + 18 + 23 + 9  ≈  70개
Pro   1년   →                      ≈ 110개
```

### 2.1 요금제별 보관 기간

| 요금제 | 자동 보관 | 영구보관 상한 |
|---|---|---|
| Free | **7일** | 3개 |
| Basic | **90일** | 20개 |
| Pro | **1년** | 50개 |
| Team | **1년** | 100개 |

> **Free 7일이 핵심이다.** 무료 사용자가 압도적으로 많은데 이들의 버전이
> 무한히 쌓이면 원가만 나가고 수익은 0이다. 그리고 "히스토리 90일"이
> 유료 전환 이유가 된다 — 보관 기간은 원가 제어이면서 동시에 요금제
> 차별화 축이다.

### 2.2 자동 정리 실행

**저장 트랜잭션 안에서 하지 않는다.** 오래된 버전 100개를 지우느라 그 저장이
몇 초 멈추면 사용자는 이유를 모른다.

```
저장 완료 → BullMQ 'version-prune' 큐에 map_id 적재 (같은 맵은 합친다)
          → 워커가 처리
```

`export`·`ai-generate`·`vault-mirror` 큐 옆에 붙인다.

> ⚠️ **`gcMapImages()` 보다 먼저 돌면 안 된다.** 버전을 지운 직후 사진 GC 가
> 돌면, 아직 살아 있는 다른 버전이 참조하던 사진을 지울 수 있다.
> `gcMapImages()` 가 하루 지난 것만 지우는 보호 장치가 있지만, 순서를
> 명시적으로 잡는다.

## 3. 영구보관 — 사용자가 어떻게 지정하는가

### 3.1 원칙: 새 개념을 가르치지 않는다

**이름을 붙이는 것이 곧 보관하는 것이다.**

Google Docs 의 '이름이 지정된 버전'이 이 방식이다. 사용자는 "영구보관"이라는
개념을 배울 필요가 없다 — **이름을 붙였다는 건 그 버전이 중요하다는 뜻**이고,
중요한 것은 안 지운다. 자연스럽다.

버튼을 둘(이름 붙이기 / 보관하기) 만들지 않는다. **하나다.**

### 3.2 사용자가 마주치는 세 자리

**① 버전 히스토리 패널** — 목록에서 별표를 누른다

```
버전 히스토리
─────────────────────────────────────────
 ★  v1.0 제출본            09-01 18:20   ← 영구보관 (별표 채움 + 이름)
 ☆  자동 저장              09-02 15:25
 ☆  자동 저장              09-02 14:10
 ☆  자동 저장              09-02 11:03
```

별표를 누르면 이름 입력창이 뜬다. **기본값은 시각이 들어간 문구**이고,
그대로 확인만 눌러도 된다.

```
┌─ 이 버전을 보관합니다 ────────────────┐
│  이름  [2026-09-02 오후 3:25 버전    ] │
│        보관한 버전은 정리되지 않습니다  │
│                      [취소]  [보관]    │
└────────────────────────────────────────┘
```

**② 저장 직후** — 마일스톤을 만든 순간

큰 작업을 마쳤을 때가 보관 의사가 생기는 자리다. 저장 알림에 작은 링크 하나면
충분하다. **모달을 띄우지 않는다** — 매번 뜨면 방해가 된다.

```
저장됨 · 오후 3:25          [이 버전 보관]
```

**③ ★ 삭제 예고 알림** — 실질적으로 가장 중요한 접점

사용자는 평소에 히스토리 패널을 열지 않는다. **"무엇을 남길까"를 생각하는
유일한 순간이 여기다.**

```
┌─ 곧 정리되는 버전이 있습니다 ─────────────────┐
│  90일이 지난 버전 12개가 7일 뒤 정리됩니다.    │
│                                                │
│  ☐  08-14 09:30                                │
│  ☐  08-15 14:20                                │
│  ☐  …                                          │
│                                                │
│         [남길 항목 보관]   [그냥 정리]         │
└────────────────────────────────────────────────┘
```

`noticeStore` 를 쓴다. **7일 유예를 두고 알린다** — 조용히 사라지면 사용자는
데이터를 잃었다고 느낀다.

### 3.3 영구보관 상한에 도달하면

```
"보관 버전이 20개로 가득 찼습니다.
 하나를 해제하고 이 버전을 보관하시겠습니까?"

 해제할 버전  [v0.3 초안  (07-12)  ▾]
                       [취소]  [교체하여 보관]
```

**이때만 사용자에게 선택을 시킨다.** 자동 버전 정리는 절대 사용자에게 미루지
않지만, 영구보관은 다르다 — 사용자가 이미 별표를 누른 그 자리에 있고,
**저장을 막는 것이 아니라 별표를 막는 것**이라 작업이 중단되지 않는다.

> ⛔ **"100개 넘었으니 정리하세요" 식의 알림으로 자동 버전을 관리하지 않는다.**
> 대부분 무시되고, 그러면 저장을 막거나(작업 중단) 그냥 쌓이거나(상한이
> 상한이 아님) 둘 다 나쁜 결과가 된다. 자동은 자동이어야 한다.

### 3.4 해제

별표를 다시 누르면 해제된다. **경고를 띄운다.**

```
보관을 해제하면 이 버전은 자동 정리 대상이 됩니다.
보관 기간(90일)이 이미 지난 버전이므로 다음 정리에서 삭제됩니다.
                                        [취소]  [해제]
```

## 4. 규칙

### 4.1 용량 회계

**영구보관도 쿼터를 차지한다.** 제외하면 무한 저장 우회로가 된다.

```
quota = map_documents.doc
      + map_document_versions.doc     ← pinned 포함
      + attachments.size_bytes
```

개수 상한(§2.1)이 그 소모를 제한하는 장치다.

### 4.2 요금제 강등

Pro(50개) → Basic(20개) 로 내려가도 **초과분을 지우지 않는다.**
새로 보관하는 것만 막는다.

> 결제 실패나 요금제 변경으로 사용자 데이터를 삭제하는 일은 없다.
> 이 원칙은 `27-sync-model.md` §4 ②(고아 노드를 지우지 않고 뿌리로 올린다)와
> 같은 계열이다 — **사용자가 만든 것을 우리가 지우지 않는다.**

### 4.3 협업맵의 권한

| 동작 | creator | editor | viewer |
|---|---|---|---|
| 보관 지정 | ✅ | ✅ | ❌ |
| 이름 수정 | ✅ | 자기가 붙인 것만 | ❌ |
| **보관 해제** | ✅ | **자기가 붙인 것만** | ❌ |

남이 "제출본"이라고 표시한 것을 아무나 해제할 수 있으면 표시의 의미가 없다.

### 4.4 복원·삭제와의 관계

- **영구보관 버전으로 복원해도 그 버전은 사라지지 않는다.** 복원은 새 버전을
  만드는 것이지 되감는 것이 아니다
- **맵을 삭제하면 버전도 함께 휴지통으로 간다.** 맵이 없는데 버전만 남을
  이유가 없다. 복원하면 함께 돌아온다

---

### 4.5 협업맵의 기준 — 개설자(creator)를 따른다

협업맵의 보관 기간·영구보관 상한은 **개설자의 요금제**를 따른다.
참여자 요금제는 보지 않는다. 여러 사람의 요금제를 섞으면 "이 버전이 왜
사라졌는가"를 설명할 수 없게 된다.

---

#### 4.5.1 소유권 이전

개설자는 소유권을 다른 참여자에게 넘길 수 있다. **제안 → 수락**이며
일방적으로 넘기지 않는다.

> **왜 수락이 필요한가**: 일방 이양을 허용하면 받는 사람 용량이 갑자기 차고,
> 원치 않는 맵의 책임을 지게 된다. 무료 사용자에게 10GB 맵을 떠넘기는
> 남용도 가능하다. Slack 워크스페이스·GitHub 저장소 이전이 모두 이 방식이다.

##### 이전되는 것 / 안 되는 것

| | 이전 | 이유 |
|---|---|---|
| 최신 버전 (`map_documents.doc`) | ✅ | 맵 그 자체 |
| 첨부 파일 | ✅ | 없으면 맵이 깨진다 |
| **영구보관 버전** | ✅ | **사람이 의미를 부여한 것이다** |
| 자동 버전 | ❌ | 시스템이 만든 것. 소유자 요금제에 종속된다 |

영구보관을 함께 넘기는 것은 §4.2(강등 시 초과분을 지우지 않는다)와 같은
계열이다 — **사용자가 만든 것을 우리가 지우지 않는다.**

##### 용량 검사

```
받는 사람 사용량 + (최신 버전 + 첨부 + 영구보관)  ≤  받는 사람 한도
```

1. **제안 시** 미리 보여준다 (안내용)
2. **수락 시점에 다시 검사한다** — 그 사이 다른 파일을 올렸을 수 있다.
   최종 판정은 이쪽이다
3. 부족하면 거부한다

```
용량이 모자라서 권한 이양이 불가합니다.
필요 3.4 GB / 여유 2.1 GB
```

##### 제안 화면

받는 사람이 **이전 후 무엇이 달라지는지** 보고 결정해야 한다.

```
┌─ 소유권 이전 제안 ───────────────────────────────┐
│  홍길동님이 "2027 사업계획" 의 소유권을            │
│  회원님께 넘기려 합니다.                           │
│                                                    │
│  이 맵 용량        3.4 GB                          │
│  회원님 여유       6.6 GB / 10 GB                  │
│  이전 후           9.99 GB / 10 GB   ⚠️            │
│                                                    │
│  ⚠️ 회원님 요금제(Basic)는 버전을 90일 보관합니다.   │
│     영구보관 12개는 그대로 유지됩니다.              │
│                                                    │
│              [거절]        [수락]                  │
└────────────────────────────────────────────────────┘
```

##### 이전 후

- 원 개설자는 **editor 로 남는다.** 자동으로 내보내지 않는다 — 실수로
  넘겼을 때 되돌리거나 확인할 방법이 없어진다. 나가는 것은 본인이 결정한다
- 보관 기간이 새 개설자 요금제로 바뀐다
- 영구보관이 새 상한을 넘으면 **유지하되 추가만 막는다** (§4.2 와 동일)

#### 4.5.2 넘어가지 않는 자동 버전 — 즉시 지우지 않는다

**원 개설자 계정에 30일 남기고**, 이전 제안 화면에서 ZIP 내려받기를 안내한다.

```
⚠️ 자동 버전 87개는 넘어가지 않습니다.
   30일간 회원님 계정에 남으며 그 후 정리됩니다.

   [히스토리 ZIP 내려받기]
```

##### ZIP 구조

```
2027-사업계획_history_20260902.zip
├─ README.md                          무엇이 들었는지 · 읽는 법
├─ ★ v1.0 제출본 (2026-08-14).md      영구보관은 이름과 별표를 파일명에 살린다
├─ 2026-08-14 0930.md
├─ 2026-08-15 1420.md
│  …
└─ files/
   ├─ img-3f7a2b91c4d05e68.png        내용 해시. 버전 간 공유
   └─ …
```

**설계 근거 셋**

1. **기존 배관을 쓴다.** `serializeEmm()` 을 버전마다 돌려 한 ZIP 에 담는다.
   새 포맷을 만들지 않는다
2. **사진이 중복되지 않는다.** 87벌이 같은 사진을 참조하는 것이 보통이므로
   `files/` 를 공유하면 크기가 87배가 아니라 거의 1배다.
   파일명을 내용 해시로 쓰는 이유가 여기서도 나온다 (vault-mirror.md §4 와 동일 규칙)
3. **서버 없이 열린다.** `content-permanence.md` §7.1 의 약속이 지켜진다.
   이 ZIP 은 "떠나는 사람이 챙겨 가는 것"이라 그 약속이 가장 중요한 자리다

##### 생성 경로

기존 `export` 큐를 쓴다. **새 경로를 만들지 않는다.**

| 버전 수 | 처리 |
|---|---|
| 20개 이하 | 즉석 생성 → 브라우저 다운로드 |
| 그 이상 | `export` 큐 → 완료 알림 → 다운로드 링크 |

87벌 직렬화는 수 초~수십 초가 걸린다. **동기 처리하면 안 된다.**
생성된 ZIP 은 서버에 **7일 보관 후 삭제**한다.

> ⚠️ **30일 뒤 자동 버전을 지울 때 사진 GC 를 조심한다.** 그 버전들만
> 참조하던 사진이 고아가 된다. `gcMapImages()` 가 하루 지난 것만 지우므로
> 30일 유예 안에서는 안전하지만, 실행 순서를 명시적으로 잡는다.

> **같은 기능이 탈퇴 시에도 필요하다.** 계정을 지우기 전 "내 데이터 전부
> 내려받기"의 구조가 이것과 같다. 한 번 만들어 두 곳에 쓴다.

## 5. DB

```sql
ALTER TABLE public.plan_quotas
  ADD COLUMN IF NOT EXISTS version_days   INTEGER,   -- NULL = 무제한
  ADD COLUMN IF NOT EXISTS max_pinned     INTEGER;   -- NULL = 무제한

UPDATE public.plan_quotas SET version_days =   7, max_pinned =   3 WHERE plan = 'free';
UPDATE public.plan_quotas SET version_days =  90, max_pinned =  20 WHERE plan = 'basic';
UPDATE public.plan_quotas SET version_days = 365, max_pinned =  50 WHERE plan = 'pro';
UPDATE public.plan_quotas SET version_days = 365, max_pinned = 100 WHERE plan = 'team';

ALTER TABLE public.map_document_versions
  ADD COLUMN IF NOT EXISTS pinned     BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN IF NOT EXISTS label      TEXT,
  ADD COLUMN IF NOT EXISTS pinned_by  UUID REFERENCES public.users(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS pinned_at  TIMESTAMPTZ;

-- 정리 대상 조회용 (pinned 는 아예 인덱스에 안 들어간다)
CREATE INDEX IF NOT EXISTS idx_versions_prune
  ON public.map_document_versions(map_id, created_at DESC)
  WHERE pinned = FALSE;
```

`NULL = 무제한`으로 두면 특별 계약·온프레미스 고객에게 예외를 줄 수 있다.
`users.quota_bytes` 를 직접 UPDATE 해 특례를 주는 것과 같은 방식이다.

## 6. 적용 순서 — 소급 적용하지 않는다

규칙을 켜는 순간 기존 버전 수천 개가 한꺼번에 사라지면 되돌릴 수 없다.

```
1단계  새 버전부터만 규칙 적용
2단계  기존 초과분은 목록만 보여주고 사용자가 "정리하기" 로 실행
3단계  안내 후 30일 유예를 두고 자동 정리
```

> 지금은 DB 를 초기화하므로 이 문제가 없다. 다만 **운영 중 값을 바꿀 때
> 같은 문제가 생긴다.** 그래서 정책을 코드가 아니라 `plan_quotas` 에 둔다 —
> 관리자 콘솔에서 조정할 수 있고, 그것이 그 테이블의 설계 의도다.

## 7. ⚠️ 판매 시작 전에 확정할 것

- 반대로 넉넉하게 시작해 나중에 조이는 것도 안 된다

지금 정하는 값이 사실상 영구적이라고 보고 확정한다.
