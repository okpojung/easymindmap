## 1. 목적 (Purpose)

Markdown 문서를 기반으로 Mindmap을 생성하기 위한
**표준 파싱 및 렌더링 정책**을 정의한다.

이 문서는 다음을 명확히 한다:

- Markdown → Mindmap 구조 변환 규칙
- Heading 기반 Node 생성 정책
- Node 내용(Content) 수집 규칙
- 스타일/레이아웃 분리 원칙

---

## 1A. 핵심 저장 정책 (Storage Policy)

> 이 세 가지 정책은 저장 모델(문서 JSON — `node.text`, `MindNode`에 node_type 없음)과 직결되는 핵심 규칙이다.

**정책 1 — Raw Text 저장:**  
Markdown 텍스트는 파싱하거나 HTML로 변환하지 않고 **raw 원문 그대로** `node.text`(문서 JSON)에 저장한다. 렌더링(파싱)은 항상 프론트엔드 표시 시점에 수행한다.

**정책 2 — 리스트(List) 처리 (현행):**  
- **순서 없는 목록 (`-`, `*`, `+`)**: 항목마다 **자식 노드로 분해**한다.
- **순서 있는 목록 (`1.`, `2.`)**: 항목마다 **자식 노드로 분해**한다.
- **체크박스 목록 (`- [ ]`, `- [x]`)**: 기본은 **노드 본문의 체크 줄**로 유지, `blockPlacement: 'note'` 옵션이면 **체크리스트 노트**로 변환한다.

**정책 3 — Heading `#` 기호 제거 저장 (현행):**  
Heading 기호(`##`, `###` 등)는 Node 트리 구조 파싱의 기준으로만 사용하며, 실제 `node.text`에는 **`#` 기호를 제거한 텍스트**를 저장한다. 내보내기(Export) 시 노드 깊이에 따라 `#`를 다시 부여한다. Heading 레벨에 따른 글자 크기 변경은 적용하지 않는다(스타일은 NODE_STYLE 정책 따름).

## 2. 기본 원칙 (Core Principles)

### 2.1 구조와 스타일의 완전 분리

- Markdown은 **구조 정의 용도**
- Mindmap은 **스타일 및 시각 표현 담당**

| 항목 | Markdown | Mindmap |
|------|----------|---------|
| 역할 | 구조 정의 | 시각 표현 |
| Heading | Level 정의 | 글자 크기 영향 없음 |
| 스타일 | 제한적 | 완전 제어 |

---

### 2.2 Heading = Node Level

Markdown Heading은 다음과 같이 변환된다:

| Markdown | 의미 | Mindmap |
|----------|------|---------|
| #        | H1   | Root Node (**첫 번째 H1만** 루트) |
| ##       | H2   | Level 1 |
| ###      | H3   | Level 2 |
| ####     | H4   | Level 3 |
| #####    | H5   | Level 4 |
| ######   | H6   | Level 5 |

> **h1Mode 부기**: 첫 H1만 루트가 되며, 두 번째 이후 H1이 존재하면(h1Mode) 전체 heading이 **한 단계 하강**한다 — H1들이 루트의 자식(Level 1)이 되고 루트는 파일명 등으로 별도 생성된다.

---

### 2.3 글자 크기 정책

- ❌ Heading에 따른 글자 크기 변경 없음
- ✅ 모든 텍스트는 Map/Node Style 정책을 따른다

우선순위:

1. Node 개별 스타일
2. Subtree override
3. Map 기본 스타일

---

### 2.4 문서형 Markdown vs 아웃라인형 Markdown (설계 초안 — 미채택)

> 현행 파서는 문서형/아웃라인형 구분 없이 **단일 규칙**으로 동작한다: heading은 계층, 불릿·순번 리스트는 자식 노드 분해, 문단은 노드 본문. 유일한 옵션은 `blockPlacement`(§4.3)다.

### 2.5 리스트 정책 (현행)

- **순서 없는 목록 (Unordered List)**: 항목마다 **자식 노드로 분해**한다 (들여쓰기 깊이 = 노드 깊이).
- **순서 있는 목록 (Ordered List)**: 항목마다 **자식 노드로 분해**한다.
- **체크박스 목록 (Task List)**: 기본은 **노드 본문의 체크 줄**로 유지, `blockPlacement: 'note'`이면 **체크리스트 노트**로 변환.
- export 시에도 위 구조화 규칙에 따라 Markdown 리스트로 역변환된다.

### 2.6 `#` 기호 처리 정책

- 줄 시작 후 공백 규칙을 만족하는 경우만 heading으로 해석한다.
- 예:
  - `# 제목` → heading
  - `C#`, `#태그`, `가격 #1` → heading 아님
- import parser는 CommonMark heading 규칙을 기본 준수한다.

## 3. Node 생성 규칙 (Node Creation Rule)

### 3.1 기본 생성 규칙

- Heading이 나오면 새로운 Node 생성
- Heading 레벨에 따라 부모/자식 관계 결정

---

### 3.2 부모 결정 알고리즘

```pseudo
현재 Heading Level = L

이전 Node 중에서
Level < L 인 가장 가까운 Node를 Parent로 설정
````

---

### 3.3 예시

```md
# 마인드맵 개발
## 목표
## 기능 정의
### 기능1
### 기능2
## DB설계
```

👉 변환 결과

```
마인드맵 개발 (Root)
 ├─ 목표
 └─ 기능 정의
 │   ├─ 기능1
 │   └─ 기능2
 └─ DB설계
```

## 4. Import 옵션 (현행 — blockPlacement 단일 옵션)

> hybrid/document/outline 3종 Import Mode는 설계 초안 — 미채택. 현행 옵션은 `blockPlacement` 하나다.

---

### 4.1 Import 기준 요약 (현행)

- Heading → 노드 계층 (첫 H1만 루트, h1Mode 시 한 단계 하강 — §2.2)
- 불릿·순번 리스트 → 자식 노드 분해 (§2.5)
- 문단 → 노드 본문
- 코드 펜스·표·독립 이미지 → 별도 자식 노드(기본) 또는 노트 (§4.3)
- 세부 기준은 §2.5(리스트 정책), §2.6(`#` 처리)를 우선 적용

---

### 4.3 blockPlacement 옵션

| 값     | 설명                          |
| -------- | ----------------------------- |
| `node` (기본값) | 코드 펜스·표·독립 이미지를 **별도 자식 노드**로 분리 |
| `note`   | 위 블록들을 해당 노드의 **노트 블록**으로 저장 (체크박스 목록은 체크리스트 노트로) |

---

### 4.4 기본 정책

- 기본값은 `blockPlacement: 'node'`.
- **A4 이동 규칙**: 한 문단이 `NODE_A4_CHARS`(2500자)를 초과하면 노드 본문 대신 노트로 이동한다.
- 자동 추론에 의해 옵션을 변경하지 않는다.

---

## 5. Heading 기호 (`#`) 정의

### 5.1 기본 정의

- `#`는 Markdown에서 Heading(제목)을 나타내는 기호이다.
- Heading은 Node Tree 구조를 생성하는 기준이 된다.

---

### 5.2 Heading 인식 조건

다음 조건을 모두 만족할 때만 Heading으로 인정한다.

1. 라인의 시작 위치에서 등장해야 한다.
2. `#` 개수는 1개 이상 6개 이하만 허용한다.
3. `#` 뒤에는 텍스트가 존재해야 한다.
4. `#` 뒤에는 최소 1칸 공백이 있어야 한다.

허용 예:

```md
# 제목
### 기능 상세
```

---

### 5.3 Heading Level 정의

| 기호   | Level | 의미          |
| ------ | ----- | ------------- |
| #      | 1     | Root 또는 최상위 (**첫 H1만 루트** — H1이 여럿이면 h1Mode로 전체 한 단계 하강) |
| ##     | 2     | 1단계 하위     |
| ###    | 3     | 2단계 하위     |
| ...    | ...   | ...           |
| ###### | 6     | 최대 depth (7개 이상 `#`는 heading이 아니라 일반 문단) |

---

### 5.4 Heading 변환 규칙

- Heading은 Node로 변환된다.
- Level 차이에 따라 Parent-Child 관계가 결정된다.
- Level이 2 → 4로 점프하는 경우:
  → 중간 Level은 자동 보정하지 않고 가장 가까운 상위 Node에 연결한다.

---

### 5.5 Heading이 아닌 `#` 처리

다음 경우의 `#`는 Heading으로 해석하지 않는다.

| 경우 | 예시 | 처리 |
|---|---|---|
| 문장 중간 | `가격은 #1 정책을 따른다` | 일반 Content |
| 프로그래밍 언어 | `C#` | 일반 Content |
| 태그/해시 | `#todo` `#중요` | 일반 Content |
| escape 문자 | `\# 제목 아님` | 일반 Content |
| 코드 블록 내부 | ` ```bash\n# 주석 ``` ` | 일반 Content |
| 인라인 코드 | `` `# not heading` `` | 일반 Content |

---

### 5.6 Literal Sharp (`#` 문자) 표현

문서 작성자가 `#`를 문자 그대로 사용하고 싶을 경우 허용 방식:

- `\#`
- 인라인 코드: `` `#` ``
- 코드 블록 내부 사용

> 권장: Heading으로 오해될 수 있는 경우 반드시 escape 사용

---

### 5.7 Heading 판정 우선순위

1. Code Block 내부 → 무조건 Heading 제외
2. Inline Code 내부 → 제외
3. Escape(`\#`) → 제외
4. 라인 시작 여부 확인
5. Heading 규칙 적용

---

### 5.8 Edge Case 처리

| Case | 입력 예시 | 처리 |
|---|---|---|
| 빈 Heading | `##` | **일반 문단으로 처리** (heading 불인정) |
| 공백만 존재 | `##    ` | **일반 문단으로 처리** |
| 7개 이상 `#` | `####### 제목` | **일반 문단으로 처리** |
| 잘못된 Level Jump | `# A` → `#### B` | B는 A의 child로 처리 |
| Heading + List 혼합 | `## 기능\n- 항목` | Heading Node 생성 후 List는 규칙에 따라 처리(자식 노드 분해) |

---

## 6. Node Content 수집 규칙 (Content Aggregation)

### 4.1 핵심 규칙 (현행)

> **다음 동일 또는 상위 Level Heading이 나오기 전까지의 내용은 현재 Node에 귀속된다.** 단, 블록 종류에 따라 본문/자식 노드/노트로 나뉜다.

---

### 4.2 블록별 귀속 규칙 (현행)

* 일반 텍스트(문단) → 노드 본문 (A4 2500자 초과 시 노트로 이동)
* 리스트(불릿·순번) → **자식 노드 분해**
* 체크박스 목록 → 본문 체크 줄(기본) / 체크리스트 노트(`note` 옵션)
* 코드 블록·표·독립 이미지 → **별도 자식 노드**(기본) / 노트(`note` 옵션)
* 인용문 → **직전 블록에 연결**

---

### 4.3 종료 조건

현재 Node의 Content 수집은 아래에서 종료된다:

* 같은 Level Heading 등장
* 더 높은 Level Heading 등장

---

### 4.4 예시

```md
## 목포
목포는 전라남도에 위치한다.

- 항구 도시
- 관광지

## 기능 정의
```

👉 결과

Node: "목포" — 본문: "목포는 전라남도에 위치한다."

자식 노드: "항구 도시", "관광지" (불릿 리스트 분해)

---

## 7. 공백 및 포맷 처리 규칙

### 5.1 Heading 공백 필수

```md
##기능 정의   ← 불허 (heading 아님 — 일반 문단)
## 기능 정의  ← 허용
```

→ `#` 뒤 **공백이 반드시 있어야** heading으로 인정한다 (CommonMark 준수 — §5.2 조건 4).

---

### 5.2 Heading 텍스트 정리

* 앞뒤 공백 제거
* 연속 공백 → 1개로 축소

---

### 5.3 빈 Heading 처리

```md
## 
```

→ heading으로 인정하지 않고 **일반 문단으로 처리**한다.

---

## 8. 리스트 처리 규칙 (현행)

### 8.1 순서 없는 목록
```md
- 항목1
- 항목2
```
👉 각각 **자식 노드로 분해** (들여쓰기 깊이 = 노드 깊이)

### 8.2 순서 있는 목록
```md
1. 1단계
2. 2단계
```
👉 각각 **자식 노드로 분해**

### 8.3 체크박스 목록
```md
- [ ] 할일1
- [x] 할일2
```
👉 기본: **노드 본문의 체크 줄**로 유지 (체크 상태 반영) / `blockPlacement: 'note'` 옵션: **체크리스트 노트**로 저장

````
## 10. 스타일 관련 정책 (중요 — 현행)

### 8.1 Markdown 스타일 처리

- ❌ Heading 크기만 미반영 (레벨 기호는 구조로만 사용, `#` 제거 저장)

---

### 8.2 허용 스타일

- 인라인 마커 6종 (위 표)
- code block (별도 자식 노드/노트)
- 링크

### 9.1 잘못된 Heading 순서

```md
````

👉 처리:

```md

```

👉 처리:

* 가상 Root 생성

```

```

---

### 9.3 내용만 있는 경우 (견출 없음)

```md
내용만 있음
```

👉 처리 (현행):

* 루트 노드를 **파일명**으로 생성
* 본문 전체는 **루트 노드의 노트**로 저장

---

### 9.4 중복 Heading

```md
## 기능
## 기능
```

👉 허용 (별도 Node)

### 9.5 매우 깊은 Level

* H6 초과(`#` 7개 이상) → heading으로 인정하지 않고 **일반 문단으로 처리**

---

### 9.6 대용량 Content

* 길이 제한 강제 없음 — 단, 한 문단이 `NODE_A4_CHARS`(2500자)를 초과하면 노드 본문 대신 노트로 이동 (§4.4)

## 12. Import 처리 흐름 (현행 — AST 없이 줄 단위 스캔)

```pseudo
Markdown 입력
 → 줄 단위 스캔 (코드 펜스/표 등은 버퍼에 누적)
 → heading 레벨 스택으로 부모 결정
 → Node Tree 생성 (블록별 본문/자식 노드/노트 귀속)
 → Mindmap Model(MindNode) 변환
```

> AST 기반 파서(Tokenizer → AST)는 설계 초안 — 미채택. 현행 구현은 **줄 단위 스캔 + 블록 버퍼 + heading 스택** 방식이다 (`packages/emm-parser`).

---

## 13. Export 정책 (현행 — 단일 EMM 직렬화)

* Simple/Full 2모드는 설계 초안 — 미채택. Export는 **단일 EMM 직렬화** 하나다.
* 구조는 Markdown(heading `#` 재부여·리스트 역변환)으로, 스타일·레이아웃 등 부가 정보는 **메타데이터 주석**으로 **항상 포함**한다.
* 메타데이터 주석 덕분에 내보내기 → 불러오기 **라운드트립**이 성립한다.
