# 27. 협업 동기화 모델 — 무엇으로 합칠 것인가 (2026-08-16 설계)

> **이 문서가 정하는 것**: 여러 사람이 같은 맵을 동시에 고칠 때 **무엇을
> 기준으로 합치는가**, 그것이 **지금의 문서 모델과 어떻게 맞물리는가**,
> 그리고 **무엇이 공개 코어이고 무엇이 유료 모듈인가**.
>
> **정하지 않는 것**: 초대·권한·스레드·채팅. 그건
> [`25-map-collaboration.md`](./25-map-collaboration.md) 와
> [`26-realtime-chat.md`](./26-realtime-chat.md) 에 이미 있다.
>
> 협업은 **유료 기능**이다. 구현은 private 저장소(`okpojung/easymindmap-pro`)
> 에 있고, **설계는 여기 공개로 남긴다**
> ([open-core-boundary.md](../open-core-boundary.md)).

---

## 0. 먼저 — 기존 설계에서 **더는 맞지 않는 전제**

`25-map-collaboration.md` 는 2단계 전제 위에 쓰여 있는데, **둘 다 지금
코드에 없다.** 그 문서를 고치기 전에 여기 적어 둔다.

| 그 문서의 전제 | 지금 사실 (2026-08-16 확인) |
|---|---|
| Supabase Realtime 으로 브로드캐스트 | **Supabase 는 Auth 전용**이다. GoTrue 만 자체 호스팅하고 Realtime 은 쓰지 않는다 |
| Soft Lock 을 Redis 에 둔다 | **Redis 가 없다.** `apps/api` 에 클라이언트도 의존성도 없다 |
| WebSocket Gateway (VM-02) | **없다.** `@nestjs/websockets` 를 쓰지 않는다 |
| LWW(마지막 쓰기 우선)로 충돌 해소 | 아래 §2 에서 **바꾼다** |

> "이미 있는 것을 쓰면 공수가 준다"가 그 설계의 근거였는데, **그 '이미
> 있는 것'이 없다.** 없는 것을 전제로 세운 계획은 착수하는 날 무너진다.

## 1. 지금의 문서 모델 — 협업을 붙이기 전에 알아야 할 것

```
map_documents.doc  JSONB   ← 맵 하나가 통째로 한 행. 트리가 그대로 들어간다
  MindNode { id, text, style?, notes?, links?, attachments?,
             image?, images?, children: MindNode[] }
```

**셋이 중요하다.**

**① 문서는 통째로 저장된다.** 자동저장은 `PUT /v1/maps/:id/document` 로
**스냅샷 전체**를 보낸다. 부분 갱신 경로(`PATCH /v1/maps/:mapId/nodes`)와
정규화 `nodes` 표가 **있기는 하지만 프런트가 쓰지 않는다.**

**② 이미지가 문서 안에 있다.** 클립보드로 붙인 사진은 `image.src` ·
`images[].src` 에 **data URL 로** 들어간다. 즉 **문서 하나가 수 MB 가 될
수 있다.**

**③ 단독 편집 잠금이 이미 돈다.** `map_edit_locks` — 맵당 한 세션, TTL 60초.
**`maps.kind` 를 보지 않는다.** 지금 상태로 두 사람이 같은 맵을 열면
**둘째 사람은 읽기 전용이 된다.** 협업의 첫 장애물은 CRDT 가 아니라 이것이다.

---

## 2. 결정 ① — **LWW 를 버리고 CRDT(Yjs)로 간다**

### 2.1 LWW 가 마인드맵에서 지는 이유

LWW 는 "같은 필드를 동시에 고치면 늦게 온 쪽이 이긴다"이다. 값 하나짜리
필드(색·접힘)에는 충분하다. **문제는 두 군데다.**

**텍스트.** A 가 문장 앞에 단어를 넣고 B 가 뒤에 넣으면, LWW 는 **한쪽 문장을
통째로 버린다.** 사용자는 자기가 쓴 문장이 사라지는 것을 본다 — 그것도
충돌 경고 없이. 마인드맵의 노드 텍스트는 짧지만 **노트 블록은 문단이다.**

**트리 구조.** A 가 노드를 다른 부모로 옮기고 B 가 그 부모를 지우면, LWW
로는 **부모 없는 노드**가 남거나 노드가 통째로 사라진다. 순서를 바꿔 적용해도
결과가 달라진다 — 협업의 기본 요구(**어느 순서로 도착해도 같은 결과**)가
깨진다.

### 2.2 Yjs 를 고른 이유 (Automerge 대신)

| | Yjs | Automerge |
|---|---|---|
| 트리 이동 | `Y.Map` + parentId 로 표현, 순환은 **우리가 막는다** | 같음 |
| 텍스트 | `Y.Text` — 문자 단위 병합이 성숙하다 | 성숙하다 |
| 메모리·속도 | 문서가 클수록 유리 | 상대적으로 무겁다 |
| 부수 자원 | **서버가 상태를 안 들고도 된다**(업데이트만 이어 붙임) | 같음 |
| 생태계 | 에디터 바인딩·awareness 가 이미 있다 | 적다 |

결정 근거는 성능 수치가 아니라 **awareness(접속자·커서)가 같은 라이브러리에
있다**는 점이다. 커서 공유를 따로 만들면 **연결이 둘**이 되고, 하나가 끊겼을
때 화면이 "접속 중인데 편집이 안 되는" 상태를 보여 준다.

> **CRDT 를 쓴다고 충돌이 사라지는 것은 아니다.** CRDT 가 보장하는 것은
> "모두가 같은 결과에 도달한다"뿐이고, **그 결과가 사용자가 원한 것인지는
> 별개다.** 트리 순환·삭제된 부모 같은 **의미 규칙은 우리가 지켜야 한다**(§4).

---

## 3. 결정 ② — **CRDT 에 담는 것은 구조와 텍스트뿐이다**

이미지 data URL 을 CRDT 에 넣으면 **한 사람이 사진 하나 붙일 때마다 수 MB
가 모든 접속자에게 흐른다.** 그리고 그 바이트가 **업데이트 로그에 영원히
남는다** — CRDT 는 지운 것도 묘비로 들고 있기 때문이다.

```
CRDT 안 (Y.Doc)                        CRDT 밖
─────────────────────────────────      ─────────────────────────
노드 id · parentId · 순서               이미지 바이트   → 첨부 저장소
텍스트(Y.Text) · 노트 블록              첨부 파일 바이트 → 첨부 저장소
스타일 · 색 · 접힘 · 태그 · 링크         커서·선택 위치   → awareness
첨부/이미지의 **참조(id·url)**          채팅 메시지     → 별도 표
```

### 3.1 그래서 **선행 조건**이 하나 생긴다 — 공개 코어 작업

**협업을 시작하기 전에, 이미지가 문서 밖으로 나가야 한다.**

지금 `image.src` 는 data URL 이다. 이것을 **첨부 저장소에 올리고 문서에는
참조만** 남기도록 바꾼다. 이미 그 길이 있다 — 첨부는 맵 내장 10MB 를 넘으면
서버 저장소로 우회한다(`17-attachment-storage`). 이미지도 같은 길을 쓴다.

> **이건 유료 기능이 아니라 코어의 문제다.** 단독 사용자에게도 이득이다 —
> 문서가 가벼워지면 자동저장이 빨라지고, 버전 히스토리가 같은 사진을
> 스냅샷마다 복사하지 않는다. **협업이 없어도 해야 할 일**이므로 공개
> 코어에 넣는다.
>
> 그리고 **역호환**이 필요하다. 이미 data URL 로 저장된 문서가 있다 —
> 열 때 그대로 읽히되, **다음 저장에서 올라가도록** 한다. 한 번에 전부
> 옮기는 마이그레이션은 하지 않는다(되돌릴 수 없는 데이터 작업이다).

---

## 4. 결정 ③ — 트리 규칙은 **우리가** 지킨다

CRDT 는 "부모를 잃은 노드"나 "자기 조상 밑으로 들어간 노드"를 막아 주지
않는다. 두 규칙을 **적용 시점에** 강제한다.

**① 순환 금지.** A 를 B 밑으로, 동시에 B 를 A 밑으로 옮기면 CRDT 는 둘 다
받아들이고 **모두가 똑같이 이상한 상태**가 된다. `move` 를 반영할 때 조상
사슬을 훑어 순환이면 **나중 것을 무시한다** — 무시했다는 것을 그 사용자
화면에 알린다. 조용히 되돌리면 "내가 옮긴 게 왜 안 되지"가 된다.

> 코어에 이미 같은 규칙이 있다 — `move_node_subtree` 가 순환을 막는다.
> **규칙을 두 벌로 만들지 않는다**: 정규화 경로와 CRDT 경로가 **같은 판정**을
> 쓰도록 판정 함수를 코어에 둔다.

**② 삭제된 부모 밑의 노드.** A 가 부모를 지우고 B 가 그 밑에 자식을 더하면,
자식은 **갈 곳이 없다.** 지우지 않고 **맵 루트로 올린다** — 그리고 그렇게
했다고 말한다. 사용자가 방금 쓴 것을 우리가 지우면 안 된다.

---

## 5. 결정 ④ — 전송은 **우리 WebSocket** 하나

Supabase Realtime 도 Redis 도 쓰지 않는다. 유료 모듈이 **자기 WebSocket
게이트웨이를 들고 온다**(코어의 이음매가 모듈째 등록하므로 가능하다 —
`open-core-boundary.md` §4).

```
브라우저 ──WS──▶ 유료 모듈 게이트웨이 ──▶ 메모리 안의 Y.Doc(맵별)
                       │                        │
                       │                        ├─ 주기적으로 업데이트 로그 적재
                       └─ awareness 중계          └─ 주기적으로 스냅샷 물질화(§6)
```

**Redis 를 지금 넣지 않는 이유**: 인스턴스가 하나면 필요 없다. 여러 인스턴스로
늘릴 때 **같은 맵이 같은 인스턴스로 가도록** 라우팅하는 것이 먼저이고, 그래도
모자랄 때 pub/sub 을 넣는다. **없어도 되는 부품을 먼저 넣으면, 그것이 죽었을
때의 장애를 공짜로 얻는다.**

> 접속자 상한 20명/맵은 그대로 지킨다(`25-map-collaboration.md` §6).
> 상한이 있어야 한 맵이 인스턴스를 다 먹는 일을 막는다.

---

## 6. 결정 ⑤ — **기존 스냅샷을 버리지 않는다**

협업맵이라고 저장 형식을 갈아 치우면, **내보내기·버전 히스토리·문서함
목록·단독 열기가 전부 두 벌**이 된다.

그래서 **CRDT 는 편집 중의 표현이고, `map_documents.doc` 는 그대로 정본**이다.

```
편집 중          Y.Doc (메모리) + 업데이트 로그 (유료 표)
저장 시점        Y.Doc → 지금과 똑같은 doc JSONB 로 물질화 → map_documents
                 (그 시점에 버전 히스토리도 지금 규칙 그대로 쌓인다)
아무도 없을 때    메모리에서 내린다. 다음에 열 때 doc + 로그로 되살린다
```

이렇게 하면 **협업맵을 단독으로 열어도 그냥 열린다.** 내보내기도 그대로
돈다. 유료 모듈을 떼어낸 서버에서도 **문서가 남는다** — 이건 사용자 데이터
문제라 양보하지 않는다.

> **업데이트 로그는 무한히 쌓이지 않는다.** 물질화한 시점에 그 이전 로그를
> 접는다(compaction). 접지 않으면 오래된 맵일수록 여는 데 오래 걸린다.

---

## 7. 결정 ⑥ — **단독 편집 잠금은 협업맵에서 끈다**

§1 ③ 의 장애물이다. `map_edit_locks` 는 지금 **모든 맵**에 걸린다.

```
maps.kind = 'collab'  →  편집 잠금을 잡지 않는다 (여러 세션이 정상)
maps.kind = 'solo'    →  지금 그대로 (다른 세션에서 열면 읽기 전용)
```

**이것도 공개 코어 작업이다.** 잠금은 코어 기능이고, 코어가 `kind` 를 보고
비켜 주는 것이 맞다. 유료 모듈이 코어의 잠금을 우회하게 만들면, **모듈이
없을 때 협업맵이 잠기지 않는 채로 남는다.**

> 대신 협업맵에는 **Soft Lock**(노드 단위·TTL 5초)이 있다. 이건 막는 잠금이
> 아니라 **"○○○ 편집 중" 표시**이고, awareness 로 흐르므로 DB 도 Redis 도
> 필요 없다.

---

## 8. 되돌리기(Undo) — 조용히 남의 것을 되돌리지 않는다

지금 되돌리기는 **클라이언트 히스토리 99단계**다. 협업에서 그대로 두면
**Ctrl+Z 가 남이 방금 한 일을 되돌린다.**

Yjs 의 `UndoManager` 를 **자기 origin 으로 한정**해 쓴다 — 내가 한 것만
되돌린다. 이건 협업맵에서만 다르게 도는 부분이므로 **유료 모듈이 가져간다.**

> 되돌릴 것이 없을 때 남의 것으로 넘어가면 안 된다. 그럴 땐 **아무 일도
> 일어나지 않는 것이 맞다.**

## 9. 경계 — 무엇이 공개이고 무엇이 유료인가

| | 어디 | 왜 |
|---|---|---|
| **이미지를 문서 밖으로**(§3.1) | **공개 코어** | 단독 사용자에게도 이득. 협업이 없어도 해야 한다 |
| **`kind='collab'` 이면 편집 잠금 비켜 주기**(§7) | **공개 코어** | 잠금은 코어 기능. 모듈이 우회하면 모듈이 없을 때 잠긴 채 남는다 |
| **순환 판정 함수**(§4 ①) | **공개 코어** | 규칙을 두 벌로 만들지 않는다 |
| 이 설계 문서 | **공개 코어** | 로드맵이 보이는 편이 신뢰에 낫다 |
| Y.Doc 매핑 · 업데이트 로그 · 물질화 | **유료** | |
| WebSocket 게이트웨이 · awareness | **유료** | |
| Soft Lock 표시 · 협업 UI · origin 한정 Undo | **유료** | |
| 협업 전용 DB 표 (`collab_*`) | **유료** (자기 델타 SQL) | 코어 헬스체크에 넣지 않는다 |

**EMM 파일 포맷은 공개다.** 협업이 문서에 필드를 더한다면(예: 노드 작성자)
**그 필드의 정의와 직렬화는 `packages/emm-parser` 에 공개로** 들어간다.
포맷이 갈리면 공개판으로 저장한 파일을 유료판이 못 읽는다 — **사용자가
잃는 것은 우리 수익이 아니라 자기 문서다.**

## 10. 순서 — 무엇부터 하나

**공개 코어 쪽이 먼저다.** 아래 둘이 안 되어 있으면 협업은 첫날 막힌다.

1. **`kind='collab'` 이면 편집 잠금을 비켜 준다** — 작다. 이것 없이는
   둘째 사람이 읽기 전용이다
2. **이미지를 문서 밖으로** — 크다. 역호환(옛 문서는 그대로 읽히고 다음
   저장에서 올라간다)이 핵심이고, **일괄 마이그레이션은 하지 않는다**
3. 순환 판정 함수를 코어에서 꺼내 쓸 수 있게 정리

**그 다음이 유료 모듈** — Y.Doc 매핑 → 게이트웨이 → 물질화 → awareness →
Soft Lock 표시 → UI.

> 1·2·3 은 **협업이 없어도 값어치가 있다**. 그래서 협업을 안 하기로 해도
> 버리는 일이 되지 않는다. 순서를 이렇게 잡은 이유가 그것이다.

## 11. 하지 않기로 한 것

| | 왜 |
|---|---|
| **서버 사이드 OT** | CRDT 로 충분하고, OT 는 서버가 모든 히스토리를 들고 순서를 잡아야 한다 |
| **Redis pub/sub 을 지금 넣기** | 인스턴스가 하나면 필요 없다. 없어도 되는 부품을 먼저 넣으면 그것이 죽었을 때의 장애를 공짜로 얻는다 |
| **문서 전체를 CRDT 로** | 이미지 바이트가 업데이트 로그에 영원히 남는다 |
| **협업맵 전용 저장 형식** | 내보내기·히스토리·문서함이 두 벌이 된다 |
| **옛 문서 일괄 마이그레이션** | 되돌릴 수 없는 데이터 작업이다. 다음 저장에서 자연히 옮겨진다 |

## 12. 아직 정하지 않은 것 — 정직하게

- **오프라인 편집을 어디까지 허용할 것인가.** Yjs 는 오래 끊겼다 돌아와도
  합치지만, **한 달 전 상태로 돌아온 사람**의 편집을 그대로 합치는 게 옳은지는
  제품 판단이다. 지금은 정하지 않는다.
- **접속자 20명 상한이 맞는 수인가.** 근거 없이 정해진 수다. 실제로 재 본 적이
  없다 — 재고 나서 고친다.
- **노드 작성자를 문서에 남길 것인가.** 남기면 EMM 포맷이 바뀌고(공개 PR),
  안 남기면 "누가 썼나"를 협업 세션 안에서만 알 수 있다.

  것이지 벤치마크 결과가 아니다. 노드 1만 개짜리 맵에서 Yjs 가 어떤지는
  **구현 전에 재 봐야 한다.**
