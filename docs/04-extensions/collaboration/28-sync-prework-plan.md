## 2. 항목 3 — 순환 판정: 지금 규칙이 **세 벌**이다

### 2.1 현황

`27-sync-model.md` §4 가 "규칙을 두 벌로 만들지 않는다"고 적었는데,
`tree-rules.ts` 를 만들면서 **오히려 한 벌이 늘었다.**

| | 위치 | 방식 | 호출부 |
|---|---|---|---|
| ① | `documentStore.ts:405 isSelfOrDescendant` | 중첩 `children` 재귀 | **925 · 962** — 실제로 도는 것 |
| ② | `move_node_subtree.sql` | ltree `new_base_path <@ old_path` | `NodeService.moveNodeSubtree()` |
| ③ | `tree-rules.ts wouldCreateCycle` | `parentOf` 사슬 | **없다** |

`findOrphans` 도 호출부가 없고, §4 ② 가 정한 **"부모 잃은 노드는 지우지
말고 뿌리로 올린다"** 는 코드 어디에도 없다.

> 함수를 만든 것으로 이 항목이 끝났다고 보면 안 된다. **쓰이지 않는 규칙은
> 규칙이 아니다.** 지금은 ③ 이 옳고 ① 이 도는 상태라, 협업 모듈이 ③ 을
> 부르기 시작하면 **화면과 협업이 서로 다른 판정을 하게 된다.**

### 2.2 단순 치환이 안 되는 이유 셋

**① 모델이 다르다.** `documentStore` 는 중첩 `children` 트리를 들고 있고
`wouldCreateCycle` 은 `parentOf` 콜백을 받는다. 어댑터가 필요하다.

**② 깊이 가드가 딸려 있다.** `documentStore.ts:962` 부근은 순환만 보는 것이
아니라 `MAX_DEPTH = 50` 도 함께 본다(970 · 988). 순환만 갈아끼우면
**깊이 제한이 조용히 빠진다** — 화면이 안 깨지므로 알아채기 어렵다.

**③ 비용.** `findParentId()` 는 부를 때마다 트리를 통째로 훑는다(O(n)).
그대로 `parentOf` 로 넘기면 이동 한 번이 O(n²) 가 된다. 1만 노드에서
드래그가 눈에 띄게 멈춘다.
→ **이동 직전에 `Map<id, parentId>` 인덱스를 한 번 만들어** 넘긴다.

### 2.3 할 일

```
A-1  documentStore 에 buildParentIndex(map): Map<string,string|null> 추가
A-2  moveNodeRelative(962) · 925 의 isSelfOrDescendant 를
     wouldCreateCycle(idx.get, nodeId, targetId) 로 교체
     — MAX_DEPTH 검사는 **그대로 둔다** (순환과 별개 규칙이다)
A-3  isSelfOrDescendant 를 지운다. 남겨 두면 다음 사람이 그걸 부른다
A-4  move_node_subtree.sql 의 ltree 판정은 **그대로 둔다**
     — DB 는 마지막 방벽이다. 앱이 틀려도 DB 가 막아야 한다.
       주석에 "판정 원본은 packages/emm-parser/src/tree-rules.ts" 를 적는다
A-5  packages/emm-parser 에 buildTreeFromFlat() 를 만든다
     평평한 { id, parentId, order } 목록 → 중첩 MindNode 트리.
     뿌리에 닿지 못하는 노드는 findOrphans 로 찾아 **뿌리로 올린다**(지우지 않는다).
     유료 물질화(§6)가 이 함수를 부른다 — 규칙을 두 벌로 만들지 않기 위함이다.

  ※ documentStore 는 중첩 children 모델이라 고아가 구조적으로 생기지 않는다.
     repairOrphans 를 거기 두지 않는다
```

> **A-5 가 왜 여기인가** (2026-08-20 정정): 처음에는 `documentStore` 에
> `repairOrphans` 를 두려 했다. 그런데 **거기는 중첩 `children` 모델이라
> 고아가 구조적으로 생기지 않는다** — 부모가 없는 노드를 표현할 방법 자체가
> 없다.
>
> 고아는 **평평한 것을 중첩으로 다시 짜는 그 지점**에서 생긴다. 협업 CRDT 는
> `{ id, parentId, order }` 로 평평하게 들고 있고(§3), 정본은 중첩 트리다(§6).
> A 가 부모를 지우고 B 가 그 밑에 자식을 더한 상태를 중첩으로 짜려 하면
> **그 자식이 갈 곳이 없다.**
>
> 물질화 구현은 유료 모듈이지만 **트리 모양 규칙은 공개 코어에 한 벌만
> 둔다**(§9). 그래서 이 함수가 그 경계다.

### 2.4 되돌려 깨뜨리기 (테스트가 잡아야 할 것)

- `wouldCreateCycle` 로 바꾸면서 **MAX_DEPTH 검사를 같이 지우면** 50단계
  넘는 이동이 통과한다 → 레이아웃이 화면 밖으로 나간다
- **인덱스를 이동 후에 만들면** 이미 옮긴 트리를 보고 판정한다 → 순환을 못 막는다
- `parentOf` 가 모르는 노드에 `null` 을 돌려주면(`undefined` 가 아니라)
  `wouldCreateCycle` 이 "뿌리에 닿았다"로 오판한다 → **둘을 구분해서 돌려준다**

**D-5·D-6 완료 (2026-08-20, e2e174) — 구현에서 정한 것**

- **메타 주석이 본문과 같은 `files/` 경로를 가리킨다** (D-5). 예전에는
  본문을 `![](files/img-1.png)` 로 내보내면서 메타 주석에 같은 사진을
  base64 로 한 번 더 넣었다 — `.md` 한 장이 사진 바이트를 **두 벌** 들고
  다녔다. `withPackagedImagePaths()`(serialize.ts) 한 함수로 맞췄고,
  **레퍼런스 직렬화(`serializeEmm`)와 앱 내보내기가 같은 함수를 쓴다** —
  포맷 정의가 두 벌이 되지 않게. 겸사겸사 **같은 사진을 여러 노드가 써도
  `files/` 에 한 벌만** 담기게 고쳤다(예전엔 노드마다 한 벌).
  · 형식 문서: `import-export/22-map-file-meta.md` §3.3 · `emm-spec.md` §4.1
  · **눈으로는 확인할 수 없다**: 메타 주석 자체가 base64 라, 안에 든 data
    URL 은 `.md` 를 텍스트로 열어도 `base64` 라는 글자로 보이지 않는다.
    **디코드해서** 봐야 한다(§3.6 참조).
- **불러오기도 같은 문으로** (D-6). `relinkImages()` 가 ZIP 의
  `files/*.png` 를 `File` 로 감싸 `attachmentUrlForFile()` 에 넘긴다.
  여러 장이면 진행률 한 줄(`uploadStore`), **한 장이 실패하면 그 장만
  data URL** 로 남기고 불러오기를 계속한다.
- **뒷문이 하나 더 있었다.** `utils/remoteImages.ts`(불러온 맵의 원격 사진
  내장)도 우리 저장소 사진을 `http` 로 보고 **되받아 data URL 로 문서에
  도로 넣고 있었다.** `serverAttachmentId()` 로 걸러 건너뛰게 했다 —
  이게 없으면 **내보냈다 다시 여는 것만으로 원상복귀**된다.
- **작은 스크린샷 문제를 닫았다** (아래 D-1~D-4 메모의 미결 항목).
  `attachmentUrlForFile` 에 **`preferServer` 옵션**을 더했다 — 부르는 쪽은
  "이건 사진"이라고만 말하고, 로그인 여부·쿼터·청크 경로는 **여전히 그
  함수 한 곳**이 정한다. 판정을 두 벌로 만들지 않으면서 첨부 규칙은 그대로
  둘 수 있었다(첨부 ≤2MB 내장 · >2MB 서버 — 회귀 시험으로 확인).
  이렇게 하지 않으면 **스크린샷 대부분(2MB 미만)이 붙이는 순간 문서에
  들어가** "문서에 사진 바이트를 넣지 않는다"가 성립하지 않는다.
- **성공 경로가 조용히 전부 실패하고 있었다** (D-1 의 버그, 함께 고침).
  `remote-image.ts` 의 `pinnedLookup` 이 Node 의 규약을 어겼다 — `net` 은
  `lookup` 을 `{ all: true }` 로 부르고 **배열**을 기대하는데 문자열 하나를
  돌려주어, 모든 다운로드가 `Invalid IP address: undefined` 로 죽었다.
  **차단 시험으로는 절대 안 걸린다** — 막는 길은 연결 전에 끝나기 때문이다.
  CI 스모크에 "연결까지 가는가" 한 줄을 박아 두었다.

**D-1~D-4 완료 (2026-08-20) — 구현에서 정한 것**

- **판정을 새로 만들지 않았다.** 클립보드 사진 파일은 첨부와 **같은 문**
  (`attachmentUrlForFile()`)을 지난다. 그래서 **작은 스크린샷(개당 2MB
  이하이고 맵 내장 합계 10MB 미만)은 붙이는 순간에는 여전히 data URL** 이다
  — 그 문이 그렇게 정해 놓았기 때문이고, 사진용 기준을 따로 만들면 두 벌이
  된다. 문서에서 빠지는 것은 저장 때 서버가 한다
  (`maps/doc-images.ts`, 8KB 이상). 붙이는 그 자리에서 바로 빼려면 **그
  문의 기준을 고쳐야 하고 그건 첨부까지 함께 바뀌는 결정**이다 (§5).
- **사진은 `blob:` 을 받지 않는다.** 그 문은 서버를 못 쓰는 큰 파일에 blob
  URL 을 주는데, 첨부에는 맞아도 사진에는 안 된다 — 새로고침하면 그 자리가
  통째로 깨지고 내보낸 파일에도 안 담긴다. 이 자리에서만 받지 않고 data
  URL 로 되돌린다(문의 기준을 고치는 것이 아니다).
- **실패를 알린다.** 붙여넣기는 네 화면(캔버스·노드 편집창·아웃라인·칸반)
  에서 시작되므로 안내를 각자 만들면 하나는 빠진다. `stores/noticeStore.ts`
  에 상태만 두고 EditorPage 한 곳에서 그린다(첨부 진행률과 같은 이유).

**D-5·D-6 을 하지 않은 이유 (2026-08-20)**

둘은 §3.4 가 2026-08-20 에 다시 쓰이면서 추가됐고, 이번 작업의 지시
범위(D-1~D-4)에 없었다. 특히 **D-5 는 그대로 하면 사진이 조용히 사라진다**:

> 메타 주석은 지금 사진을 data URL 로 들고 있고, **ZIP 불러오기의
> `relinkAttachments()` 는 첨부(`attachments[]`)만 되살린다 — 사진은
> 되살리지 않는다.** 메타 주석에서 사진 data URL 만 빼면, 내보낸 파일을
> 다시 불러올 때 **사진이 통째로 없어진다.** D-5 는 "`files/` 의 사진을
> 다시 잇는 길"과 **함께** 가야 한다(그게 사실상 D-6 이다).

그래서 둘을 한 덩어리로, 되돌려 깨뜨리기(내보내기 → 다시 불러오기 왕복)를
갖춘 다음 작업으로 남긴다.

### 3.5 base64 가 남는 곳 — 의도된 예외 (2026-08-20 결정)

"지식 저장소에 base64 를 두지 않는다"가 규칙이다. 다음 둘은 지식
저장소가 아니라 **배달 형식**과 **임시 상태**이므로 예외로 둔다.

| 곳 | 왜 예외인가 |
|---|---|
| `export/exportHtml.ts` | 단일 파일 HTML. 빼면 `.html` + `_files/` 폴더가 되어 "파일 하나로 온전히"가 깨진다 (content-permanence.md §7.1) |
| 게스트(비로그인) 경로 | 서버가 없다. 이 문서는 서버·vault·CRDT 어디에도 닿지 않고 브라우저 안에서만 산다 |
| **리치 노트 HTML 속 `<img>`** (2026-08-20 추가) | 슬라이스 1 의 되돌리기(`export/serverImages.ts`)와 2 의 토큰 붙이기(`utils/imageSrc.ts`)가 **`image`·`images` 만 훑는다.** 노트 HTML 에 서버 주소를 넣으면 **내보낸 파일이 서버 없이 안 열린다** — 위 첫 줄과 같은 이유다. 서버는 **받아오는 일만** 대신하고(`from-url` 의 `store: false`) 결과는 data URL 로 둔다: CORS 는 넘고 자기완결성은 지킨다 |

> ★ **셋째 줄은 "의도된 예외"가 아니라 "아직 못 옮긴 곳"이다.** 위 둘과
> 달리 언젠가는 없앨 수 있다 — 되돌리기·토큰 붙이기를 노트 HTML 까지
> 넓히면 된다(다음 슬라이스). 그 전에는 넣으면 안 된다.

> **일관성을 이유로 이 둘을 고치지 마라.** 형식마다 관습이 다른 것은
> 불일치가 아니다. `.md` 가 외부 파일을 참조하는 것과 단일 HTML 이
> 인라인하는 것은 같은 층위의 관습이다.

### 3.6 되돌려 깨뜨리기

- D-6 을 빠뜨리면 D-2·D-3 으로 앞문을 잠가도 **ZIP 불러오기라는 뒷문으로
  base64 가 계속 들어온다**
- exportHtml 을 "일관성" 이라며 고치면 파일이 폴더가 된다.
  **회귀 테스트에 안 걸린다** — 파일은 정상 생성되고, 사진이 안 보이는 것은
  사람이 열어 봐야 안다
- 게스트 경로를 막으면 로그인 없이 사진을 못 붙인다 → 첫 사용 경험이 깨진다
- **노트 HTML 에 서버 주소를 넣으면** 내보낸 파일에서 그 사진만 조용히
  깨진다 — `serverImages.ts` 가 노트 HTML 을 훑지 않기 때문이다.
  **회귀 테스트에 안 걸린다**(파일은 정상 생성된다). e2e173 이 이걸 본다
- **업로드 실패를 삼키면** 노드에 빈 사진 자리가 남는다. 실패하면 data URL
  로 남기고 **그렇게 했다고 알린다**(e2e173 ⑮가 이걸 본다)
- ★ **`.md` 를 눈으로 보고 "base64 없음" 이라 판정하면 안 된다.**
  메타 주석 **자체가 base64** 라서, 그 안에 사진 data URL 이 통째로 들어
  있어도 파일에는 `base64` 라는 글자가 **보이지 않는다.** D-5 를 되돌려도
  텍스트 검사는 그대로 통과한다 — **디코드해서** 사진 `src` 를 봐야 한다
  (e2e174 가 그렇게 본다)
- ★ **막는 쪽만 시험하면 받는 쪽이 죽은 것을 못 본다.** SSRF 차단은 연결
  **전에** 끝나므로, 연결 자체가 고장 나도(예: DNS 해석기가 Node 의
  `lookup` 규약을 어겨 `Invalid IP address`) 차단 시험은 전부 통과한다.
  실제로 D-1 병합 뒤 **모든 다운로드가 조용히 실패하고 있었다.** 스모크에
  "연결까지 가는가" 를 함께 둔다
- **`remoteImages.ts` 를 잊으면** 앞문·뒷문을 다 잠가도 소용이 없다.
  우리 저장소 사진도 `http` 라서, 거르지 않으면 불러올 때마다 되받아
  **data URL 로 문서에 도로 넣는다**
