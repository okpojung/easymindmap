## 0. 이 문서의 위상

EasyMindMap은 단순한 마인드맵 작성 도구가 아니라, **마인드맵을 위한
Markdown 포맷(mmd)을 정의·표준화하고 이를 편집·렌더링하는 레퍼런스
구현**을 지향한다. 이 문서는 그 포맷의 정식 명세다.

- `markdown-export.md`는 이 스펙의 **구현 규칙 상세**(변환 표 단위)이며,
  구현이 바뀔 때마다 갱신되는 살아있는 문서다.
- 본 스펙은 포맷의 **설계 원칙·문법·적합성 기준·버전 정책**을 정의하는
  상위 문서다. 두 문서가 충돌하면 본 스펙 개정을 통해 해소한다.

## 1. 배경과 목표

### 1.1 시장 공백

마인드맵을 표현하는 텍스트 포맷의 사실상 표준은 아직 없다.

| 항목 | Mermaid (mindmap) | Markmap | FreeMind/Freeplane | **mmd** |
|---|---|---|---|---|
| 기반 | MD 코드블록 | MD 헤딩 | XML | **CommonMark/GFM 본문 + `emm` 선언 블록** |
| 구조 | 트리 | 트리 | 트리 | 트리 (+확장 예정: 크로스 엣지) |
| 노드 콘텐츠(노트·표·코드) | 제한 | 없음 | 있음 | ✅ 문단·표·코드·체크리스트 노트 |
| 레이아웃 | ❌ | ❌ | 제한 | ✅ 방사형·트리·계층·진행트리·타임라인 + 레벨/서브트리 오버라이드 |
| 스타일(도형·색·폰트) | 제한 | ❌ | 있음 | ✅ 레벨 정책 + 노드 오버라이드 |
| 사진(위치 보존) | ❌ | ❌ | 제한 | ✅ `files/` 동봉 + 텍스트 중간 위치 |
| 일반 MD 뷰어에서 가독 | 코드블록으로 보임 | ✅ | ❌ | ✅ **본문이 순수 GFM** |
| 무손실 왕복(라운드트립) | ❌ | ❌ | 자체 포맷 내 | 구조·내용·레이아웃 정책은 MD 로, 노드별 스타일까지는 **HTML 내보내기**로 |
| AI 생성 친화성 | 중간 | 높음 | 낮음 | 높음 (본문 = 일반 MD) |

### 1.2 목표

1. **사람이 읽을 수 있어야 한다** — mmd 파일은 어떤 Markdown
   뷰어(GitHub·Obsidian·Notion·VS Code)에서도 정상적인 문서로 보인다.
2. **CommonMark/GFM과 충돌하지 않는다** — 본문에 새 문법을 발명하지
   않는다. 맵 정책은 코드블록(`emm` 선언)에, 노드별 충실도는 HTML 내보내기에 둔다.
3. **구조와 스타일을 분리한다** — 헤딩은 글자 크기가 아니라 **노드
   레벨**이다. 시각 표현은 맵 정책(레벨 규칙)과 노드 오버라이드가
   담당한다.
4. **무손실 왕복** — 맵 → MD → 맵을 반복해도 구조·노트·스타일·레이아웃·
   설정·사진 위치가 보존된다.
5. **AI 입출력 친화** — LLM이 일반 Markdown만 생성해도 유효한 mmd
   문서다 (메타데이터는 선택 사항).
6. **도구 독립(tool-independent)** — 본 스펙과 적합성 코퍼스만으로
   제3자 파서/렌더러를 구현할 수 있어야 한다.

### 1.3 비목표 (v1.0)

- 좌표 픽셀 단위의 완전한 시각 재현 규격화 (레이아웃은 엔진 재계산)
- 협업 상태·권한·감사 로그의 파일 내 표현
- 본문 내 커스텀 지시자 문법(`:::`, `@key:` 등) — v1.0은 도입하지 않음

## 2. 설계 원칙 (Normative)

### 2.1 2계층 구조 — "본문은 순수 GFM, 맵 정책은 `emm` 선언으로" (2026-09-15 개정)

mmd 문서는 두 계층으로 구성된다.

```
┌─────────────────────────────────────────────┐
│  ① 본문 (Content Layer)                      │
│     100% CommonMark/GFM — 새 문법 없음        │
│     구조(헤딩·리스트)·노트(인용·표·펜스)·      │
│     링크·사진·첨부(📎)·인라인 강조             │
├─────────────────────────────────────────────┤
│  ② 맵 선언 (Declaration Layer) — 선택         │
│     첫 헤딩 바로 아래 ```emm 코드블록 (§3.7):  │
│     맵 ID · 템플릿 또는 레벨별 레이아웃·도형·  │
│     글자 크기 — 사람이 읽고 고친다             │
└─────────────────────────────────────────────┘
```

이 구조의 결과:

- 선언이 없어도 **유효한 mmd 문서**다 (구조·콘텐츠는 본문만으로 복원).
  손으로 쓴 일반 MD, AI가 생성한 MD가 즉시 mmd가 된다.
- 선언이 있으면 맵의 **레이아웃 정책**이 함께 돌아온다.
- **노드별 충실도(스타일·아이콘·태그·접힘·수동 크기 등)는 MD 가 담지
  않는다.** 그것은 HTML 내보내기(`#easymindmap-map` JSON)와 서버 저장이
  맡는다 — mmd 는 **내용 교환 형식**이고, 자체 무손실 형식은 HTML 이다.

> 역사적 참고: 2026-09-15 까지는 파일 끝 HTML 주석
> `<!-- easymindmap:v1:BASE64(JSON) -->` 에 맵 전체 스냅숏을 실어 MD 만으로
> 무손실 왕복을 보장했다(구 §4 메타데이터 계층). 노드 수에 비례해 본문의
> 2~3배로 커지고, 사람이 읽을 수 없으며, diff 가 무의미하고, 본문과 짝짓는
> 텍스트 매칭이 취약해 **폐기했다** (공개 전이라 옛 파일은 읽지 않는다).
> 그 이전의 "simple/full 이원 export" 도 같은 이유로 이미 폐기됐다.

### 2.2 헤딩 = 레벨 (스타일 아님)

- `#`~`######`은 노드의 **깊이**만 의미한다.
- 렌더러는 헤딩 레벨에 따른 글자 크기·굵기를 적용하지 **않는다**.
  글자 크기는 맵의 레벨 폰트 정책 → 서브트리/노드 오버라이드 순으로
  결정된다.
- 같은 레벨의 노드는 같은 기본 스타일을 가진다.

### 2.3 정책(policy)과 오버라이드(override)의 분리

- 레벨별 레이아웃·폰트·도형 등 "규칙"은 **맵 단위 정책**이며 메타데이터
  계층에 저장한다.
- 노드에는 정책과 **다른 값만**(오버라이드) 저장한다. 본문에 반복 기술을
  금지해 파일 비대화와 diff 오염을 막는다.

### 2.4 관용적 파싱 (Postel's law)

- 파서는 가능한 한 중단하지 않고 복구한다.
- 알 수 없는 메타데이터 필드는 무시한다 (전방 호환).
- 손상된 메타데이터는 버리고 본문만으로 구조를 복원한다.

## 3. 문서 구조 문법 (Content Layer — Normative)

이 장의 규칙은 레퍼런스 구현과 E2E 적합성 코퍼스로 검증된 **현행
규격**이다. 변환 표 단위의 세부 규칙과 예시는 `markdown-export.md`
§1~§2가 규범이다. 여기서는 규격의 뼈대를 요약한다.

### 3.1 노드 계층

| 본문 | 맵 |
|---|---|
| 파일의 첫 `#` | 루트(중심 주제) + 맵 제목 |
| 제목 이후 본문의 `#` | **새 중심주제** (2026-09-15 — 아래 "여러 중심주제"). 예전의 h1Mode(본문 `#`를 2레벨로 내림)는 폐기 |
| `##`~`######` | 2~6레벨 노드 |
| 불릿 리스트(`-`/`*`/`+`, 들여쓰기 2칸=1단계) | 마지막 견출(또는 절)의 하위 노드 |
| 순번 리스트(`1.`/`1)`) | 하위 노드 — 번호를 텍스트에 유지 |
| 들여쓰기 없는 순번 항목 | **절 머리** — 다음 순번/견출 전까지의 문단·펜스가 그 절의 자식 |
| 7레벨 이상 | 리스트 들여쓰기로 표현 |

부모 결정: 현재 항목보다 얕은 가장 가까운 이전 노드가 부모다.
루트 없는 문서는 가상 루트를 생성한다.

**여러 중심주제 (2026-09-15, mmd 표준 세션 결정).** 표준 트리의 뿌리는
이름도 글자도 없는 **보이지 않는 노드**다. `#` 제목이 둘인 문서는 뿌리
아래 형제가 둘인 트리이고, 트리를 어떻게 그릴지는 표준이 정하지 않으므로
뿌리는 그리지 않고 **뿌리의 자식을 각각 중심주제로** 그린다 — 한 장의
맵에 중심이 여럿이다(ThinkWise 의 플로팅 노드와 같은 모양).

| 문서 | 맵 화면 | 내보내기 |
|---|---|---|
| `# 중심주제1`(하위 1~3) … `# 중심주제2`(하위 4~6) | 중심주제 2개 | `# 중심주제1 … # 중심주제2 …` 그대로 |
| `#` 하나뿐인 문서 | 중심주제 1개 (예전과 같음) | 그대로 |

- 두 번째 `#` 아래의 `##`·문단·리스트는 그 중심의 가지이고, 첫 `##` 전의
  문단·인용문은 그 중심의 머리말(루트 노트)이다 — 첫 중심과 같은 규칙.
- `##` 로 시작한 문서 뒤에 `#` 가 오면 그것도 새 중심이다 (첫 중심은
  파일 이름을 제목으로 가진다).
- 빈 `#` 는 이름 없는 중심주제다. 내보낼 때도 `#` 만 쓴다.
- md 에는 좌표가 없고 **순서만** 있다. 중심의 순서는 `#` 순서이며, 화면에서
  옮겨도 바뀌지 않는다. 옮긴 자리는 앱 저장본·HTML 내보내기의 모델
  (`SampleCenter.pos`)에만 남는다.
- 모델: `SampleMap.root`/`branches` 가 첫 중심, 두 번째 이후는
  `SampleMap.centers[]` (`{ root, branches, pos? }`). 예전 데이터(중심
  하나)는 그대로 읽힌다. 전체 순회는 `mapCenters(map)`.
- 아직 남은 것: A-1 ② 의 나머지 — 견출 없이 `- 가`, `- 나` 만 있는 문서의
  최상위 항목을 각각 중심으로 보는 것은 **"하나의 중심주제로 묶기"** 편집
  동작과 함께 넣는다(그 전에는 지금처럼 파일 이름 중심 하나). 중심의
  추가·삭제·드래그 이동, 아웃라인·검색·HTML 뷰어·MCP 의 둘째 중심 이후
  지원도 다음 단계다. **빈 견출(`##` · `## #`)은 이름 없는
노드가 된다** (2026-09-15 — 앱이 글자를 모두 지운 노드를 저장하므로 왕복에서
그 노드와 하위 구조가 보존되어야 한다. 내보낼 때는 공백 없는 `##` 로 쓴다).

### 3.2 노드 콘텐츠 수집

- 견출/절 머리 뒤의 일반 문단(연속 줄)은 한 노드로 합쳐 그 하위가 된다.
- 문단 바로 뒤의 불릿은 그 문단 노드의 자식이 된다.
- 리스트 항목의 들여쓴 연속 줄은 항목 노드의 추가 줄로 병합된다.
- 첫 견출 전의 문단·표·인용문은 **루트의 노트**가 된다(머리말).

### 3.3 노트 (구조화 블록)

| 본문 | 맵 |
|---|---|
| `>` 인용문 | 현재 노드의 **문단 노트** |
| ``` 코드 펜스 ``` (언어 표기 유지) | 현재 노드의 **코드 노트** |
| 파이프 표 | 직전 노드의 **표 노트** (구분선 제거, `셀 | 셀` 줄 형식) |

노트는 노드 "본문"이 아니라 노드에 첨부된 구조화 블록이며, 렌더러는
인디케이터(T/C/⊞/✓)와 뷰어 팝업으로 표시한다.

> **블록 배치(blockPlacement) 기본값**: 파서 API 기본은 `'note'`
> (하위 호환)지만, **앱의 불러오기 UI 와 AI 생성 경로 기본은
> `'node'`**(블록=노드 본문)다 — `rich-node-content.md` §2.2 참조.

### 3.4 링크·사진

| 본문 | 맵 |
|---|---|
| `[라벨](url)` (노드 텍스트 내) | 텍스트에는 라벨만, URL은 노드 링크(🔗)로 첨부 |
| `🔗 [라벨](url)` (export 형식) | 노드 링크 |
| `![대체](files/img-N.ext)` | 노드 사진 — export 시 사진 바이트는 `files/`로 ZIP 패키징(**같은 사진은 한 벌만**), 텍스트 중간 위치(afterLine)는 메타데이터가 보존. 메타데이터도 **같은 `files/` 경로**를 가리킨다 |
| `![대체](https://…)` · `![대체](data:image/…;base64,…)` | 노드 사진 — 원격 URL 은 앱이 불러올 때 내려받아 보관, **내장 data URL 은 그대로 사진**(2026-09-06 — AI(MCP)가 파일 바이트를 직접 실을 때. 크기는 API 가 파일 머리에서 읽고 폭 640 상한). 사진뿐인 문단은 `node` 배치에서 자식 노드가 된다(대체 텍스트가 이름) |
| 노트(인용문) 안 링크 | 원문 유지 — 뷰어가 앵커로 렌더링 |

### 3.5 인라인 강조

`**굵게**` `*기울임*` `~~취소선~~` `__밑줄__` `==하이라이트==`
`` `코드` ``는 노드 텍스트에 원문 그대로 저장되고, 렌더러가 마커 문자를
숨기고 서식으로 표시한다. 인라인 코드는 모노스페이스 + 회색 배경 띠
(#ECEFF3, 테마 무관 고정 — markmap 호환, 2026-07). 백슬래시
이스케이프(`1\.`, `\-`)는 해제한다.

**표준 출처·호환성 (Informative)** — mmd 는 GFM 의 상위집합이다:

| 마커 | 출처 | 타 앱에서 열었을 때 |
|---|---|---|
| `**` `*` `` ` `` (+링크·이미지) | CommonMark | 동일 표시 |
| `~~` · `- [x]` · 표 | GFM 확장 | GFM 지원 앱에서 동일 표시 |
| `==하이라이트==` | **mmd 확장** (Obsidian·Typora·markmap 관행) | 해당 앱=하이라이트, GitHub=마커 문자 노출 |
| `__밑줄__` | **mmd 확장 — CommonMark 재해석** | 표준에서 `__`는 굵게(strong)라 **굵게로 표시**됨 |

> MD 표준에 밑줄 문법이 없어(`<u>`가 링크와 혼동된다는 이유로 의도적
> 제외) mmd 는 `__` 를 밑줄로 재해석한다. 어떤 경우에도 **내용은 유실
> 되지 않으며** 강조 해석만 달라진다. mmd↔mmd 왕복은 완전 보존.

### 3.6 체크리스트 (2026-07)

`- [x] 항목` / `- [ ] 항목` 줄은 자식 노드가 아니라 **현재 노드의
체크리스트 노트**로 파싱한다(markmap 호환). 대문자 `[X]`도 체크로
인정. export 시 체크리스트 노트는 같은 형식으로 직렬화되어 완전
왕복된다. (일반 불릿 `- 항목`은 기존대로 자식 노드.)

### 3.7 맵 선언 — `emm` 코드블록 (2026-08)

문서가 **스스로 어떤 맵인지 밝히는** 블록이다. 정보 문자열이 `emm` 인 펜스
코드블록이며, 첫 헤딩 바로 뒤에 둔다.

````markdown
# 배포 절차

```emm
map: 7f3a9c
template: tree-progtree
levels:
  2:
    shape: rounded
    font: 15
```

## 준비
````

#### 왜 front matter 가 아니라 코드블록인가

**front matter 는 CommonMark 가 아니다.** 표준 파서는 닫는 `---` 를 문단 뒤의
**setext 헤딩 밑줄**로 읽어 문서 맨 앞에 **가짜 노드**를 만든다. 그것을 표준
쪽에서 어떻게 다룰지는 아직 열린 질문이다
([spec#17](https://github.com/mindmapmarkdown/spec/issues/17),
[RFC 0022](https://github.com/mindmapmarkdown/spec/blob/main/rfcs/0022-front-matter-root-content.md)).

**펜스 코드블록은 진짜 CommonMark 다.** 표준의 L-1(헤딩과 리스트 항목만 노드가
된다)과 L-3(나머지 블록은 노드 내용)에 그대로 들어맞으므로:

| | front matter | **`emm` 코드블록** |
|---|---|---|
| CommonMark 인가 | **아니다** | **맞다** |
| lift 결과 | **가짜 `section` 노드** | 그 노드의 **내용** |
| 표준 변경이 필요한가 | RFC 필요 | **필요 없다** |
| 왕복 보존 | 미정 | **표준이 이미 보장** (E-5·P-9) |

**표준이 이 선언을 알 필요가 없다.** §1.1.2 가 레이아웃·스타일을 규정하지
않는다고 못 박았고, 코드블록에 담긴 앱 설정은 표준 눈에는 그냥 노드 내용이다.

#### 선언이 담는 것과 담지 않는 것

| 담는다 | 담지 않는다 |
|---|---|
| `map:` 서버 맵 ID · `template:` 또는 `levels:`(레벨별 `layout` · `shape` · `font`) | 노드별 스타일·아이콘·태그·접힘·수동 크기·좌표 — HTML 내보내기·서버 몫 |

**내보내기도 이 블록을 쓴다** (2026-09-15). 앱이 맵 설정에서 `levels:` 를
만들어 첫 헤딩 아래에 쓰고, 불러올 때는 같은 키를 읽는다. 블록은 중심
노드의 `emm` 코드 노트로 **보이며**, 다시 내보낼 때는 그 노트를 건너뛰고
맵 설정에서 새로 쓴다 — 같은 정보를 두 곳에 두지 않는다.

## 4. 메타데이터 계층 — 폐기 (2026-09-15)

파일 끝 HTML 주석 `<!-- easymindmap:v1:BASE64(JSON) -->` 에 맵 전체
스냅숏을 싣던 계층은 **쓰지도 읽지도 않는다.** 이유는 §2.1 의 역사적
참고. 이 절 번호는 다른 문서의 참조를 깨지 않기 위해 남긴다.

- 무손실 보존이 필요하면 **HTML 내보내기**를 쓴다 — `<script type=
  "application/json" id="easymindmap-map">` 에 `MapFileMeta`(맵 전체)가
  실린다 (`import-export/22-map-file-meta.md`).
- MD 가 맵에 대해 말하는 것은 §3.7 의 `emm` 선언뿐이다.
- 파서 API: `buildEmmBody(map, images, { declaration })` 가 본문을,
  `buildDeclaration` / `readDeclaration` 이 선언을 쓰고 읽는다.
  `serializeEmm` · `buildMetaComment` · `decodeMetaBase64` · `MD_META_RE`
  는 제거됐다.

### 4.3 본문 형태 표시 `mdForm` (Informative, 2026-09-15)

파서는 본문에서 **리스트 항목(`- 항목`)으로 읽은 노드**에 `mdForm: 'list'`
를 남긴다. 이 값은 노드의 **내용이 아니라 본문에서의 표기 형태**를 기억하는
것으로, 직렬화가 그 노드를 견출(`###`)이 아니라 다시 `-` 로 쓰는 데만
쓴다. 값이 없으면 견출로 본다. 규칙의 자세한 내용은 `markdown-export.md` §2.

## 5. 적합성 (Conformance)

구현체는 두 수준 중 하나를 선언할 수 있다.

### 5.1 mmd-Basic (구조 적합)

- §3 본문 문법으로 트리·노트·링크를 읽고/쓸 수 있다.
- `emm` 선언 블록은 **무시해도 된다** (코드블록이므로 일반 도구에서는
  그대로 보존된다).
- 일반 Markdown 도구는 사실상 mmd-Basic 뷰어다.

### 5.2 mmd-Full (선언 적합)

- mmd-Basic + §3.7 `emm` 선언의 기록·복원.
- 왕복 보장: `맵 → MD → 맵` 후 구조·노트·링크·첨부·사진·리스트 형태·
  레벨별 레이아웃·도형·글자 크기가 동일해야 한다. 노드별 스타일 등은
  MD 의 범위 밖이다 (HTML 내보내기가 보장한다).

### 5.3 적합성 검증 코퍼스

적합성 코퍼스는 **`packages/emm-parser/conformance/`**의 정식 자산이다:
문서형 8종 — **전량 합성**(보고서형 report-tables 19노드 · 대화 내보내기
형식 chat-export 24노드 · 견출 없는 순번 절 19노드 · README 배지 링크 ·
회의록(본문 `#` 다수 → 중심 여럿) · 깊은 견출 · 머리말만
문서 · markmap 호환 기능 · **여러 중심주제** multi-center) + AI 프롬프트
기대 출력 4종 = 14케이스. 케이스마다 ▸파싱 결과
스냅숏 ▸본문 왕복 노드 수를 자동 검증한다 (메타데이터 왕복은 2026-09-15 폐기)
(`npm test`). **제3자 구현체는 이 코퍼스를 통과하면 mmd 호환을 선언할
수 있으며, 변환 규칙 변경은 코퍼스 전체 통과 + 문서 갱신을 조건으로
한다.**

## 8. 제3자 구현 가이드 (Informative)

1. **최소 구현(mmd-Basic)**: CommonMark 파서로 헤딩 트리를 만들고
   §3.1~3.2의 부모 결정·콘텐츠 수집 규칙을 얹으면 된다. 인용/표/펜스를
   노드의 노트로 분류하면 끝.
2. **선언 구현(mmd-Full)**: 첫 헤딩 아래 ```emm 코드블록의 `map:` ·
   `template:` · `levels:` 를 읽는다 (§3.7). 들여쓰기만 읽는 최소 파서면
   된다 — YAML 이 아니다.
3. 렌더링 시 헤딩 크기를 적용하지 말 것 (§2.2).
4. 재기록 시 `emm` 코드블록을 버리지 말 것 — 모르는 키도 그대로 둔다.

## 레퍼런스 파서 설치 (2026-08-18)

`packages/emm-parser` 는 이제 **밖에서 설치해 쓸 수 있다** — CommonJS·ESM·
타입을 함께 낸다(`npm run build` → `dist/{cjs,esm,types}`).

예전에는 `main` 이 `src/index.ts` 라 **번들러 없이는 읽을 수 없었다.**
mmd 가 공개 포맷이고 이 패키지가 그 레퍼런스 구현인데, 정작 제3자가
설치해 쓸 수 없는 모양이었다. 서버(NestJS)가 트리 규칙을 `require` 하면서
드러났다.
