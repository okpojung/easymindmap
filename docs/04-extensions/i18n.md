# 다국어(i18n) 지원 계획 — 한국어 · 영어(최소)

> 상태: **계획 (백로그 B10)** — 2026-07-31 사용자 결정: 글로벌 사용을
> 위해 로그인 후 개인설정에서 언어를 선택할 수 있어야 하며, 많은
> 언어가 어렵다면 **최소한 영어는 지원**한다.

## 1. 목표와 원칙

- 1차 목표 언어: **한국어(기본) + 영어**. 사전(리소스) 구조는 언어를
  추가하기만 하면 되도록 설계해 이후 일본어 등 확장에 대비한다.
- 언어 결정 우선순위:
  1. **로그인 사용자의 프로필 설정** (서버 저장 — 어느 기기에서나 동일)
  2. 로컬 설정 (비로그인 — localStorage 기억)
  3. **브라우저 언어 자동 감지** (첫 방문 기본값: `navigator.language`
     가 ko\*면 한국어, 아니면 영어)
- **EMM 형식·파서는 언어 중립** — 문서 구조(견출·표·코드)만 다루므로
  영향 없음. 단 파서가 만드는 소수의 한국어 리터럴(블록 노드 라벨
  `표`/`코드`/`체크리스트`, 이미지 파일명 폴백 `이미지`)은 맵 데이터에
  들어가므로 **생성 시점의 언어**를 따르게 사전화한다.

## 2. 단계 (Phase)

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| P1 | **문자열 사전 기반 구축** — `src/i18n/ko.ts`·`en.ts` + `t('key')` 헬퍼(경량 자체 구현 또는 react-i18next). 에디터 UI의 화면 노출 문자열(버튼·툴팁·안내·다이얼로그 — 수백 개)을 키로 추출·치환. 설정 메뉴에 언어 선택(한국어/English, localStorage 기억 + 브라우저 언어 기본값) | 없음 (프런트 단독) |
| P2 | **HTML 뷰어 내보내기 현지화** — 뷰어 UI 문자열(검색·접기·툴팁 등)을 내보내는 시점의 언어로 베이크. exportHtml.ts의 VIEWER_JS 문자열도 사전 경유 | P1 |
| P3 | **로그인 개인설정 연동** — 사용자 프로필에 `language` 필드, 개인설정 화면에서 변경, 로그인 시 프로필 값이 로컬 설정을 덮어씀 | 서버 로그인 |
| P4 | **문서·AI** — user-guide 영어판, 제품 소개 영어판, AI 생성 지침의 답변 언어 옵션 | P1, 오픈 준비 |

## 3. 구현 시 주의 (조사 결과, 2026-07-31)

- 프런트 95개 파일에 한글 문자열 약 7,300곳 — 대부분은 **코드 주석**
  (주석은 번역 대상 아님). 화면 노출 문자열은 수백 개 수준으로 추정.
- **E2E 테스트가 한국어 라벨 셀렉터에 광범위하게 의존** —
  `button[title="내보내기"]`, `text=📄 MD 파일 불러오기`,
  `'복사됨 ✓'` 등. i18n 도입과 **함께** 주요 조작 요소를
  `data-testid`로 이행해야 언어를 바꿔도 테스트가 깨지지 않는다
  (도입 규모의 상당 부분이 이 작업).
- 날짜/시각 표시(`toLocaleString('ko-KR')` 등)도 언어 설정을 따르게.
- 사전 키는 화면 단위 접두사(`toolbar.export`, `newmap.importMd` …)로
  묶어 미번역 키 검출 스크립트(ko에 있는데 en에 없는 키)를 CI에 둔다.

## 4. 뒤늦은 도입이지만 구조적 부담은 제한적인 이유

초기 설계에 i18n이 빠진 것은 사실이나, 현 구조에서 후행 도입의
비용은 대부분 **기계적 치환**이며 구조 변경은 거의 없다:

- **데이터(맵·EMM 파일)는 처음부터 언어 중립** — 사용자가 만든 맵과
  내보낸 파일은 마이그레이션이 필요 없다.
- UI 문자열이 컴포넌트 안 리터럴로 흩어져 있을 뿐, 별도 프레임워크
  제약이 없어 `t('key')` 치환을 화면 단위로 점진 진행할 수 있다
  (한 번에 전부 바꿀 필요 없음 — 미치환 문자열은 한국어로 남을 뿐).
- 가장 큰 실비용은 문자열 추출 자체보다 **E2E 셀렉터의 data-testid
  이행**(§3)이며, 이는 테스트 견고성 측면에서 언젠가 해야 할 일이기도
  하다.

## 5. 권장 시점

P1~P2는 프런트 단독으로 가능하지만 문자열 치환 + 테스트 셀렉터 이행
규모가 커서, **정식 오픈 준비 단계에 B3(코드 스플리팅)과 함께** 묶어
진행을 권장. P3는 서버 로그인 도입 시.
