# 오픈코어 경계 — 무엇이 공개이고 무엇이 유료인가

> **결정 1 (2026-08-15)**: 저장소는 **공개(Apache-2.0)로 그대로 둔다.**
> 유료 기능의 **구현만 별도 private 저장소**에서 개발한다. **설계 문서는
> 공개 저장소에 그대로 남긴다** — 로드맵이 보이는 편이 신뢰에 낫다.
>
> **결정 2 (2026-08-16)**: 유료 범위는 협업만이 아니다. **로드맵의 MVP 를
> 넘는 제품 기능 전부**(협업 · 실시간 번역 · 각종 플러그인 · WBS · Redmine ·
> Obsidian · 대시보드 · AI 실행형 절차 …)가 유료다. **경계선은 MVP 다.**
>
> 이 문서는 그 경계를 정하고, **공개 코어에 어떤 구멍(확장점)을 뚫어 둘지**를
> 적는다. 지금 뚫어 두지 않으면 나중에 코어를 다시 뜯어야 한다.

---

## 1. 왜 저장소를 나누나 — 법이 아니라 사고 방지다

**법적으로는 나눌 필요가 없다.** Apache-2.0 은 허용적(permissive) 라이선스라
**파생물을 독점으로 만들어 파는 것을 명시적으로 허용**한다. GPL/AGPL 같은
"가져다 쓰면 너도 공개하라"가 없고, SaaS 로 제공할 때의 공개 의무(네트워크
카피레프트)도 없다. 코어가 Apache-2.0 이어도 **유료 모듈을 비공개로 두는 데
아무 문제가 없다.**

나누는 이유는 하나다.

> **git 저장소는 통째로 public 이거나 private 이다.** "이 폴더만 비공개"는
> 불가능하고, 실수로 한 번 커밋되면 **되돌릴 수 없다** — 지우고 force-push
> 해도 이미 클론·포크된 사본과 GitHub 캐시에는 남는다.

저장소를 나누는 것이 **실수를 구조적으로 막는 유일한 방법**이다.

> ⚠️ Apache-2.0 은 **경쟁자가 우리 코어로 자기 SaaS 를 만드는 것도 허용**한다.
> 그것이 문제가 되면 **앞으로의 버전**에 AGPL·BSL 을 적용하는 방법이 있다
> (저작권을 한 사람이 갖고 있으므로 가능하다). 다만 **이미 공개한 스냅샷은
> 영원히 Apache-2.0 이다.** 별개 결정이므로 여기서 정하지 않는다.

## 2. 저장소 배치

| 저장소 | 공개 | 라이선스 | 담는 것 |
|---|---|---|---|
| `okpojung/easymindmap` | **public** | Apache-2.0 | **MVP 전부** + 운영 도구 + **확장점** + **설계 문서(유료 기능 포함)** |
| `okpojung/easymindmap-pro` | **private** | 독점 | **MVP 이외 제품 기능 전부**의 구현 (서버 + 화면) |

배포는 private 쪽에서 둘을 합쳐 빌드한다(§6).

**세 번째 저장소(deploy)는 만들지 않는다.** 지금 배포는 Coolify 가 저장소
하나를 보고 도는 구조이고, 유료판은 private 저장소 하나가 코어를 의존성으로
당겨 오면 충분하다. 저장소가 늘면 "어느 것이 진짜인가"를 매번 따져야 한다.

## 3. 경계 — 선은 **MVP** 다

`docs/00-project-overview/roadmap.md` 의 **MVP 표가 공개 범위의 기준**이다.
그 표에 있는 것은 공개, **MVP 를 넘는 제품 기능은 유료**다.

| | 공개 코어 | private 유료 |
|---|---|---|
| MVP 기능 전부(편집기·Kanban·자동저장·AI 생성·Export/Import·문서함·버전 히스토리 …) | ✅ | — |
| **협업** (동기화·Presence·잠금·채팅·스레드) | ❌ | ✅ |
| **실시간 번역** (노드 번역·채팅 번역·캐시) | ❌ | ✅ |
| **각종 플러그인** (Redmine · Obsidian · 외부 연동) | ❌ | ✅ |
| WBS · 리소스 할당 · 대시보드 맵 · AI 실행형 절차 | ❌ | ✅ |
| 유료 기능의 **설계 문서** | ✅ 그대로 | — |
| 확장점 **계약 · 스텁 · 경로** | ✅ | — |
| 유료 전용 **DB 표** | ❌ | ✅ (자기 델타 SQL 로) |
| 유료 기능의 **e2e 스크립트·카탈로그** | ❌ | ✅ |

**"자리와 규칙은 공개, 알맹이는 비공개"** 가 원칙이다.

### 3.1 예외 셋 — 이걸 안 정해 두면 매번 헷갈린다

**"MVP 표에 없으면 유료"** 를 글자 그대로 적용하면 어긋나는 것이 셋 있다.

#### ① 운영 도구는 제품 기능이 아니다 → **공개**

관리자 콘솔 · 헬스체크 · 백업 절차 · 감사 로그 · 로그인 이력 ·
개인정보 처리방침. MVP 표에 없지만 이것들은 **파는 물건이 아니라 공개판을
돌리는 데 필요한 것**이다. 공개판을 받아 자기 서버에 세운 사람이 회원을
관리하고 장애를 알아채지 못하면, 그건 제품이 아니라 반쪽이다.

> 가르는 질문: **"이걸 빼면 팔 것이 없어지나, 돌릴 수가 없어지나?"**
> 팔 것이 없어지면 유료, 돌릴 수가 없어지면 공개다.

#### ② EMM 포맷과 파서는 **공개** — 유료 기능의 필드라도

이 저장소는 [Mindmap Markdown](https://mindmapmarkdown.org) 표준의
**레퍼런스 구현**이라고 README 에서 선언한다. 포맷을 비공개로 돌리면
**표준이 아니게 된다.**

그래서 유료 기능이 파일 포맷에 필드를 더할 때(예: WBS 의 시작일·종료일·
진척률), **그 필드의 정의와 직렬화는 `packages/emm-parser` 에 공개로 들어간다.**
비공개인 것은 **그 필드로 무엇을 하는가**(WBS 화면·계산·간트·동기화)다.

> 포맷은 공개, 그 포맷을 다루는 기능은 유료. 이렇게 갈라야 공개판으로
> 저장한 파일을 유료판이 읽고, 유료판으로 저장한 파일을 공개판이 **깨지지
> 않고** 읽는다. 파일 호환이 깨지면 사용자가 잃는 것은 우리 수익이 아니라
> 자기 문서다.

#### ③ 화면의 **자리**는 공개, 알맹이는 비공개

메뉴 항목 · `준비 중` 배지 · 협업자 아바타 같은 **표시용 껍데기**는 코어에
둔다. 자리까지 유료 모듈이 만들게 하면 **코어의 레이아웃을 유료 모듈이
알아야** 해서 경계가 무너진다.

> 이 패턴은 이미 두 군데서 쓰고 있다 — 관리자 콘솔의 **결제관리 탭이
> `준비 중` 자리만 차지**하는 것(`AdminPage.tsx` 의 `TABS[].soon`), 그리고
> **협업 presence UI**(`CollabAvatars` · `CollabCursor` · 편집중 배지)가
> `featureFlags.ts` 의 `COLLAB_PRESENCE_UI = false` 로 꺼진 채 목데이터를
> 들고 있는 것이다. 둘 다 **경계상 올바른 쪽**에 있으므로 손대지 않는다.

### 3.2 이미 공개된 것은 되돌릴 수 없다

**이 경계는 앞으로 만들 것에만 적용된다.** 이미 Apache-2.0 으로 공개된
스냅샷은 영원히 그 라이선스이고, 지운다고 회수되지 않는다.

지금 공개 저장소에 **MVP 를 넘는 제품 기능의 구현은 없다**(2026-08-16 확인 —
WBS·Redmine·Obsidian·번역·대시보드·Workflow 는 전부 설계 문서만 있고 코드가
없다). 협업 관련 코드는 위 ③ 의 껍데기 105줄뿐이다. **그래서 지금 선을 그으면
소급해서 지울 것이 없다.**

## 4. 서버 확장점 — **이음매는 하나다**

### 4.1 왜 기능마다 뚫지 않나

2026-08-15 에 만든 첫 확장점은 `@easymindmap/collab` **하나에 못 박혀**
있었다. 유료 범위가 MVP 이외 전부로 정해진 이상 그 방식은 못 쓴다.

> 유료 기능이 8개면 코어에 **거의 똑같은 모듈이 8개** 생기고, 유료 기능이
> 하나 늘 때마다 **공개 코어를 고쳐야 한다.** 그러면 확장점을 만든 의미가
> 없다 — 확장점의 값어치는 **코어를 다시 뜯지 않아도 되는 것**이다.

그래서 **코어는 패키지 하나만 찾는다.**

```
공개 코어  ──찾는다──▶  @easymindmap/pro   (private 저장소가 배포)
                          ├── 협업
                          ├── 실시간 번역
                          ├── 플러그인 (Redmine · Obsidian …)
                          └── … 늘어도 코어는 안 바뀐다
```

**유료 기능을 하나 더 만들어도 공개 코어에는 커밋이 없다.** 이게 이 설계가
사려는 것 전부다.

### 4.2 라이선스 판정은 **비공개 쪽에 둔다**

어느 고객이 어느 기능을 살 수 있는지 정하는 코드가 공개 코어에 있으면
**지우면 그만이다.** 판정은 `@easymindmap/pro` 안에 있고, 코어는 그 결과만
받는다. 코어는 "무엇이 켜졌나"를 알 뿐 "왜 켜도 되는가"를 모른다.

### 4.3 코어가 아는 것 — 기능 목록과 그 상태

```
apps/api/src/pro/
  pro.module.ts       ← 이 자리에서 갈린다 (공개)
  pro.contract.ts     ← 인터페이스 (공개)
  pro.stub.ts         ← 유료 모듈이 없을 때 (공개)
  pro.controller.ts   ← GET /v1/features (공개)
```

```ts
// pro.contract.ts (공개 코어)
export interface ProFeature {
  id: string;          // 'collab' · 'translate' · 'plugins' …
  enabled: boolean;
  reason: string | null;   // 꺼져 있으면 **왜** — 화면이 그대로 보여 준다
}
export interface ProContract {
  features(): ProFeature[];
}
```

```ts
// pro.module.ts (공개 코어)
static register(): DynamicModule {
  // **선택 의존성**이다 — 없으면 스텁으로 간다.
  // require 를 try 로 감싸는 이유: 번들러가 없는 패키지를 찾다 빌드를
  // 깨뜨리지 않게 하려면 정적 import 를 쓸 수 없다.
  try {
    const pro = require('@easymindmap/pro');
    return { module: ProModule, imports: [pro.ProModule], … };
  } catch { /* 유료 모듈이 없다 — 공개판이다 */ }
  return { module: ProModule, providers: [{ provide: PRO, useClass: ProStub }], … };
}
```

**유료 기능의 경로는 유료 모듈이 가져온다.** 코어가 가진 경로는
`GET /v1/features` 하나뿐이고, 그것이 **꺼져 있어도 왜 꺼졌는지** 답한다.

> 첫 설계(2026-08-15)에서는 경로를 코어에 두라고 적었다. 그 이유는 "모듈이
> 없을 때 404 가 *원래 없다*인지 *유료라서 없다*인지 구분되지 않는다"였다.
> **`/v1/features` 가 그 일을 대신하므로 이유가 사라졌다** — 화면은 경로를
> 두드려 보는 대신 목록을 한 번 물어보면 된다. 유료 경로까지 코어가 들고
> 있으면 기능이 늘 때마다 코어를 고쳐야 한다(§4.1).

**규칙 셋.**

1. **코어는 유료 모듈의 타입을 import 하지 않는다.** 계약만 보고, 구현은
   런타임에 꽂힌다. 그래야 공개 저장소만으로 타입체크가 통과한다.
2. **스텁이 기본이다.** 유료 모듈이 없을 때가 **정상 동작**이지 오류 상태가
   아니다 — 공개판을 받아 쓰는 사람에게는 그게 제품이다.
3. **기동 로그에 어느 쪽인지 한 줄 남긴다.** `유료 모듈: 설치됨(협업·번역) /
   없음(스텁)`. 운영에서 "왜 이 기능이 안 되지"를 로그 한 줄로 끝내기 위해서다.

## 5. 프런트 확장점 — Vite 별칭

프런트는 번들러가 빌드 시점에 정하므로 **별칭(alias)** 이 맞다. 이 저장소는
이미 같은 패턴을 쓴다 — `@emm` → `packages/emm-parser/src`.

```ts
// vite.config.ts
alias: {
  '@emm': …,
  // 유료 UI 가 있으면 그쪽, 없으면 코어의 스텁으로
  '@pro': existsSync(proUi) ? proUi : './src/pro/stub',
}
```

```
apps/frontend/src/pro/
  contract.ts   ← 화면이 기대하는 모양 (공개)
  stub.tsx      ← "유료 기능입니다" 안내 (공개)
```

**메뉴 자리는 코어에 둔다**(§3.1 ③). 화면은 `GET /v1/features` 를 한 번
물어보고, 꺼진 기능은 **자리를 두되 왜 꺼졌는지**를 보여 준다.

## 6. DB 경계

| | 누가 소유하나 |
|---|---|
| `maps`·`map_documents`·`users` 등 | 코어 |
| `maps.kind = 'collab'` 표식 | 코어 (이미 있다) |
| 유료 전용 표 (Presence·잠금·채팅·번역 캐시·연동 설정 등) | **유료 모듈** — 자기 델타 SQL 로 만든다 |

**코어의 헬스체크(`REQUIRED_TABLES`)에 유료 표를 넣지 않는다.** 넣으면
공개판만 배포했을 때 영원히 `degraded` 가 된다. 유료 모듈은 자기 표를
자기가 확인한다.

**유료 표 이름은 접두사로 갈라 둔다**(`pro_` 또는 기능별 `collab_`·
`trans_`). 한 DB 에 코어 표와 섞여 있으므로, 이름만 보고 **어느 저장소가
소유한 표인지** 알 수 있어야 한다. 백업·복구·스키마 점검 때 이것 하나로
갈린다.

## 7. 빌드·배포

> **2026-08-16 정정.** 아래 내용은 처음에 사실과 다르게 적혀 있었다.
> "코어를 npm 의존성으로 당겨 오고 태그로 고정한다"고 했지만, 확인해 보니
> **코어에 태그가 하나도 없고**(`git tag` = 0개), **코어는 npm workspaces
> 모노레포가 아니다** — 루트에 `package.json` 이 없고 `apps/api`·
> `apps/frontend` 가 각자 갖고 있다. 그 방식은 지금 성립하지 않는다.

private 저장소가 **코어를 clone 해서 그 위에 유료 모듈을 얹어** 빌드한다.

```
easymindmap-pro/
  packages/…          → @easymindmap/pro      (NestJS 모듈 · 기능별 하위 폴더)
  ui/                 → @easymindmap/pro-ui   (React)
  Dockerfile          → ① 코어 clone(고정 리비전) ② 유료 모듈 얹기 ③ 함께 빌드
```

**어느 코어 위에서 도는지는 리비전으로 고정한다.** 지금은 태그가 없으므로
**커밋 SHA** 로 고정하고, 코어에 릴리스 태그를 찍기 시작하면 태그로 바꾼다.
고정하지 않으면 "어제는 되던 게 오늘 안 된다"의 원인을 영원히 못 찾는다.

> **배포물에 코어의 `LICENSE`(와 `NOTICE`)를 함께 넣는다** — Apache-2.0 §4
> 의 조건이다(§9). Dockerfile 을 고칠 때마다 이 사본이 여전히 들어가는지
> 확인한다. 빠뜨리면 **허용된 결합이 침해가 된다.**

Coolify 는 **유료판 배포에서 private 저장소를 Source 로** 쓴다. private
저장소를 Source 로 쓰려면 **배포 키/GitHub App 연결이 따로 필요**하다 —
지금 공개 저장소를 연결한 방식 그대로는 안 된다. 공개판을 따로 돌릴 일이
있으면 지금 설정을 그대로 두면 된다.

## 8. 공개 저장소에 남기면 안 되는 것

설계 문서는 남기기로 했지만(사용자 결정), 아래는 **절대 넘어가면 안 된다.**

- 유료 기능의 **구현 코드**(부분·미완성이라도)
- 유료 기능의 **e2e 스크립트와 카탈로그 항목** — 무엇을 어떻게 만들었는지가
  그대로 드러난다. 유료 쪽 검증은 private 저장소의 카탈로그에 적는다
- API 키·라이선스 키·서명 비밀값
- 유료 고객 명단·계약 조건

> **판단이 서지 않으면 private 에 둔다.** 나중에 공개로 옮기는 것은 언제든
> 되지만, 공개된 것을 비공개로 되돌리는 것은 **불가능하다.**

## 9. 라이선스 표기

- 공개 코어: `LICENSE`(Apache-2.0) 그대로. 기여자가 생기면 `NOTICE` 관리.
- private 모듈: 파일 머리에 **독점 표기**를 넣는다.
  ```
  Copyright (c) 2026 <상호>. All rights reserved.
  This file is NOT covered by the Apache-2.0 license of easymindmap core.
  ```
- 유료 모듈이 코어를 쓰는 것은 Apache-2.0 이 허용한다. **배포물에 코어의
  라이선스 사본과 NOTICE 를 포함**해야 한다(Apache-2.0 §4).

### 10.2 저장소 이름 (2026-08-16 정리 완료)

private 저장소 이름은 처음에 `easymindmap-collab` 이었다. 담는 것이 협업만이
아니게 되면서(결정 2) 이름이 좁아져 **`easymindmap-pro` 로 바꿨다.**

**배포가 붙기 전이라 값이 거의 안 들었다** — 고칠 것은 문서의 이름 언급뿐이었다.
GitHub 은 옛 URL 을 리다이렉트로 살려 두지만, **누가 옛 이름으로 저장소를 새로
만들면 그 리다이렉트가 끊긴다.** 그래서 리다이렉트에 기대지 않고 링크를 새
이름으로 고쳐 둔다.

> 이름을 바꿔야 할 것 같으면 **배포가 붙기 전에** 하는 것이 맞다. 붙은 뒤에는
> Coolify Source·배포 키·CI 설정까지 따라 움직인다.
