## 0. 이 서비스의 모양 — **맵 쇼핑몰** (2026-09-05 사용자 정리)

> "퍼블리싱하여 맵을 등록하는 웹페이지는 어떻게 보면 **하나의 다양한 맵을
> 판매하는 쇼핑몰 개념**이다."
> "유튜브와 같은 개념일 수도 있겠다."
> — 사용자, 2026-09-05

이 한 마디가 §1~§5 의 배경이다. 여기서 정리해 둔다.

### 0.1 무엇이 같은가 — 쇼핑몰·유튜브에서 가져오는 것

| 그쪽 | 우리 | 이미 있는 것 |
|---|---|---|
| 상품 등록 | 퍼블리싱 | `POST /maps/{id}/publish` |
| 상품 상세 페이지 | 공개 뷰 `/p/{id}` | `PublicMapPage` |
| 썸네일 | 실루엣 미리보기 | `preview.png` (§2) |
| 판매자 = 한 사람 | **단독맵만** | §5.0 |
| 내리기 | 퍼블리싱 중단 | `DELETE …/publish` |
| 진열대(둘러보기) | `/explore` | **아직 없다** |
| 판매자 관리 화면 | 퍼블리싱 관리 | **아직 없다** (0.3) |

### 0.2 무엇이 다른가 — 유튜브와 갈리는 지점 하나

유튜브는 영상을 **비공개로 돌렸다가 다시 공개해도 URL 이 그대로**다.
우리는 **중단하면 그 주소가 영구히 죽는다**(`27-publish-share.md` §6.4).

일부러 다르게 골랐다. 유튜브의 "비공개" 는 *보관* 이고, 우리의 "중단" 은
*내림* 이다 — 시스템은 그 둘을 구분할 수 없으므로 하나로 정했다.
나중에 "잠시 내림(보관)" 과 "완전히 내림" 을 **사용자가 직접 고르게** 하고
싶어지면, 그때 `published_maps` 에 상태 한 칸을 더하면 된다. 지금 미리
만들지 않는다.

### 0.3 그래서 다음 작업 — **퍼블리싱한 맵은 문서함에서 따로 뺀다**

> "퍼블리싱맵은 내 문서함에도 넣는 것이 아니라 **쇼핑몰에 상품을 등록하는
> 것 같은 개념**으로, 내 문서함에서 빼고 별도로 관리하는 것이 어떤가."
> — 사용자, 2026-09-05

**그렇게 한다.** 다만 *데이터*를 옮기지 않고 *보이는 자리*만 나눈다.

* 문서함 대화상자에 **`퍼블리싱` 섹션(탭)** 을 하나 만든다 —
  휴지통이 이미 그렇게 나뉘어 있다.
* 목록의 판정은 **저장된 표시가 아니라 지금의 퍼블리싱 상태**에서 끌어온다
  (`publish_id IS NOT NULL`). 그래야 **중단하는 순간 문서함으로 저절로
  돌아온다** — 따로 되돌리는 코드가 필요 없고, 어긋날 수도 없다.
* 그 탭이 나중에 **상품 관리 화면**이 된다 — 값·소개글·분류·판매 현황이
  붙을 자리가 거기다(§3·§6).
* 이번 작업(편집 금지·상호 배제·용어)과 **파일이 겹치므로 다음 브랜치로**
  미룬다 (`CLAUDE.md` §2.1 — 브랜치를 쌓지 않는다).

### 0.4 진열대 — **`퍼블리싱맵` 메뉴를 가진 웹사이트** (2026-09-05 사용자)

> "easymindmap 전용 홈페이지에 만들어 그 웹사이트에 **퍼블리싱맵 메뉴**를
> 만들어서 공개해야 될 것 같다." — 사용자, 2026-09-05

맞다. 지금은 **링크를 아는 사람만** 퍼블리싱된 맵을 볼 수 있다 — 상품은
있는데 **진열대가 없다.** 다만 이걸 짓기 전에 순서가 있다.

**⑴ 먼저 `<head>` 다 (SEO·링크 카드).** 진열대를 만들어도 지금 구조로는
검색에도 안 걸리고, 카톡·슬랙에 붙여넣어도 카드가 안 뜬다 — nginx 가 모든
주소에 같은 `index.html` 을 주기 때문이다(`27-publish-share.md` §13).
쇼핑몰에서 **상품 페이지가 검색이 안 되는 것**은 진열대가 없는 것보다
치명적이다. **API 가 `/p/{id}` 의 `<head>` 를 맵마다 만들어 주는 것**이
가장 작은 해법이다 — 제목·소개·`preview.png` 를 이미 서버가 알고 있다.

**⑵ 그다음 목록(`/explore`).** 이건 지금 앱 안의 한 화면으로 충분하다.
따로 사이트를 세우면 배포 대상·인증·디자인 토큰이 두 벌이 된다.
**같은 프런트엔드의 한 경로**로 시작하고, 마케팅 페이지가 정말 따로
필요해지면 그때 분리한다 (분리는 나중에 해도 늦지 않지만, 합치는 것은
어렵다).

**⑶ 목록에 넣을 것.** 퍼블리싱된 맵 중 **저자가 "진열대에 올린다"고 고른
것만.** 링크로만 나누고 싶은 맵(사내 문서·개인 홈페이지용)이 검색 결과에
뜨면 그건 사고다 — `published_maps` 에 `listed` 한 칸이면 된다.

순서는 ⑴ → 0.3(퍼블리싱 관리 화면) → ⑵ 다.

## 1. 무엇을 파는가

**맵 하나가 상품 하나다.** 저자가 정리해 둔 지식을 그대로 판다.
**파는 것은 단독맵뿐이다** — 저자가 한 사람이라야 배분 문제가 없다(§5.0).

리포트 판매 사이트와 다른 점이 하나 있다 — **산 사람이 그 맵을 자기
에디터로 다시 불러올 수 있다.** 불러오기는 이미 있는 기능이다
(`새 맵 → 불러오기`). 그래서 구매자는

- 산 맵을 **자기 맵에 이어 붙이고**
- 자기 상황에 맞게 **고쳐 쓰고**
- 거기서 **자기 버전을 키운다**

**"읽는 자료"가 아니라 "쓸 수 있는 뼈대"** 라는 것이 이 상품의 차별점이고,
그것은 §4 의 "구매 = 다운로드" 때문에 가능하다. 웹에서만 보게 했으면
오히려 약해진다. 판매 화면의 문구도 그 점을 말해야 한다.

## 2. 미리보기 — 실루엣 + 2레벨 목차

사지 않은 사람에게 보여 주는 것은 **둘**이다. 역할이 다르다.

| | 무엇을 전달하나 |
|---|---|
| **실루엣 이미지** | **규모와 구조** — 얼마나 크고 어떻게 뻗어 있나 |
| **2레벨 제목 목록** | **내용** — 무엇에 대한 맵인가 |

하나만으로는 부족하다. 이미지만 있으면 "무엇에 대한 맵인지" 알 수 없어
살 이유가 없고, 목차만 있으면 **"이만큼 정리했다"** 는 규모감이 전달되지
않는다. 목차는 덤으로 검색·스크린리더 문제까지 해결한다(이미지는
검색에 안 잡힌다).

### 2.1 ★ 실루엣은 "희미하게"가 아니라 "글자를 뺀 것"이다

전체 맵을 **작게 또는 흐리게** 만들어 내보내는 방식은 안 된다.

**축소·블러는 복원된다.** 마인드맵은 폰트가 균일하고 배경이 단색이라
업스케일·디블러·OCR 이 특히 잘 먹는다. "알아볼 수 없을 정도"의 경계를
잡아도, 몇 달 뒤 모델이 좋아지면 그 경계가 무너진다. **한 번 나간
이미지는 회수할 수 없다.**

그래서 **렌더링 단계에서 글자를 아예 뺀다.** 복원할 원본이 없으면
복원되지 않는다.

```
노드   둥근 사각형 — 크기·색은 그대로
글자   회색 막대 ▬▬▬  (글자 수에 비례한 길이만)
연결선·레이아웃·색  그대로
```

잃는 것이 없다 — 전달하려던 것이 **규모·구조·밀도·색 배치**였고,
글자는 어차피 안 읽히게 할 셈이었다. 대신 **안전이 확실해진다.**

> ✅ **구현됨** (2026-09-05, 코어 #389). `apps/frontend/src/export/silhouette.ts`.
> 아래 §2.1·§2.2 가 정한 그대로다 — 검증은 `test-catalog.md` e2e198.

### 2.2 어디서 만드나 — 저자의 브라우저

서버에는 헤드리스 브라우저도 큐도 없다(2026-09-04 확인 —
`puppeteer`·`playwright`·`sharp`·`bull`·`redis` 가 `apps/api` 에 전부 없다).
이미지 한 장을 위해 그 인프라를 들이는 것은 과하다.

**저자가 게시할 때 그 브라우저에서 한 번 만들어 올린다.** 게시는 자주
하는 일이 아니라 이 방식이 맞고, 프런트에 이미 `canvas.toDataURL` 경로가
있다(`utils/embedImage.ts`). 올린 이미지는 `published_maps` 옆에 둔다.

> 저자가 내용을 고치면 실루엣이 낡는다. **게시 화면에서 "미리보기 다시
> 만들기"를 누르게 한다** — 자동 갱신은 저자가 게시 페이지를 열지 않으면
> 돌지 않으므로, 눌러야 한다는 것을 화면이 말해 주는 편이 정직하다.

#### 2.2.1 구현하며 정한 것 (2026-09-05)

| | 정한 것과 이유 |
|---|---|
| **저장 자리** | `published_maps.storage_path` — 처음부터 그러라고 있던 칸이다. 첨부 표에 넣지 않았다: 이 그림은 **사용자의 파일이 아니라 게시가 만든 부산물**이라 저장 용량을 깎으면 안 되고 문서함에 보여서도 안 된다 |
| **크기** | **1200×630** 한 벌. 링크 카드(Open Graph)가 기대하는 1.91:1 이고, 목록 썸네일도 같은 파일을 쓴다 |
| **게시 취소하면 파일도 지운다** | 다시 게시하면 **새 링크**라 새 키를 쓴다. 안 지우면 아무도 못 여는 그림이 저장소에 영영 남는다. 행은 그대로 둔다(게시 기록은 지운 적 없는 사실이다) |
| **PNG 인지 바이트로 확인** | 확장자·`Content-Type` 은 보내는 쪽이 정하는 값이라, 그것만 믿으면 아무 파일이나 우리 저장소에 들어온다 |
| **캐시 5분** | 저자가 "다시 만들기" 를 누르면 **같은 주소의 내용이 바뀐다.** 길게 잡으면 낡은 그림이 남는다 |

#### 2.2.2 ★ 세로로 긴 맵 — 통째로 맞추면 실오라기가 된다 (측정, 2026-09-05)

카드는 1200×630 인데 맵의 비율은 제각각이다. 트리 레이아웃 61노드는 세로가
가로의 9배쯤 되는데, 이걸 통째로 맞추면 배율이 0.15 로 떨어져 **가로 5%
짜리 세로 띠**만 남았다 — 가지 2개짜리 작은 맵보다 **더 작아 보였다.**

그래서 **가로를 절반도 못 쓰면 가로에 맞추고 세로를 자른다.** 2배까지만
키운다(더 키우면 노드 몇 개가 화면을 채워 오히려 작은 맵처럼 보인다).
가로 5% → 44% 가 됐다.

잘려 나가는 것은 맵의 끝부분이고 남는 것은 **밀도·구조·색 배치**다 —
전달하려던 것이 그것이다. 전체 규모는 화면이 숫자로 따로 말한다
("전체 147노드", §2.3).

## 3. ★ 접는 것은 숨기는 것이 아니다 — 서버가 자른다

**설계에서 가장 중요한 규칙이다.**

미리보기를 "3레벨 이하를 접은 상태"로 만들면 안 된다. 접기는 **화면
상태**이지 접근 제어가 아니다. 서버가 맵 전체를 내려보내고 클라이언트가
접어 두면, **F12 한 번이면 유료 내용이 전부 보인다.**

> 결제하지 않은 사람에게는 **잘라 낸 문서**를 보낸다.
> 접힌 문서가 아니라, 3레벨 이하가 **애초에 없는** 문서다.

노드 수·깊이 같은 숫자는 **서버가 세어서 숫자만** 내려보낸다.

```
GET /published/{publishId}        미리보기 문서(2레벨까지) + 통계 + 실루엣
GET /published/{publishId}/file   전문. 구매 확인 후에만. 아니면 402
```

> 경로 표기는 `27-publish-share.md` §10 의 정리를 따른다 — **브라우저 URL 은
> `/p/{publishId}` 단축형, API 엔드포인트 기준은 `/published/{publishId}`**
> (`api-spec.md` v2.3 §8).

이것은 `open-core-boundary.md` §4.2 (*"라이선스 판정은 비공개 쪽에 둔다"*)
와 §1.2 (*"공개 코어에 있으면 지우면 그만이다"*)가 말하는 것과 같은
성질의 실수다. **판정은 서버에서, 데이터는 안 보낸다.**

## 4. 구매 = 다운로드하여 소유

> **결제하면 파일을 받는다. 받은 파일은 산 시점 그대로다.**
> 게시가 취소되면 웹에서는 더 볼 수도 살 수도 없고, **파일만 남는다.**

자료 판매 사이트(해피캠퍼스·텀블벅·Gumroad)가 전부 이 구조다. 검증된
길이고, 구매자도 설명 없이 이해한다.

### 4.1 이 규칙 하나로 없어지는 것

| 안 만들어도 되는 것 | 왜 |
|---|---|
| 구매 시점 문서 **박제** | 파일이 구매자 손에 있다 |
| "언제까지 보관하나" 규칙 | 보관하지 않는다 |
| 구매 시점 **version 기록** | 받은 파일이 그 기록이다 |
| "산 시점 판 열람" 화면 | 파일을 열면 된다 |

`map_sales`(§5)에는 **"언제 누가 무엇을 얼마에 샀다"만** 남고 내용은
남지 않는다.

### 4.2 만드는 것도 새로 없다

```
결제 확인 → 서버가 전문을 브라우저에 한 번 내려준다
          → 기존 내보내기 코드가 브라우저에서 파일을 만든다
             (export/exportHtml · exportMarkdown · zip.ts)
```

서버에 새 배관이 필요 없다. `content-permanence.md` 가 약속한 **"내보낸
파일은 서버 없이 열린다"** 가 그대로 인도 방식이 된다.

### 4.3 퍼블리싱 중에는 내용이 **바뀌지 않는다** (2026-09-05 정정)

> 이 절은 원래 "저자가 오탈자를 고치면 페이지도 바뀐다" 였다.
> **더 이상 그렇지 않다.** 퍼블리싱한 맵은 완성본이라 **편집 자체가
> 막힌다** (`27-publish-share.md` §6.2). 고치려면 중단해야 하고,
> 중단하면 그 주소는 죽는다(§6.4).

그래서 규칙이 오히려 단순해졌다.

* 링크가 살아 있는 동안 독자가 보는 판은 **하나**다 — 파는 물건이 몰래
  바뀌지 않는다. **판매에는 이쪽이 맞다.**
* 저자가 고치고 싶으면 **중단 → 편집 → 다시 퍼블리싱**이고, 그것은
  **새 주소로 새로 내놓는 일**이다 (개정판을 내는 것과 같다).
* **이미 받은 파일은 어느 쪽이든 그대로다.**

사용자 설명도 한 줄로 끝난다 —
*"올려 둔 동안에는 내용이 바뀌지 않습니다. 고치시려면 내렸다가 다시
올리시면 됩니다."*

### 4.4 ★ 재배포는 막지 못한다 — 알고 고른 것이다

**파일을 준 순간 산 사람이 그것을 남에게 넘기는 것을 기술로 막을 수
없다.** HTML·ZIP 은 서버 없이 열리도록 **설계된** 것이기 때문이다.

이것은 결함이 아니라 **맞바꿈**이다. 해피캠퍼스도 텀블벅도 같은 자리에
있고, 감수하고 운영한다. DRM 을 걸려면 이 제품의 핵심 약속
(`content-permanence`)을 깨야 한다.

현실적인 억제책은 **구매자 워터마크**(파일에 구매자 이메일·구매번호를
박는 것) 하나뿐이다. 넣을지는 §10 에 미결로 둔다.

## 5. 수수료와 정산 — 원장을 세 층으로

구매액 전부가 저자에게 가지 않는다. **일정 비율을 수수료로 떼고 나머지를
저자에게 준다.**

```
구매자 결제 4,900원
   → PG 가 우리 통장에 입금
   → 우리 몫  수수료 10% =   490원
   → 저자 몫            = 4,410원   ← 우리 돈이 아니다. 맡아 두는 것이다
```

**저자 몫은 우리 돈이 아니다.** 그래서 코드보다 회계·법률 쪽 무게가 크다
(§9).

### 5.0 ★ 파는 것은 **단독맵뿐**이라 배분 문제가 없다

무료 게시가 단독맵만 되므로(`27-publish-share.md` §6) 유료도 단독맵만이다.
**이 한 줄이 정산에서 가장 어려운 문제를 통째로 지운다.**

협업맵을 팔 수 있게 두면 이것부터 정해야 한다.

- 참여자 여럿의 **지분을 어떻게 나누나** — 균등? 기여도? 개설자가 정하나?
- **기여도를 무엇으로 재나** — 노드 수? 글자 수? 편집 횟수? 어느 것도
  "누가 더 좋은 생각을 냈나" 를 재지 못한다
- 정산 전에 **참여자가 나가면** 그 몫은 어디로 가나
- 나중에 **참여자가 늘면** 이미 판 건의 몫이 달라지나
- 지분에 이의가 생기면 **누가 판정하나** — 우리가 하면 분쟁의 당사자가 된다

전부 코드가 아니라 **합의와 분쟁의 문제**다. 답을 정해도 다음 사례에서
다시 다툰다. 단독맵만 파는 한 저자는 언제나 한 사람이고, `map_sales` 의
저자 칸도 하나면 된다(§5.1).

> 협업 저작물을 팔아야 할 날이 오면, 그때는 **판매 주체를 사람이 아니라
> 팀으로** 두는 설계부터 새로 해야 한다. 지금 구조에 끼워 넣을 것이 아니다.

### 5.1 원장 세 층

기존 `pay_orders` 는 **우리 매출**만 다룬다(요금제를 팔고 `applyPlan` 으로
지급). 중개는 그 뒤가 있다. **`pay_orders` 는 손대지 않고 위에 얹는다.**

```
pay_orders     결제 사실            (이미 있다 — 그대로 둔다)
  └ map_sales  판매 1건             맵·저자·구매자·판매가·수수료율·저자몫·상태
       └ payouts  정산 1건          저자·기간·합계·이체 결과
```

### 5.2 ★ 요율은 설정값이고, 판매는 박제다

**둘 다 필요하다.** 헷갈리기 쉬운 자리라 분명히 해 둔다.

| | 어디 | 왜 |
|---|---|---|
| **지금 요율** | `sale_settings.fee_percent` — 콘솔에서 바뀐다 | 앞으로의 판매에 적용 |
| **그 판매의 요율** | `map_sales.fee_percent` — 판매 시점 값을 **박는다** | 지난 판매가 흔들리면 안 된다 |

요율을 10% → 15% 로 바꿨을 때 **어제 판 건의 저자 몫이 함께 줄어들면
안 된다.** 정산은 돈이라 되돌릴 수 없다. `map_sales` 는 판매 시점의
요율·판매가·저자몫을 **계산된 결과까지** 함께 남긴다.

`plan_quotas` 와 `pay_orders` 의 관계가 이미 같다 — 표는 "지금 얼마"를
정하고, 주문에는 `charge_krw` 가 박혀 있다.

### 5.3 설정은 환경변수가 아니라 DB 다

**환경변수로 두면 안 된다.** 이 저장소의 배포 구조에서 환경변수는 바꾸면
재배포·재기동이 따라온다 — `dev-server-coolify.md` 가 *"변수만 고치고
재배포하지 않으면 아무것도 바뀌지 않는다"* 고 못박고 있다.

**DB 값은 관리자 콘솔에서 바로 고쳐진다.** `plan_quotas` 가 정확히 그
패턴이고, 스키마 주석이 설계 의도까지 적어 두었다 — *"정책을 코드가
아니라 표에 둔다. 관리자 콘솔에서 조정할 수 있고, 그것이 그 테이블의
설계 의도다."*

```sql
-- 유료 저장소(pro)의 델타 SQL. 관리자 콘솔 → 설정관리에서 고친다.
CREATE TABLE IF NOT EXISTS public.sale_settings (
    id              SMALLINT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    fee_percent     NUMERIC(5,2) NOT NULL,   -- 수수료율 (%)
    min_price_krw   INT NOT NULL,            -- 판매가 하한
    max_price_krw   INT NOT NULL,            -- 판매가 상한
    hold_days       INT NOT NULL,            -- 정산 유예 (§5.4)
    min_payout_krw  INT NOT NULL,            -- 최소 정산액 (§5.5)
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_by      TEXT
);
```

**범위는 코드에 두고 서버가 강제한다.** `admin-settings.ts` 의
`PLAN_QUOTA_MIN_MB`·`PLAN_PRICE_MIN_KRW` 와 같은 방식이고, 그 상수들의
주석이 이유를 잘 적어 두었다 — *"오타로 자릿수를 하나 더 치면 디스크가
차기 전까지 아무도 모른다."*

| 값 | 범위 | 왜 |
|---|---|---|
| `fee_percent` | **0 ~ 50** | 사고로 90 을 넣어도 저자가 절반은 받는다 |
| `min_price_krw` | 1,000 이상 | **PG 최소 결제 금액**. 아래로 두면 저장은 되는데 결제창이 거절한다 |
| `hold_days` | 0 ~ 90 | 0 이면 차지백 위험을 전부 우리가 진다 |

`SettingItem.editable` 에 `kind: 'saleFeePercent'` 등을 더하면 콘솔의
화면·저장 경로가 그대로 재사용된다.

### 5.4 정산 유예가 필요하다

이미 저자에게 보낸 뒤 환불·차지백이 나면 회수해야 하는데, **개인에게서
돈을 되받는 것은 사실상 불가능하다.** 그래서 **판매 후 `hold_days` 가
지난 건만** 정산 대상에 넣는다.

§4(구매 = 즉시 다운로드, 이행 완료) 덕분에 **일반 환불은 거의 없다.**
남는 위험은 **카드 도용 차지백**이고, 그건 보통 수십 일 뒤에 온다.
유예를 짧게 잡으면 그 위험을 우리가 떠안는 구조다.

### 5.5 최소 정산액과 이월

4,410원을 매번 이체하면 이체 수수료가 더 크다. **`min_payout_krw` 미만은
다음 회차로 이월**한다. 이월액은 저자 화면에 항상 보여 준다 — 안 보여
주면 "내 돈이 어디 갔나"가 된다.

### 6.2 읽어 낸 규칙

**수수료율은 "우리가 무엇을 해 주는가"에 비례한다.**

```
 8~13%   결제와 전달만 한다 — 손님은 저자가 데려온다
20~30%   마켓에서 발견되게 해 준다 — 우리가 손님을 데려온다
40~60%   제작·마케팅·브랜드까지 얹는다
```

**1단계의 우리는 첫 줄이다.** 저자가 자기 링크로 팔고, 발견 기능(마켓·
검색·추천)은 아직 없다. 그 상태에서 20%를 받으면 **주지 않은 것의 값을
받는 것**이 된다.

### 6.3 권고

> **초기 요율 10%.**

PG 1.8~3% 를 빼면 우리 실질 몫은 **7~8%** 다. 서버·저장소·결제 운영비를
덮되 "결제만 해 주고 많이 뗀다"는 소리는 듣지 않는 자리다.

- **올리기는 쉽고 내리기는 어렵다.** 낮게 시작해 발견 기능을 만든 뒤
  올리는 편이, 높게 시작해 저자가 떠난 뒤 내리는 것보다 낫다
- **Gumroad 방식이 참고가 된다** — 직접 판매 10%, 마켓 노출 30%. 우리도
  나중에 마켓·추천을 만들면 **그 경로로 팔린 건만** 더 받으면 된다.
  `map_sales` 에 유입 경로를 남겨 두면 그때 나눌 수 있다
- 요율은 §5.3 대로 **콘솔에서 바뀐다.** 이 값은 초기값일 뿐이다

### 6.4 ★ 원천징수는 수수료가 아니다 — 화면에서 갈라 보여 준다

사업자 등록이 없는 개인 저자는 **수수료를 뗀 금액의 3.3%가 원천징수**
대상이 될 수 있다(§9 에서 확인 필요 항목으로 다시 다룬다).

```
판매가            4,900원
− 수수료 10%      − 490원
= 정산 기준       4,410원
− 원천징수 3.3%   − 145원
= 실수령         4,265원
```

**두 개를 한 줄로 합쳐 보여 주면 반드시 분쟁이 난다.** 저자가 "10%라며
왜 13%를 뗐냐"고 묻게 된다. 판매 화면과 정산 내역에서 **항상 갈라
보여 준다.**

## 8. 단계 — 무료부터 연다

**1단계: 무료 게시 + 실루엣 미리보기.**
결제·정산 없이 게시를 완성한다. `27-publish-share.md` 에 설계가 이미
있고, §2 의 실루엣과 목차만 얹으면 된다. **법적 부담이 0 이다.**

**2단계: 유료 판매.**
§9 의 확인 항목이 정리된 뒤에 연다.

1단계를 먼저 여는 이유는 순서 때문만이 아니다 — **"사람들이 남의 맵을
보러 오는가"를 먼저 확인할 수 있다.** 아무도 안 보는데 정산 구조부터
만드는 것이 가장 비싼 실수다.

## 9. ★ 확인이 필요한 것 — 코드로 고칠 수 없다

수수료를 떼고 저자에게 정산하는 순간 **중개 플랫폼**이 된다. 아래는
**세무사·변호사 확인 없이 열면 안 되는** 항목이다.

| | 무엇을 확인하나 |
|---|---|
| **통신판매중개업 신고** | 남의 물건을 중개하면 신고 대상인가. "우리는 중개자이며 거래 당사자가 아니다"를 어디에 어떻게 고지하나 |
| **원천징수** | 개인 저자에게 사업소득 3.3% 원천징수 의무가 있나. 있으면 신고·납부는 누가 |
| **예치금 성격** | 저자 몫을 우리 통장에 보관하는 것이 전자금융거래법상 어디에 걸리나 |
| **세금계산서·현금영수증** | 구매자에게 누가 발행하나 — 우리인가 저자인가 |
| **환불 책임 주체** | 중개자인 우리가 지나, 판매자인 저자가 지나 |
| **청약철회 고지** | 구매 즉시 다운로드라 철회가 사실상 불가능하다. 그렇게 제한할 수 있으나 **결제 전에 고지해야** 한다 — 문구와 위치 |

특히 **원천징수는 빠뜨리면 나중에 가산세로 돌아온다.**

> 이 절이 정리되기 전에는 §8 의 2단계를 열지 않는다.

## 10. 아직 정하지 않은 것

- **수수료 초기값** — §6.3 은 10% 를 권고할 뿐이다. 확정은 콘솔에 넣을 때
- **판매가 하한·상한** — 하한은 PG 최소 1,000원이 바닥이다. 상한은 미정
- **정산 유예 일수·주기·최소 정산액** — 차지백이 실제로 언제 오는지
  겪어 봐야 정할 수 있다. 초기에는 보수적으로(길게) 잡는다
- **구매자 워터마크** — 파일에 구매자 정보를 박을지 (§4.4)
- **미리보기 경계** — 지금은 2레벨 고정. 저자가 조정하게 할지
- **저자가 크게 갱신했을 때** — 1회 구매라 구매자는 낡은 판을 들고 있다.
  "할인 재구매 안내" 같은 것이 필요해질 수 있다. **지금 만들 것은 아니고
  나중에 필요해질 자리**로 표시만 해 둔다
- **유입 경로별 요율** — 마켓·추천을 만들면 그 경로만 더 받는 구조
  (§6.3). `map_sales` 에 경로를 남길지는 그때 정한다
- **저자 등급제** — 해피캠퍼스처럼 판매량에 따라 요율을 낮출지. 초기에는
  단일 요율이 맞다
