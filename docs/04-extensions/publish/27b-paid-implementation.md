> [`27a-paid-publish.md`](27a-paid-publish.md) 는 **무엇을·왜**를 정했다

> 시작: 2026-09-19 (사용자 "유료공개 기능 설계부터 시작해줘")

### 0.1 2단계에서 **실제로 만든 것**

- `apps/api/src/publish/trim-for-preview.ts` — **남길 칸만 적는다**(§5.1)
- `GET /published/{id}` 가 유료면 잘라서 + `locked`·`priceKrw`·`stats`
- `og.html` 도 같은 판정 — 네 길이 `openWhere()` 한 줄을 쓴다 (§5.2)
- `map_documents.preview_text` + 2레벨 색인 (§5.3, 아래 바뀐 점)
- `published_maps.price_krw` · `paid_at` + `PATCH …/publish/price`
- 지식창고 카드·목록에 값, 뷰어에 **잠김 띠**(§8.2)
- `PRO_FEATURE_CATALOG` 에 `map-sales` (아래 바뀐 점)

### 0.2 ★ 설계에서 **바꾼 것 둘** — 이유와 함께

**⑴ §5.3 색인 경계를 "절차" 가 아니라 "트리거" 로.**
설계는 *"유료로 내놓는 순간 그 맵의 `search_text` 를 2레벨까지로 다시
만든다"* 였다. 그 방식은 **상태를 바꾸는 절차 하나**에 기대는데, 그 절차가
한 번 빠지면(배포 중 오류 · 직접 UPDATE · 백업 복원) 색인은 전문인 채로
남고 **아무도 모른다.** 대신 `preview_text` 칸을 하나 더 두고 **트리거가 두
색인을 늘 함께** 만든다. 조회하는 쪽이 유료 여부를 보고 고르므로 **어긋날
수 있는 순간이 없다.**

**⑵ §4.2 의 402 스텁 대신 `GET /v1/features`.**
설계는 *"pro 가 안 실렸을 때 코어가 402 를 답한다"* 였다. 그러려면 코어에
`/sales/*` 같은 **유료 경로**가 생기는데, 그것은 `open-core-boundary.md
§4.1`("기능별 경로는 유료 모듈이 자기가 가져온다")을 깨고 유료 기능이 늘
때마다 공개 코어에 커밋을 만든다. 402 로 하려던 일 — *"404 가 '원래 없다'
인지 '못 판다' 인지 구분되게"* — 는 **이미 있는 `/v1/features` 가 한다.**
화면은 거기서 `map-sales` 가 꺼진 것과 **그 이유**를 읽어, 값 칸·구매
단추를 아예 그리지 않거나 이유를 적는다.

### 0.3 ★ (지난 기록) 2단계를 끝냈어도 **아직 아무도 살 수 없다**

> 2026-09-22: 3~6단계로 **저자 쪽은 다 열렸다.** 아래는 2단계 시점의 기록이다.
> 지금 남은 것은 손님의 [구매하기] 화면과 환불이고, 그것은 §12 의 환불 API
> 를 기다린다.

값을 매기는 칸은 `map-sales` 가 켜진 서버에서만 그려진다. 지금은 꺼져
있으므로(pro 가 이 기능을 모른다) **저자에게 보이는 것은 "아직 값을 매길
수 없습니다" 한 줄**이다. 일부러 그렇게 뒀다 — 값만 매겨 두면 저자는
**팔린다고 믿는데 손님에게는 살 길이 없는** 맵이 생긴다(27a §3 이 경고한
자리). 코어가 하는 일은 **자르는 것**이고, 파는 것은 3단계다.


### 2.1 ★ 경계를 여기에 긋는 이유

27a §7.1 이 이미 말했다 — **자르는 쪽이 코어에 있어야 안전하게 실패한다.**
유료 모듈이 안 실린 공개판에서 유료 맵을 열면 *"전문이 새는 것이 아니라
미리보기만 나오는"* 것이 옳다. 반대로 두면 **유료 모듈이 빠진 순간 전부
공개된다.**

그 규칙을 이 문서의 표로 옮기면 이렇게 된다.

| 코어가 아는 것 | 코어가 **모르는 것** |
|---|---|
| 이 맵이 `visibility='paid'` 다 | 누가 샀나 |
| 그래서 **2레벨까지만** 내보낸다 | 얼마를 벌었나 · 수수료 · 저자 몫 |
| 값이 얼마인지(화면에 적을 숫자) | 결제가 성공했나 |

**값(가격)은 코어에 둔다** (§3.1). 비밀이 아니라 **손님에게 보여 줘야 하는
숫자**이고, 지식창고 목록(코어 API)이 그것을 그린다. 코어가 몰라야 하는
것은 가격이 아니라 **거래**다.

## 3. 데이터 모델

### 3.1 코어 — `published_maps` 에 칸 **둘**을 더한다

```sql
-- 코어 델타. 더하는 변경이라 기존 데이터가 지워지지 않는다.
ALTER TABLE public.published_maps
  ADD COLUMN IF NOT EXISTS price_krw INT,          -- NULL = 무료
  ADD COLUMN IF NOT EXISTS paid_at   TIMESTAMPTZ;  -- 유료로 내놓은 시각
```

| 칸 | 왜 코어인가 |
|---|---|
| `price_krw` | 지식창고 목록·미리보기 화면이 그린다. **보여 주려고 있는 숫자**다 |
| `paid_at` | "언제부터 유료였나" — 무료↔유료를 오간 맵의 이력 판정에 쓴다 |

**수수료율·저자몫은 코어에 두지 않는다.** 그것은 거래의 값이라 `map_sales`
(pro)에만 있다 — 27a §5.2 의 "요율은 설정값이고 판매는 박제다" 가 그대로다.

> ★ `visibility='paid'` 는 **이미 코어 enum 에 있다**
> (`publish.service.ts`). 지금은 `assertUsable` 이 400 으로 막는다. 여는
> 자리는 그 한 줄이다 — 다만 **열기 전에 §5 의 자르기가 먼저 있어야 한다.**
> 순서를 뒤집으면 유료 맵의 전문이 그대로 열린다.

### 3.2 pro — 표 다섯

> ★ **실제 이름은 전부 `sale_` 로 시작한다** (2026-09-21 구현). 유료 모듈의
> `CLAUDE.md` §1.2 가 "표 이름은 접두사로 갈라 둔다 — 한 DB 에 코어 표와
> 섞이므로 **이름만 보고 소유자를 알 수 있어야** 한다" 고 정해 두었고, 그
> 규칙이 이 문서의 이름보다 우선한다.
>
> | 이 문서 | 실제 |
> |---|---|
> | `map_sales` | `sale_orders` |
> | `purchase_claims` | `sale_claims` |
> | `payouts` | `sale_payouts` |
> | `author_payout_accounts` | `sale_accounts` |
> | `sale_settings` | `sale_settings` (그대로) |

```sql
-- ① 판매 1건. **두 정산 모드에서 모양이 같다** (§6).
CREATE TABLE map_sales (
    id               UUID PRIMARY KEY,
    publish_id       TEXT NOT NULL,          -- 코어의 published_maps
    map_id           UUID NOT NULL,
    author_user_id   UUID NOT NULL,          -- 단독맵뿐이라 **한 사람**이다 (27a §5.0)
    buyer_user_id    UUID,                   -- ★ 비로그인 구매면 NULL (§7)
    buyer_email      TEXT NOT NULL,          -- 영수증·재다운로드 안내가 갈 곳
    price_krw        INT  NOT NULL,          -- 판매 시점 값 — **박제**
    fee_percent      NUMERIC(5,2) NOT NULL,  -- 판매 시점 요율 — **박제**
    fee_krw          INT  NOT NULL,          -- 계산 결과까지 남긴다
    author_krw       INT  NOT NULL,
    status           TEXT NOT NULL,          -- pending/paid/refunded/failed
    pg_payment_key   TEXT,
    downloaded_at    TIMESTAMPTZ,            -- ★ 환불 판정의 기준 (§8.2)
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    paid_at          TIMESTAMPTZ,
    refunded_at      TIMESTAMPTZ
);

-- ② 비로그인 구매의 **열쇠** (§7)
CREATE TABLE purchase_claims (
    token        TEXT PRIMARY KEY,           -- 긴 난수. 이것이 곧 열쇠다
    sale_id      UUID NOT NULL REFERENCES map_sales(id),
    expires_at   TIMESTAMPTZ NOT NULL,       -- 계정에 붙기 전까지만 산다
    claimed_at   TIMESTAMPTZ,
    claimed_by   UUID
);

-- ③ 정산 1건 — **모드 A 에서만 쓴다** (§6)
CREATE TABLE payouts (
    id             UUID PRIMARY KEY,
    author_user_id UUID NOT NULL,
    period_from    DATE NOT NULL,
    period_to      DATE NOT NULL,
    gross_krw      INT  NOT NULL,   -- 저자몫 합계
    withheld_krw   INT  NOT NULL,   -- 원천징수 (27a §6.4 — 수수료와 **갈라** 적는다)
    net_krw        INT  NOT NULL,
    carried_krw    INT  NOT NULL,   -- 최소 정산액 미만 이월 (27a §5.5)
    status         TEXT NOT NULL,   -- ready/sent/failed
    sent_at        TIMESTAMPTZ
);

-- ④ 저자의 받을 자리 — **두 모드 공통**
CREATE TABLE author_payout_accounts (
    user_id     UUID PRIMARY KEY,
    mode        TEXT NOT NULL,   -- 'bank'(모드 A) | 'pg_submall'(모드 B)
    status      TEXT NOT NULL,   -- none/pending/ready/rejected
    ref         TEXT,            -- 하위상점 ID 또는 계좌 참조(원문은 두지 않는다)
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- ⑤ 설정 — 27a §5.3 그대로. 관리자 콘솔에서 고친다
CREATE TABLE sale_settings ( ... 27a §5.3 ... );
```

> ★ **`pay_orders` 는 손대지 않는다** (27a §5.1). 그것은 *우리* 매출
> (요금제 판매)이다. 중개 판매는 위에 얹는다.

### 3.3 ★ 왜 `map_sales.buyer_user_id` 가 **NULL 을 허용**하나

사용자가 "비로그인 구매 후 계정 연결" 을 골랐기 때문이다. 처음에는 **이메일
하나뿐인 구매**가 존재한다. 여기에 NOT NULL 을 걸면 "손님 계정"을 유령으로
만들게 되고, 나중에 진짜 계정과 합치는 일이 생긴다 — 그 병합이 정확히
우리가 피하고 싶은 종류의 작업이다(§7.3).

## 4. API — 무엇이 새로 생기나

경로 표기는 27-publish-share §10 을 따른다(브라우저는 `/p/{id}`, API 는
`/published/{id}`).

### 4.1 코어

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| `PATCH` | `/maps/{id}/publish/price` | 값 매기기·내리기 (`price_krw` · `visibility`) |
| `GET` | `/published/{id}` | **유료면 잘라서** 준다 (§5) + `price`·`locked:true` |
| `GET` | `/published` | 목록에 `priceKrw` 를 실어 준다 |

### 4.2 pro

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| `POST` | `/published/{id}/checkout` | 결제 시작 — 로그인/비로그인 모두 |
| `POST` | `/sales/confirm` | PG 승인 콜백 → `map_sales.status='paid'` |
| `POST` | `/sales/{token}/file` | ★ **전문**. 토큰을 본문으로 받는다(§7.2) |
| `POST` | `/sales/{token}/claim` | 비로그인 구매를 **내 계정에 붙인다** |
| `GET` | `/me/purchases` | 내 구매 목록 — 다시 받기 |
| `GET` | `/me/sales` | 저자의 판매·정산 내역 (수수료·원천징수 **갈라서**) |
| `POST` | `/sales/{id}/refund` | 환불 (§8.2 — 다운로드 전이면 전액) |

**6단계에서 더해진 저자 경로** (2026-09-22)

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| `GET` | `/me/sales/ready` | 값을 매길 수 있나 + **왜** + `rates`(요율·값 범위) |
| `GET` · `POST` | `/me/sales/account` | 정산받을 계좌 — 예금주·은행만 (번호는 받지 않는다) |

★ `ready` 가 **요율까지 주는 이유**: 값 칸 옆에 수수료·원천징수·받는 금액을
갈라 적으려면 화면이 요율을 알아야 하는데, 요율은 관리자가 바꾸는 값이라
화면에 박아 두면 **어긋난 쪽이 저자에게 보이는 숫자**가 된다. 설정을 못
읽으면 `rates: null` 로 주고 **화면은 금액을 적지 않는다** — 모르는 숫자는
적지 않는다.

~~**pro 가 안 실렸을 때** 코어는 이 경로들에 **402** 를 답하고 이유를 적는다.~~

★ **2026-09-21 구현에서 바꿨다** (§0.2 ⑵) — 코어에 유료 경로를 뚫지
않는다. 402 로 하려던 일은 **이미 있는 `GET /v1/features` 가 한다**:
`map-sales` 가 꺼져 있는 것과 **그 이유**를 화면이 읽어, 값 칸·구매 단추를
아예 그리지 않거나 이유를 적는다. 유료 경로는 유료 모듈이 자기가 가져온다
(`open-core-boundary.md` §4.1).

## 5. ★ 코어가 하는 일 — **서버가 자른다**

27a §3 이 설계에서 가장 중요하다고 한 자리다. 구현 단위로 내리면 셋이다.

### 5.1 `trimForPreview(doc, depth = 2)`

중심(root) + 1레벨 + 2레벨까지만 남기고 **그 아래는 아예 지운다.**

같이 지우는 것이 있다 — **노트·첨부·링크**다. 2레벨 노드에 달린 노트 안에
본문이 통째로 들어 있는 맵이 흔하다. 깊이만 보고 자르면 **잘라 낸 줄 알고
전문을 내보낸다.** 이 한 줄이 이 함수에서 가장 틀리기 쉬운 자리다.

```
남긴다   노드 텍스트 · 색 · 모양 · 레이아웃 · 형제 순서
지운다   3레벨 이하 전부 · 모든 노트 · 첨부 · 링크 · 이미지 원본
숫자만   전체 노드 수 · 최대 깊이 · 첨부 개수 (서버가 세어 숫자로)
```

### 5.2 ★ 같은 판정을 쓰는 자리가 **넷**이다

`getPublished` 만 고치면 샌다. 퍼블리싱된 맵의 내용은 **네 길**로 나간다.

| 길 | 유료일 때 |
|---|---|
| `GET /published/{id}` | 잘라서 |
| `GET /published/{id}/og.html` | 제목·소개만 (지금도 그렇다 — 그대로면 된다) |
| `GET /published/{id}/preview.png` | 실루엣은 **글자가 없다**(27a §2.1) — 그대로 |
| **지식창고 검색 `?q=`** | §5.3 |

### 5.3 ★ 검색 색인도 **2레벨까지만** (이번에 찾은 자리)

지식창고 검색은 맵 **내용**을 뒤진다(`map_documents.search_text`, 2026-09-17).
유료 맵을 그대로 색인하면 내용 자체는 안 나가도 **"이 맵 안에 그 말이
있다"는 사실**이 `내용 12건` 으로 샌다. 사지 않은 사람이 검색어를 바꿔 가며
두드리면 잘라 낸 부분을 **스무고개로 확인**할 수 있다.

> ~~**유료로 내놓는 순간 그 맵의 `search_text` 를 2레벨까지로 다시 만든다.**~~
>
> ★ **2026-09-21 구현에서 바꿨다** (§0.2 ⑴) — 절차에 기대지 않는다.
> `map_documents.preview_text` 칸을 하나 더 두고 **트리거가 두 색인을 늘
> 함께** 만든다. 조회하는 쪽이 유료 여부를 보고 고르므로 **어긋날 수 있는
> 순간이 없다.** 그 칸이 없는 서버에서는 유료 맵을 내용 검색에서 아예 뺀다
> (전문으로 되돌리지 않는다).

잃는 것은 "유료 맵이 깊은 검색어로는 안 잡힌다" 인데, **제목·2레벨 제목은
잡히므로 발견 자체는 된다.** 파는 물건의 목차가 검색되는 것과 같다.

## 6. ★ 판매 처리기 — `map_sales` 까지는 한 벌, **정산부터 갈린다**

사용자가 "둘 다 되게 추상화" 를 골랐다. 추상화의 **경계선을 어디에 긋느냐**
가 전부다. 두 모드를 나란히 놓으면 답이 보인다.

| | 모드 A — 우리가 받아 정산 | 모드 B — PG 하위상점 |
|---|---|---|
| 돈이 들어오는 곳 | **우리 통장** | PG 가 저자에게 직접 |
| `map_sales` | 필요 | **필요 (같은 모양)** |
| `payouts` | 필요 | **불필요** — PG 가 한다 |
| 예치금·원천징수 | **우리 책임** | PG 쪽으로 넘어간다 |
| 저자 진입 | 가입만 | **PG 하위상점 등록(실명·계좌)** 이 먼저 |

**같은 것이 `map_sales` 까지고, 다른 것은 그 뒤다.** 그래서 인터페이스를
"결제"가 아니라 **"판매 이후"** 에 맞춰 자른다.

```ts
interface SalesProvider {
  readonly settlementMode: 'we-hold' | 'pg-submall';

  /** 값 계산 — 수수료·저자몫. 두 모드가 같다 */
  quote(priceKrw: number): { feeKrw: number; authorKrw: number };

  /** 결제 시작 — 돌려보낼 주소나 결제 키 */
  checkout(sale: SaleDraft): Promise<{ redirectUrl?: string; paymentKey?: string }>;

  /** 승인 확인 — 여기까지 오면 map_sales 가 'paid' 다 */
  confirm(paymentKey: string): Promise<{ ok: boolean; pgRef: string }>;

  refund(saleId: string, reason: string): Promise<void>;

  /** ★ 모드 A 에서만 구현한다. 모드 B 는 던지지 않고 **아무것도 안 한다** */
  settle?(period: { from: Date; to: Date }): Promise<PayoutResult[]>;

  /** 저자가 팔 수 있는 상태인가 — 모드 B 는 하위상점 등록을 본다 */
  authorReady(userId: string): Promise<{ ready: boolean; reason?: string }>;
}
```

`settle` 를 **선택(optional)으로 두는 것**이 핵심이다. "모드 B 에서는
정산이 없다" 를 *빈 구현*으로 흉내 내면, 나중에 정산 화면이 빈 표를 그리며
"정산이 0건" 이라고 말하게 된다 — **없는 것과 0건은 다르다.** 화면은
`settlementMode` 를 보고 **정산 탭 자체를 그리지 않는다.**

> ★ **추상화는 여기까지다.** "어떤 PG 든 갈아 끼울 수 있게" 까지 파고들지
> 않는다 — **쓸 일이 올지 모르는 유연성**은 값만 치르고 검증되지 않는다.
> 지금 필요한 것은 "A 와 B 중 어느 쪽으로 가도 `map_sales` 를 다시 짜지
> 않는 것" 하나이고, 그 하나는 §11 의 확인이 끝나면 **반드시** 필요해진다.

## 7. ★ 비로그인 구매 → 계정 연결

사용자가 고른 길이다. 전환은 가장 좋지만 **틀리면 남의 구매를 여는 길**이라
가장 조심할 자리다.

### 7.1 흐름

```
① 지식창고에서 유료 맵 → [구매]  (로그인 안 해도 된다)
② 이메일 입력 → 결제
③ 승인되면  map_sales(buyer_user_id = NULL, buyer_email = 그 주소)
           purchase_claims(token = 긴 난수, expires_at = +30일)
④ 완료 화면에서 **바로 내려받는다** + 같은 링크를 이메일로도 보낸다
⑤ 그 화면에 [내 계정에 저장] — 로그인/가입하면 buyer_user_id 가 채워진다
   → 그때부터 토큰이 없어도 [내 구매] 에서 다시 받는다
```

### 7.2 ★ 토큰은 **주소에 싣지 않는다**

`GET /sales/{token}/file` 로 두면 토큰이 **주소창·referrer·서버 로그**에
남는다. 받은 파일을 여는 순간 그 페이지가 남의 사이트로 referrer 를 보내면
**그 토큰으로 누구나 같은 파일을 받는다.**

- 다운로드는 **`POST`** 로 받고 토큰은 **본문**에 싣는다.
- 완료 화면 자체에는 `Referrer-Policy: no-referrer` 를 건다.
- 이메일 링크는 `/purchase?c=…` 같은 **1회 교환용 짧은 코드**로 보내고,
  그 화면이 코드를 진짜 토큰으로 바꾼다.

### 7.3 같은 이메일로 나중에 가입하면?

**자동으로 붙이지 않는다** — 단, **검증된** 이메일이면 붙인다. 검증 없이
붙이면 "남의 이메일을 적고 가입해 그 사람의 구매를 가져가는" 길이 열린다.

★ **구현에서 확정된 자리** (2026-09-21, pro-e2e27):

- 검증 판정은 `public.users.email_verified_at IS NOT NULL` 이다. 이메일
  자체는 `auth.users`(GoTrue)에 있으므로 **두 표를 조인**한다 — 처음에
  `public.users.email` 을 읽었다가 **그 칸이 없어서** 잡혔다.
- **검증은 "저절로 붙는 것" 의 조건이지 권한의 조건이 아니다.** 열쇠를
  가지고 있으면 검증 전이어도 붙는다 — 열쇠가 그 자체로 증명이다.
- 자동 연결은 **`[내 구매]` 를 열 때** 일어난다. 화면이 따로 부를 자리를
  두면 부르는 것을 잊었을 때 사용자는 *"분명히 샀는데 없다"* 를 보게 되고,
  그 사이 열쇠가 만료되면 되돌릴 방법이 없다.
- **이미 남에게 붙은 구매는 거절한다**(409). 조용히 성공시키면 토큰을
  주운 사람이 "붙였다" 는 답을 받고 자기 목록에 없는 이유를 모른다.

**되돌려 깨뜨려 확인했다** — 검증 조건을 빼면 검증 안 된 계정이 남의
구매를 실제로 가져간다.

## 8. 화면

### 8.1 저자 — 퍼블리싱 대화상자에 한 줄

지금 `[🔗 링크 공개] · [📚 지식창고에 올린다]` 가 있는 자리에 **값**이 붙는다.

```
📚 지식창고에 올린다
   ◉ 무료공개        ○ 유료공개  [ 4,900 ]원
                                  ─────────────────────
                                  수수료 10%       −490원
                                  원천징수 3.3%    −145원   ← **갈라서** 적는다
                                  받으시는 금액   4,265원
```

27a §6.4 그대로 — 수수료와 원천징수를 **한 줄로 합치지 않는다.** 합치면
저자가 "10%라며 왜 13%를 뗐냐" 고 묻게 되고, 그 물음은 정당하다.

모드 B 라면 값을 매기기 전에 **[판매자 등록]** 이 먼저다
(`authorReady()` 가 false 면 값 칸을 잠그고 그 이유를 적는다).

#### 8.1.1 ★ 6단계에서 **실제로 만든 것** (2026-09-22)

**모드 A 에서도 "등록이 먼저" 는 그대로다** — 다만 등록하는 것이 하위상점이
아니라 **정산받을 계좌**다. 보낼 곳이 없으면 판 돈을 들고만 있게 된다.

```
💰 유료공개 — 값을 매기면 팝니다
   [ 4900 ]원  [값 매기기]      ← 계좌가 확인되기 전에는 **칸이 잠긴다**
   ┌────────────────────────────┐
   │ 손님이 내는 값      4,900원 │
   │ 중개 수수료 10%      −490원 │   ← 갈라서 (27a §6.4)
   │ 원천징수 3.3%(정산할 때) −145원 │
   │ 받으시는 금액      4,265원 │
   └────────────────────────────┘   ← `ProSalesGate` 가 그린다
```

지킨 것 넷.

- **기본이 잠김이다.** 유료 모듈이 "받을 준비가 됐다" 고 답해야 풀린다.
  답을 못 얻었을 때도(서버 오류) 잠근 채로 둔다 — 값을 매겨 두고 팔리지
  않는 것보다 **잠깐 기다리는 쪽**이 싸다.
- **[값을 내리고 무료공개로] 는 잠그지 않는다.** 계좌가 나중에 반려된
  저자까지 잠그면, 팔리지도 내려지지도 않는 맵이 남는다.
- **화면만 잠그지 않는다.** `checkout` 이 **같은 판정을 다시** 한다 —
  화면을 거치지 않는 요청이 그대로 들어오기 때문이다. 손님에게는 저자의
  계좌 사정을 말하지 않고 *"저자의 정산 준비가 끝나지 않아 지금은 살 수
  없습니다"* 까지만 답한다.
- **금액은 원장이 쓰는 `money.ts` 를 그대로 불러 쓴다.** 화면이 따로
  계산하면, 화면과 원장이 다른 숫자를 말하는 날이 온다.

#### 8.1.2 계정 메뉴 ▸ 💰 판매·정산 (2026-09-22)

한 창에 넷을 둔다 — **정산 계좌 · 아직 받지 않은 금액 · 판매 내역 · 정산
회차**. 갈라 두면 저자는 "내 돈이 지금 어디 있나" 를 네 군데서 맞춰 봐야
한다.

- 계좌는 **예금주·은행만** 받는다. 송금은 사람이 은행에서 하므로 번호로
  우리가 자동으로 할 일이 없고, 원문을 두면 **지켜야 할 비밀만 하나 더**
  생긴다. 번호는 확인할 때 따로 여쭙는다(§11).
- **"아직 받지 않은 금액" 을 숫자로 보여 준다** — 최소 정산액에 못 미쳐
  넘어간 저자가 *"왜 이번 달에 안 들어왔나"* 를 묻기 **전에** 화면이 답해야
  한다. 환불 기간(`hold_days`)·최소 정산액·원천징수율을 함께 적는다.
- 계좌를 **다시 등록하면 다시 확인 대기**이고, 그 사이에는 이미 값을 매긴
  맵도 팔리지 않는다. 그래서 누르기 전에 그 사실을 적는다.
- 정산이 없는 방식(모드 B)이면 **정산 칸 자체를 그리지 않는다** — 빈 표는
  "정산이 0건" 이라고 말하는 셈인데, **없는 것과 0건은 다르다.**

### 8.2 구매자 — 잘린 미리보기 + 구매

```
[실루엣 이미지]   ← 글자가 없다. 규모·구조만 전한다
목차 (2레벨까지)  ← 무엇에 대한 맵인가
166 노드 · 최대 7단계 · 첨부 3개   ← 서버가 센 숫자
────────────────────────
4,900원  [구매하기]
· 구매 즉시 파일을 내려받습니다 (HTML · md · 이미지)
· 산 맵은 내 에디터로 불러와 고쳐 쓸 수 있습니다
· 다운로드 전에는 전액 환불됩니다   ← ★ 아래
```

★ **"다운로드 전에는 전액 환불"** 은 우리가 인심을 쓰는 것이 아니라
**법이 요구하는 자리를 정확히 지키는 것**이다. 디지털 콘텐츠는 제공이
시작되면 청약철회를 제한할 수 있지만, **시작 전에는 제한할 수 없다.**
`map_sales.downloaded_at` 이 그 경계를 기록한다 — 그래서 그 칸이 §3.2 에
있다. (제한 고지의 문구·위치는 27a §9 의 확인 항목이다.)

### 8.3 관리자 콘솔 — 설정관리에 넷

`fee_percent` · `min_price_krw` · `max_price_krw` · `hold_days` ·
`min_payout_krw`. `SettingItem.editable` 에 종류만 더하면 화면·저장 경로가
그대로 재사용된다(27a §5.3).

**상한이 왜 필요한가** — 없으면 저자가 자릿수를 하나 더 쳐서 `49,000,000원`
짜리 맵이 지식창고 첫 줄에 걸린다. 권고: **1,000 ~ 100,000원.**

| **6** | **저자 화면** — 값 칸 잠금·셈 · 계좌 · 판매·정산 창 (§8.1.1·§8.1.2) | ✅ 2026-09-22 — **e2e304 28항목**(실 브라우저) · **pro-e2e29 28항목**, 되돌려 깨뜨리기 2 |
| **7** | 손님 화면 — [구매하기] · 환불 | ⏸ 환불 API 를 기다린다 (§12) |

**2단계를 1단계보다 먼저 하지 않는다.** 확인 결과가 "못 판다" 로 나와도
2단계는 버려지지 않지만(자르기는 그 자체로 옳다), **순서를 지키는 편이
우리가 무엇을 기다리는지 잊지 않는 길**이다.

### 10.2 ★ 5단계에서 확정된 것 (2026-09-22)

**정산은 "보내는 일" 이 아니라 "고정하는 일" 이다.** 실제 송금은 사람이
은행에서 한다. `settle()` 이 하는 것은 누구에게 얼마를 보내야 하는지
계산해 원장에 박제하고, 그 판매들이 **다음 회차에 다시 세어지지 않게**
묶는 것이다.

거르는 순서와 이유:

| | 왜 |
|---|---|
| 환불 기간(`hold_days`)이 지난 것만 | 지나기 전에 보내면, 환불이 들어왔을 때 **이미 나간 돈을 돌려받아야** 한다 |
| 계좌가 확인된 저자만 | 보낼 곳이 없는 정산은 장부에만 있다 |
| 최소 정산액 이상만 | 못 미치면 **행을 만들지 않는다** — 다음 회차에 저절로 합쳐진다 |

★ **`payouts.carried_krw` 를 쓰지 않는다** (§3.2 ③ 의 그 칸, 항상 0).
이월은 **원장이 스스로 들고 있다** — `payout_id IS NULL` 인 판매가 곧
이월분이다. 별도 칸에 또 적으면 **두 곳이 어긋날 수 있고**, 어긋난 쪽이
어느 쪽인지 나중에 알 방법이 없다. 이월 금액은 회차의 **결과**로만
보고한다(화면이 "얼마가 넘어갔다" 를 그린다).

★ **두 겹으로 막고, 두 겹이 다 필요하다.** 후보를 고를 때
`payout_id IS NULL`, 묶을 때 **한 번 더** 같은 조건 + 건수가 안 맞으면
통째로 롤백. 되돌려 깨뜨려 보니 **한 겹만 빼면 DB 쪽이 잡아내고, 두 겹을
빼면 같은 45,000원이 5번 정산된다.**

★ **관리자 판정을 코어에서 가져오지 않는다.** 코어 `AdminGuard` 를
import 하면 유료 모듈이 코어 내부 구조에 묶인다. 코어의 관리자 표는
자기서술형(`base64url(email).exp.HMAC`)이고 키·명단이 같은 서버의
환경변수라, 유료 모듈이 **같은 규칙을 다시 쓴다**(`userFromRequest` 와
같은 해법). 명단에서 빠진 사람의 표가 그 순간 무효라는 것까지 같다.

★ **저자 화면은 "아직 못 받은 돈" 을 숫자로 보여 준다.** 최소 정산액에
못 미쳐 넘어간 저자가 *"왜 이번 달에 안 들어왔나"* 를 **묻기 전에** 화면이
답해야 한다.

### 10.1 ★ 모드 A 로 정해졌다 (2026-09-21)

§6 의 두 모드 중 하나를 골라야 pro 의 표(`payouts`)와 저자 진입 흐름이
정해진다. 이것은 **돈의 흐름과 법적 책임**이라 우리가 고를 것이 아니다.

지금 아는 사실은 이렇다.

- pro 저장소에 **사이다페이 클라이언트가 이미 있다**(`src/pay/ciderpay.client.ts`
  · `docs/pg-ciderpay.md`). 요금제 결제(`pay_orders`)용으로 만든 것이다.
- 그 연동에는 **하위상점(submall) 이야기가 없다.** 돈은 우리 가맹점으로
  들어온다 — 즉 지금 있는 배관은 **모드 A** 의 모양이다.
- 모드 B 로 가려면 사이다페이에 **하위상점 기능이 있는지**, 있다면 계약에
  포함돼 있는지를 확인해야 한다.

> 사용자가 **모드 A** 를 골랐다. 그래서 저자 몫을 **우리가 잠시 보관**한다 —
> 27a §9 의 "예치금 성격" 이 여기 걸리고, 그 확인은 끝났다고 하셨다.
>
> 구현에 그대로 내려온 것이 둘이다.
>
> - **저자는 정산 계좌를 먼저 등록해야 판다** (`sale_accounts.status='ready'`).
>   보낼 곳이 없는데 팔게 두면, 못 보낸다는 사실을 **저자가 물건을 내준
>   뒤에** 알게 된다.
> - **수수료와 원천징수를 갈라 적는다** (27a §6.4). 합치면 저자가 "10%라며
>   왜 13%를 뗐냐" 고 묻게 되고, 그 물음은 정당하다.

## 11. 사용자가 해야 하는 것 — 코드로 못 한다

| 무엇 | 왜 우리가 못 하나 |
|---|---|
| 27a §9 의 여섯 확인 | 세무사·변호사의 판단이다 |
| **PG 계약** | ✅ 사이다페이 (2026-09-21). 모드 A 라 하위상점은 필요 없다 |
| ★ **사이다페이의 결제-후 취소 API** | 문서에 없다 — 엔드포인트·파라미터를 받아야 환불을 붙인다 (§12) |
| ★ **저자 정산 계좌 확인** | `sale_accounts.status` 를 `ready` 로 바꾸는 것은 **사람의 확인**이다. 경로는 5단계에서 생겼다(`PATCH /v1/admin/sales/accounts/{userId}`) — 누르는 것은 사람이다 |
| ★ **계좌번호를 어디서 받나** | 우리는 **예금주·은행만** 갖는다(원문을 두면 지켜야 할 비밀만 는다). 실제 계좌번호는 확인할 때 따로 받아 송금하는 사람이 쓴다 — 그 절차는 사람 몫이다 |
| ★ **정산 회차를 언제 돌리나** | 자동 주기를 두지 않았다. 돈을 내보내는 일은 **누군가 누른 결과**여야 하고, "언제 무엇이 나갔나" 에 "설정된 주기에 저절로" 보다 나은 답이 있어야 한다 |
| 통신판매중개업 신고 | 신고 주체가 사업자다 |
| 수수료 초기값 확정 | 27a §6.3 은 10% 를 **권고**할 뿐이다 |

★ **6단계 뒤 사용자 절차가 하나 분명해졌다** (2026-09-22). 저자가 계좌를
등록하면 `sale_accounts.status='pending'` 이 되고, **그 상태에서는 저자가
값을 매길 수 없고 이미 값이 매겨진 맵도 팔리지 않는다.** 그러니 확인을
미루면 그동안 가게가 닫혀 있는 셈이다 — 확인은 **예금주·은행을 보고
계좌번호를 따로 받은 뒤** `PATCH /v1/admin/sales/accounts/{userId}` 로
`ready` 를 주면 된다. 반려할 때는 **이유를 반드시 적는다**(서버가 막는다) —
저자 화면에 그 문장이 그대로 보이고, 저자는 그것을 읽고 다시 등록한다.

> **pro 저장소가 이 세션에 열려 있지 않다.** §3.2·§6 의 표와 코드는
> `okpojung/easymindmap-pro` 몫이라, 만들 때가 되면 그 저장소를 열어 줘야
> 한다. 코어 쪽(§9 표의 위 넷)은 지금 저장소에서 할 수 있다.

## 12. 아직 정하지 않은 것

**여기가 살아 있는 목록이다** — 27a §10 은 2026-09-05 의 기록으로 그대로
두고, 이 문서가 답한 것(정산 구조 · 구매자 계정 · 값의 자리 · 미리보기
경계의 구현)은 아래에서 뺐다.

- **모드 A / B** — §11 의 확인 결과로 정해진다
- **미리보기 깊이** — 2레벨 고정으로 시작. 저자가 조정하게 할지는 나중
- **구매자 워터마크** — 파일에 구매자 정보를 박을지 (27a §4.4)
- **낡은 판을 든 구매자** — 저자가 크게 갱신했을 때의 재구매 안내
- **유입 경로별 요율** — 마켓·추천을 만들면 (27a §6.3)
- **환불 기한** — "다운로드 전" 말고 시간 기한도 둘지
- ★ **이메일 링크의 1회 교환용 짧은 코드** (§7.2 ③) — 아직 없다. 메일
  발송이 붙을 때 함께 만든다. 지금은 완료 화면에서 바로 받거나,
  `[내 계정에 저장]` 으로 붙여 두는 두 길이 있다.
- ★ **환불의 PG 호출** (2026-09-21에 생긴 것) — 사이다페이의 **결제-후
  취소 엔드포인트가 우리 문서에 없다**(`pay_orders` 도 결제-**전** 취소만
  쓴다). 돈이 움직이는 호출을 추측해 쓰지 않았다. 원장 쪽은 준비돼 있다
  (`sale_orders.status='refunded'` · `downloaded_at` 이 청약철회 경계) —
  **엔드포인트와 파라미터를 받으면 붙이는 일만 남는다.**
  → 사용자가 사이다페이에서 받아야 하는 것 (§11)
