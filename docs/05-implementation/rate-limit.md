# 레이트 리밋 (Rate Limit) — 왜 필요하고 무엇을 하는가

* 문서 버전: v1.0
* 작성일: 2026-08-08
* 대상: **처음 접하는 사람** — 배경 지식 없이 읽을 수 있게 썼다
* 구현: `apps/api/src/common/rate-limit/rate-limit.guard.ts`
* 관련: [`env-spec.md`](env-spec.md) · [`backlog.md` B14](../00-project-overview/backlog.md)

---

## 1. 한 줄 요약

**레이트 리밋 = "한 사람이 정해진 시간 안에 서버를 부를 수 있는 최대 횟수".**

우리 설정은 **60초에 600번**이다. 그 이상 부르면 서버가 잠깐 `429` 라고
답하고 요청을 처리하지 않는다.

여기서 "부른다"는 **브라우저가 우리 API 서버에 보내는 네트워크 요청**을
말한다. **다크모드 전환·줌·노드 편집 같은 화면 조작은 서버를 안 부르므로
0번**이다 — 무엇이 세고 무엇이 안 세는지는 **§4.5** 에 표로 정리했다.

---

## 2. 왜 필요한가 — 없으면 무슨 일이 생기나

### 2.1 서버는 무한하지 않다

우리 API 는 요청 하나마다 **DB 를 조회하고, 파일을 읽고, 메모리를 쓴다.**
동시에 감당할 수 있는 양에 한계가 있다.

정상 사용자는 이 한계 근처에도 못 간다. 사람이 마우스로 클릭하는 속도는
1초에 몇 번이 고작이다. **문제는 사람이 아니라 프로그램이다.**

```
사람:      "저장" 클릭 → 요청 1번           (1분에 몇 번)
스크립트:  while(true) { 요청 }             (1초에 수천 번)
```

### 2.2 없으면 이런 일이 실제로 생긴다

| 상황 | 무슨 일이 벌어지나 |
|---|---|
| **누군가 장난으로 반복 호출** | 서버가 그 요청을 처리하느라 **정상 사용자가 느려지거나 아예 못 쓴다** |
| **비밀번호 무차별 대입** | 로그인을 초당 수천 번 시도해 비밀번호를 맞힌다. 한 번에 3번씩만 시도할 수 있으면 사실상 불가능해진다 |
| **내 코드의 버그** | 프런트엔드에 무한 루프가 생기면 **우리 앱이 우리 서버를 공격한다.** 실제로 흔하다 |
| **크롤러·봇** | 검색엔진이 아닌 잡다한 스캐너가 하루 종일 두드린다 (이 저장소의 nginx 로그에도 `/admin/.env` 를 찾는 스캐너가 실제로 찍혀 있다) |
| **비용** | 클라우드는 트래픽·CPU 만큼 돈을 낸다. 막지 않으면 **요금이 그대로 늘어난다** |

> **핵심**: 레이트 리밋은 "나쁜 사람"만 막는 장치가 아니다. **내 실수와
> 남의 버그로부터 서버를 지키는 안전장치**에 더 가깝다.

### 2.3 비유

건물 엘리베이터의 **정원 표시**와 같다.

* 정원을 넘겨 타면 엘리베이터가 안 움직인다 → 몇 명이 내리고 다음에 탄다
* 정원이 없으면? 한 번에 다 타려다 **줄이 끊어져 전부 못 쓴다**
* 평소에 정원을 신경 쓰는 사람은 없다 — **넘길 일이 없기 때문이다**

레이트 리밋도 같다. **정상 사용자는 있는 줄도 모른다.**

## 3. 어떻게 동작하나 — 그림으로

서버는 **"누가 몇 번 불렀는지" 세는 바구니**를 사람마다 하나씩 둔다.

```
        ┌───────────── 60초 창(window) ─────────────┐
사용자A │ ●●●●●●●●●●  (10번)                        │  → 통과 (600번 중 10번)
사용자B │ ●●●●●●●●●●●●●●● … ●●●  (600번)           │  → 601번째부터 429
        └───────────────────────────────────────────┘
                    ↑ 60초가 지나면 바구니를 비운다
```

1. 요청이 오면 **그 사람의 바구니에 구슬을 하나 넣는다**
2. 구슬이 **600개를 넘으면** 그 요청을 처리하지 않고 `429` 로 돌려보낸다
3. **60초가 지나면 바구니를 비운다** → 다시 쓸 수 있다

**중요**: 막히는 것은 **한도를 넘긴 사람뿐**이다. 다른 사용자는 아무
영향이 없다. 서버가 멈추는 것도 아니다.

### 3.1 `429` 는 무슨 뜻인가

HTTP 응답 코드다. 우리가 흔히 보는 것과 나란히 놓으면:

| 코드 | 뜻 | 사람 말로 |
|---|---|---|
| `200` | OK | "됐습니다" |
| `401` | Unauthorized | "당신이 누군지 모르겠습니다" (로그인 필요) |
| `403` | Forbidden | "누군지는 알지만 권한이 없습니다" |
| `404` | Not Found | "그런 건 없습니다" |
| **`429`** | **Too Many Requests** | **"너무 자주 부릅니다. 잠시 뒤에 다시 오세요"** |
| `500` | Server Error | "우리 잘못입니다" |

`429` 는 **일시적**이라는 점이 중요하다. 시간이 지나면 저절로 풀린다.

## 4. 우리는 어떻게 만들었나

### 4.1 어디에 붙였나

NestJS 의 **전역 가드(global guard)** 로 붙였다. 가드는 요청이 실제
처리 코드에 닿기 **전에** 검사하는 문지기다.

```
요청 도착
   ↓
[레이트 리밋 가드]  ← 여기서 걸리면 429 로 돌려보낸다 (DB 도 안 건드림)
   ↓
[인증 가드]        ← 로그인 확인
   ↓
실제 처리 (맵 저장, 목록 조회 …)
```

**순서가 중요하다.** 레이트 리밋이 앞에 있어야 남용 요청이 DB 까지
가지 않는다 — 막는 비용 자체가 싸야 방어가 의미 있다.

### 4.2 "한 사람"을 어떻게 구분하나 — 여기가 함정이다

바구니를 나누려면 **요청을 보낸 사람을 식별**해야 한다. 흔히 IP 주소를
쓰는데, **그것만 쓰면 문제가 생긴다.**

> **회사·학교에서 접속하면 여러 사람이 같은 공인 IP 로 나간다.**
> IP 로만 세면 그 사람들이 **전부 한 바구니**에 담긴다 — 한 사람이
> 많이 쓰면 옆자리 동료가 막힌다.

우리 사내망도 정확히 그렇다. 그래서 이렇게 했다.

| 상황 | 무엇으로 세나 | 왜 |
|---|---|---|
| **로그인한 요청** | **토큰**(해시해서) | 사람마다 다르다 — IP 가 같아도 바구니가 나뉜다 |
| 로그인 전 | IP | 달리 구분할 방법이 없다 |

토큰 값 자체는 메모리에 남기지 않으려고 **해시**해서 쓴다.

### 4.3 프록시 뒤에 있으면 IP 가 안 보인다 — 반드시 짚어야 할 것

우리 API 는 이렇게 들어온다.

```
사용자 → NPM(nginx) → Traefik → API 컨테이너
```

이때 API 가 보는 "요청을 보낸 주소"는 **사용자가 아니라 바로 앞 프록시**다.
아무 설정도 안 하면 **모든 사용자가 프록시 IP 하나로 보인다** → 바구니가
하나뿐이 된다 → 한 사람 때문에 전원이 막힌다.

그래서 `main.ts` 가 프록시 신뢰 범위를 정한다.

```ts
app.set('trust proxy', ['loopback', 'linklocal', 'uniquelocal']); // 기본
```

* 뜻: **"사설망 주소는 전부 우리 프록시다"** — 사슬을 뒤에서부터 벗겨
  내다가 **처음 만나는 공인 IP**(= 진짜 접속자)에서 멈춘다
* ⚠️ **`true`(무제한 신뢰)로 두면 안 된다.** 클라이언트가 헤더를
  **위조**해 IP 를 바꿔 가며 한도를 무한히 우회할 수 있다
* 배포마다 다르면 `TRUST_PROXY` 환경변수로 덮어쓴다 —
  숫자(`2`) · 목록(`loopback, uniquelocal`) · `false`

#### 왜 숫자(1)에서 바꿨나 (2026-08-09)

처음에는 `app.set('trust proxy', 1)` — "내 앞 1단계까지 믿는다"였다.
그런데 실제 배포는 위 그림처럼 **nginx → Traefik 두 단계**라, 한 단계만
벗기면 진짜 접속자가 아니라 **nginx 의 내부 IP**(192.168.x.x)에서 멈춘다.
히스토리에 남는 접속 IP 가 PC 든 휴대폰이든 전부 같은 내부 주소로 찍혀
발견됐다(사용자 보고). 레이트 리밋도 같은 값을 쓰므로, **모든 사용자가
한 바구니**에 담기던 상태였다 — 이 설정이 막으려던 바로 그 문제다.

**단계 수를 사람이 세어 맞추는 방식이 문제였다.** 프록시를 하나 끼우거나
빼는 순간 조용히 틀리고, 틀려도 에러가 안 난다. 그래서 "몇 단계"가 아니라
**"어떤 주소를 프록시로 볼 것인가"**로 바꿨다. 2단계든 3단계든 그대로
맞는다.

> 남는 한 가지: 접속자가 **같은 사설망 안**에 있으면(사내 LAN) 벗길 대상과
> 구분되지 않아 프록시가 적어 준 값을 그대로 쓴다. 인터넷을 통해 들어오는
> 접속에는 해당하지 않는다.

#### 확인하는 법 — `GET /v1/health/ip`

서버가 **내 IP 를 무엇으로 보는지** 그대로 돌려준다. 브라우저로 그냥
열면 되고, PC·휴대폰에서 각각 열어 비교하면 된다.

```json
{ "ip": "203.0.113.9", "ips": ["203.0.113.9", "192.168.94.74"],
  "xForwardedFor": "203.0.113.9, 192.168.94.74",
  "remoteAddress": "192.168.94.60", "trustProxy": ["loopback","linklocal","uniquelocal"],
  "hint": "OK — 공인 IP 입니다. 히스토리에도 이 값이 남습니다." }
```

`hint` 가 무엇을 고쳐야 하는지 말해 준다 — 사설 IP 인데 `xForwardedFor`
가 비어 있으면 **프록시(NPM)에서 X-Forwarded-For 전달을 켜야** 하고,
헤더는 오는데도 사설 IP 면 `TRUST_PROXY` 를 조정한다. 자기 요청의
헤더만 되돌려 주므로 다른 사람의 정보는 나오지 않는다.

### 4.4 예외 — 세지 않는 것

**`/v1/health`(헬스체크)는 세지 않는다.** 배포·감시 도구가 주기적으로
부르는데, 그것 때문에 한도가 차면 **정작 장애일 때 상태를 못 본다.**
"고장을 알려 주는 장치가 고장 때문에 막히는" 상황을 피한다.

## 4.5 "서버 호출 1번" 이란 무엇인가 — 한도에 세는 것과 안 세는 것

레이트 리밋이 세는 것은 **브라우저가 우리 API 서버에 보내는 네트워크
요청(HTTP request) 하나**다. 화면에서 하는 조작 하나가 아니다.

> **핵심 한 줄**: **서버에 데이터를 묻거나(GET) 바꾸라고(POST/PATCH/DELETE)
> 보낼 때만** 1번으로 센다. **화면 안에서 끝나는 조작은 0번**이다.

### 세지 않는다 — 브라우저 안에서 끝나는 것 (요청이 안 나간다)

이건 서버에 아무것도 안 보낸다. **아무리 빨리 반복해도 한도와 무관하다.**

| 조작 | 왜 0번인가 |
|---|---|
| **다크/라이트 모드 전환** | 테마는 `localStorage` 에만 저장 — 서버 안 부른다 |
| **맵 확대·축소(줌), 화면 이동(Pan)** | 그리기 상태(메모리)만 바뀐다 |
| **노드 접기·펴기, 선택, 마우스 호버** | 보기 상태다 (§14-save.md §7.10) |
| **노드 편집·추가·삭제·이동, 텍스트 입력** | **로컬 문서와 브라우저 초안(IndexedDB)** 에만 쓴다. 서버에는 나중에 자동저장이 **한 번에 모아** 보낸다 |
| 되돌리기(Ctrl+Z)·다시 실행 | 세션 메모리 안에서 처리 |
| 아웃라인↔맵↔칸반 보기 전환 | 같은 데이터를 다르게 그릴 뿐 |
| 검색(맵 안에서) · 노트 팝업 열기 | 화면 안 처리 |

> **왜 편집이 0번인가** — 실시간 저장을 **폐지**했기 때문이다(2026-08-06,
> §14-save.md §7.9). 예전에는 글자를 칠 때마다 서버로 갔지만, 지금은
> **주기 자동저장**이 5분에 한 번, 또는 미저장 50건이 쌓였을 때만 모아
> 보낸다. 그래서 100개 노드를 만들어도 서버 호출은 **자동저장 1번**이다.

### 센다 — 서버에 실제로 요청이 나가는 것 (1개당 1번)

우리 API 를 부르는 **모든 지점**은 이것뿐이다 (`apiClient.ts` 전수).

| 언제 | 메서드·경로 | 몇 번 |
|---|---|---|
| 앱 열기 | `GET /maps`, `GET /folders`, `GET /maps/:id/document` | 2~4번 |
| **자동저장 / 손으로 ☁ 저장** | `PUT /maps/:id/document` | 저장 1회당 1번 |
| 맵 이름변경·폴더 만들기/이동/삭제 | `PATCH`·`POST`·`DELETE /folders…` | 조작당 1번 |
| 맵 삭제 | `DELETE /maps/:id` | 1번 |
| 편집 잠금 유지 | `POST /maps/:id/edit-heartbeat` | 편집 중 주기적으로 소량 |
| **첨부 업로드(청크)** | `POST/GET/DELETE /attachments…` | **파일 조각 수만큼 — 여기가 가장 많다** |
| 히스토리 열기·복원 | `GET /maps/:id/versions…` | 열 때 1번 |

**"1초에 10번"을 사람이 손으로 만들기는 거의 불가능하다.** 저장 버튼을
1초에 10번 누를 수 없고, 자동저장은 5분 간격이다. 유일하게 요청이 몰리는
곳은 **대용량 첨부의 청크 업로드**인데, 그래서 한도를 넉넉히 잡았다(§5.2).

### 4.6 대용량 첨부는 몇 번인가 — 1GB = 약 130번 (실측 계산)

**청크 업로드**만 요청이 여럿 나간다. 파일을 조각으로 쪼개 하나씩 올리기
때문이다. 조각 하나가 1번이다.

* 조각 크기 = **8MB** (`ATTACHMENT_PART_KB = 8×1024`, `chunk-upload.service.ts`)
* 동시 업로드 = **3개씩 병렬** (`chunkUpload.ts` 의 `CONCURRENCY = 3`)

| 요청 | 횟수 |
|---|---|
| 세션 시작 `POST /attachments/uploads` | 1 |
| 조각 올리기 `PUT …/parts/N` | **파일크기 ÷ 8MB** |
| 완료 `POST …/complete` | 1 |

파일 크기별로 계산하면:

| 파일 크기 | 조각 수 | **총 요청 (시작+조각+완료)** | 60초 한도 600 대비 |
|---|---|---|---|
| 10MB | 2 | 4번 | 0.7% |
| 100MB | 13 | 15번 | 2.5% |
| **1GB** (최대 첨부) | **128** | **약 130번** | **22%** |
| 1GB **4개 연속** | 512 | ~520번 | 87% (아슬) |
| 1GB **5개 연속** | 640 | ~650번 | **초과** |

**정상적인 1GB 업로드 1개 = 한도의 22%**, 여유가 4.6배다. 게다가 조각을
**3개씩** 올리므로(동시성 3), 8MB 전송 시간이 걸려 130번이 60초에 다
몰리지도 않는다 — 보통 훨씬 긴 시간에 퍼진다.

> **한도에 닿는 유일한 정상 시나리오**: 1분 안에 1GB 파일을 **4~5개
> 연속으로** 올릴 때다. 실사용에서 드물지만, 그런 사용이 확인되면
> `RATE_LIMIT_MAX` 를 환경변수로 올리면 된다(재빌드 불필요, §5.3).
>
> 조각을 **더 크게**(예: 16MB) 하면 요청 수가 절반(1GB → ~66번)이 된다.
> 다만 조각이 크면 전송이 끊겼을 때 다시 올릴 양이 커지므로 8MB 가 기본값.

## 5. 한도를 왜 600 으로 정했나

숫자는 감이 아니라 **정상 사용량에서 거꾸로** 잡는다. 무엇이 "1번"인지는
바로 위 §4.5 참고.

### 5.1 정상 사용자는 얼마나 부르나

| 언제 | 몇 번 |
|---|---|
| 앱 열기 (맵 목록 + 문서 1개) | 2~5번 |
| **자동저장** | **5분에 1번** (기본값 — 실시간 저장은 2026-08-06에 폐지) |
| 손으로 ☁ 저장 | 1번 |
| 첨부 업로드 (청크) | 파일 크기에 비례 — **여기가 가장 많다** (**1GB ≈ 130번**, §4.6) |

**첨부를 빼면 1분에 10번을 넘기기 어렵다.** 즉 600은 **정상 사용의 수십 배**다.
첨부를 포함해도 **최대 첨부(1GB)가 한도의 22%**라 여유가 크다 (§4.6).

> 다크모드·줌·노드 편집 같은 **화면 조작은 아무리 빨라도 0번**이라 여기
> 안 들어간다 (§4.5).

### 5.2 그런데 왜 그렇게 넉넉하게?

**한도를 좁게 잡아서 얻는 것보다 잃는 것이 크기 때문이다.**

* 공격자는 어차피 600번이든 100번이든 **막힌다** — 방어 효과는 거의 같다
* 반면 좁으면 **정상 사용자가 가끔 막힌다** → 사용자는 원인을 모른 채
  "이 앱 자꾸 오류난다"고 느낀다. 이게 훨씬 비싸다
* 대용량 첨부의 청크 업로드는 **짧은 시간에 요청이 몰린다** — 좁으면
  정상 업로드가 중간에 끊긴다

> **원칙: 레이트 리밋은 "정상 사용자를 절대 막지 않는 선"에서 가장
> 낮게 잡는다.** 남용 차단은 그 선만 넘겨도 충분히 달성된다.

### 5.3 나중에 조절하려면

**재빌드 없이 환경변수로** 바꿀 수 있게 해 뒀다 (Coolify → 환경변수 → 재시작).

```bash
RATE_LIMIT_WINDOW_MS=60000   # 창 크기 (밀리초). 60000 = 60초
RATE_LIMIT_MAX=600           # 그 창 안에서 허용할 최대 횟수
RATE_LIMIT_ENABLED=true      # false 면 통째로 끔 (부하 테스트 등)
```

## 6. 레이트 리밋이 **못 하는** 것 — 오해 방지

이것 하나로 다 막힌다고 생각하면 위험하다. **못 하는 일이 분명히 있다.**

| 못 막는 것 | 왜 | 무엇이 막나 |
|---|---|---|
| **정상 속도의 데이터 탈취** | 1분에 10번씩 천천히 남의 맵을 읽으면 한도에 안 걸린다 | **인증·권한**(JWT 가드 + 소유자 검증 + RLS) |
| **분산 공격(DDoS)** | 수천 대가 각각 조금씩 보내면 개별 한도엔 안 걸린다 | 앞단 인프라 (CDN·WAF) |
| **한 번에 큰 요청** | 100MB 짜리 요청 1번은 "1번"이다 | **본문 크기 제한**(25MB) · **첨부 쿼터**(요금제) |
| **저장 공간 남용** | 요청 수와 무관하다 | **쿼터** (Free 10MB · Basic 10GB) |

**레이트 리밋은 여러 방어층 중 하나다.** 우리 API 의 방어층은 이렇다.

```
① 레이트 리밋   "너무 자주 부르지 마라"          ← 이 문서
② 인증(JWT)     "당신이 누구인지 증명해라"
③ 권한·RLS      "남의 것은 못 본다"
④ 크기 제한     "한 번에 너무 큰 건 안 된다"
⑤ 쿼터          "총량은 요금제만큼만"
```

## 7. 개발할 때 주의할 것

### 7.1 자동화 테스트가 한도에 걸릴 수 있다

**e2e 테스트는 사람보다 훨씬 빠르게 API 를 연타한다.** 한도가 좁으면
테스트가 `429` 로 무더기 실패하고 — 이게 가장 나쁜데 — **제품 결함으로
오독된다.**

그래서:
* 한도를 넉넉히 잡았다(§5)
* 정말 필요하면 테스트 환경만 `RATE_LIMIT_ENABLED=false` 로 끈다
* **회귀 테스트가 무더기로 깨지면 429 부터 의심**한다

### 7.2 429 를 만나면 화면이 무엇을 말하는지 확인한다

사용자가 `429` 를 받았을 때 **"알 수 없는 오류"만 뜨면 안 된다.**

라이브러리 기본 메시지는 이랬다 — 사용자가 할 수 있는 일이 없다.

```json
{"statusCode":429,"message":"ThrottlerException: Too Many Requests"}
```

그래서 **우리 문구로 바꿨다**(`throwThrottlingException` 재정의):

```json
{"statusCode":429,"error":"Too Many Requests",
 "message":"요청이 너무 잦습니다. 60초 뒤에 다시 시도해 주세요.",
 "retryAfterSec":60}
```

프런트엔드(`apiClient.ts`)는 서버가 준 `message` 를 그대로 화면에 띄우므로
이 문구가 사용자에게 보인다. **새 기능을 만들 때 이 경로를 잊기 쉽다.**

### 7.3 재시도는 반드시 간격을 두고

`429` 를 받고 **즉시 재시도하면 상황이 더 나빠진다.** 우리 자동저장은
실패 시 1·3·10·30초로 간격을 늘려 가며 재시도한다(지수 백오프). 새로
만드는 호출도 같은 규칙을 따른다.

## 8. 현재 설정 요약

| 항목 | 값 | 비고 |
|---|---|---|
| 창 크기 | **60초** | `RATE_LIMIT_WINDOW_MS` |
| 최대 횟수 | **600번** | `RATE_LIMIT_MAX` — 정상 사용의 수십 배 |
| 세는 단위 | 로그인 시 **토큰**, 아니면 **IP** | 같은 회사 IP 뒤 사용자가 서로 안 막히게 |
| 예외 | `/v1/health` | 감시 도구가 막히면 안 된다 |
| 저장 위치 | **API 프로세스 메모리** | 아래 참고 |
| 끄기 | `RATE_LIMIT_ENABLED=false` | 부하 테스트 등 |
| 429 응답 | 한국어 안내 + `Retry-After` | "요청이 너무 잦습니다. N초 뒤에…" |

> **메모리 저장의 한계**: 지금은 API 가 1개라 문제없다. 나중에 API 를
> **여러 대로 늘리면** 각 대가 따로 세므로 실질 한도가 대수만큼 커진다.
> 그때는 카운터를 Redis 로 옮긴다 (`@nestjs/throttler` 의 Redis 스토리지).
> 서버를 재시작하면 카운터도 초기화되는데, 이건 실무상 문제가 안 된다.
