### 3\. 왜 `easymindmap`은 React를 선택했을까? (좋은 설계인가?)

결론부터 말씀드리면, \*\*마인드맵 같은 서비스에 React 선택은 매우 '좋은 전략'\*\*입니다. 그 이유는 다음과 같습니다.

#### ① 컴포넌트(부품) 중심의 설계 \[구조화 시각화\]

마인드맵의 각 요소(노드, 선, 메뉴바)를 독립된 '레고 블록'처럼 만들 수 있습니다.

*   **장점:** '노드(Node)'라는 블록 하나만 잘 만들어두면, 화면에 100개가 있든 1000개가 있든 똑같은 로직을 재사용할 수 있습니다.

#### ② 가상 DOM (Virtual DOM)을 통한 빠른 화면 업데이트

마인드맵에서 노드 하나를 옮길 때마다 전체 화면을 다시 그리면 컴퓨터가 매우 느려집니다.

*   **React의 마법:** React는 메모리에 가상의 화면을 먼저 그려보고, **실제 바뀐 부분(노드 위치 등)만 딱 집어서** 실제 화면에 반영합니다. 이는 마인드맵처럼 변화가 잦은 서비스에서 끊김 없는 사용자 경험을 제공합니다.

#### ③ 강력한 '마인드맵 전용' 라이브러리 활용

React 생태계에는 `React Flow`나 `D3.js`와 같이 복잡한 그래프와 선을 그리는 데 최적화된 도구들이 매우 많습니다. Angular나 Vue보다 이런 도구들을 가져다 쓰기가 훨씬 수월합니다.

첫 화면 크기도 비슷하다. EMM 운영 화면이 처음 내려받는 JavaScript는 약 2.5MB(gzip 압축 시 약 750KB, 2026-11-11 측정)다. 그중 React 런타임은 약 45KB(gzip)에 불과하다. 따라서 첫 화면 크기는 프레임워크 선택보다 **우리 기능 코드를 어떻게 나눠 싣는지(지연 로딩)**에 더 크게 좌우된다.

#### 5-4. 다른 제품 사례: Angular 기반 ThinkWise

- ThinkWise 웹(web.thinkwise.co.kr)은 **Angular 15.2.10**으로 만들어져 있다(2026-11-10 확인).
- 같은 강의록 MD(노드 5,750개)를 ThinkWise의 "md 가져오기"로 넣자 **브라우저가 7분 넘게 응답하지 않았고**, 빈 문서만 남았다(2026-11-11 시험).
  - 원인: 가져오기가 모든 노드를 한 번에 만들고, 노드마다 XML을 만들어 명령 하나로 서버에 보낸다. 중간에 화면을 갱신하지도 않고 작업을 나누지도 않는 구현이다.
- 같은 MD를 34개 차시로 나눠 한 차시씩 넣으니, 한 번에 3~70초씩 걸려 끝까지 들어갔다. 다만 두 번은 화면에만 들어가고 서버에 저장되지 않아 다시 넣어야 했다.
- 저장 크기도 크게 다르다. 같은 맵이 **EMM에서는 1.5MB, ThinkWise에서는 30.0MB**다. ThinkWise는 노드마다 서식이 담긴 XML을 저장해 노드당 약 5.2KB가 된다.
- **교훈:** 멈춤의 원인은 Angular가 아니라, 큰 작업을 한 번에 동기로 처리하고 노드마다 큰 자료를 만드는 제품 설계다. React로 같은 방식을 짰어도 똑같이 멈췄을 것이다.

EMM에서 같은 MD를 가져오는 데 걸리는 시간은 아직 따로 재지 않았다. 다만 EMM 가져오기는 MD를 맵 자료로 한 번에 바꾼 뒤 화면에 통째로 넣는다. 노드마다 편집 명령과 XML을 만들지 않는다.

#### 5-5. 성능 관점의 결론과 할 일

**결론**

1. **프레임워크 자체 속도는 Vue > React ≈ Angular다.** 종합 점수가 각각 1.30 / 1.56 / 1.51~1.59배이고, 첫 화면 크기도 Vue가 가장 작다. 성능만 보면 Vue가 약간 유리하다.
2. **그러나 EMM의 체감 성능을 정하는 것은 프레임워크가 아니라 설계다.** EMM에서 실측한 큰 개선(13초→0.1초, 6초→2.5초)은 모두 우리 코드의 알고리즘·가상화·캐시에서 나왔다. 반대로 ThinkWise(Angular)가 멈춘 것도 제품 설계 때문이었다.
3. 따라서 **성능 면에서도 React 선택을 유지해도 된다.** 지금 프레임워크를 바꿔서 얻는 속도는 약 20% 안팎이다. 반면 잃는 것(다시 만드는 비용, React 생태계의 그래프·캔버스 라이브러리)은 훨씬 크다.

**React를 쓰면서 지켜야 할 성능 규칙 (할 일)**

| 번호 | 할 일 | 이유 |
| --- | --- | --- |
| 1 | 노드 순서를 바꿀 때 `key`를 노드 id로 유지하고, 바뀐 형제 범위만 다시 그린다 | React는 "자리 바꾸기"가 약하다(위 표의 87ms) |
| 2 | 화면 밖 생략과 가상화를 새 화면(간트, 작업 목록, 문서함 등)에도 적용한다 | 그리는 양을 줄이는 것이 가장 효과가 크다 |
| 3 | 배치 계산·MD 해석·글자 폭 측정처럼 무거운 계산은 Web Worker로 옮기는 것을 검토한다 | 계산하는 동안에도 입력과 화면이 멈추지 않게 한다 |
| 4 | 무거운 갱신은 `useTransition`으로 뒤로 미루고 입력 반응을 먼저 처리한다 | 타이핑과 클릭 반응을 유지한다 |
| 5 | React 19와 React Compiler(자동 memo) 업그레이드는 **측정한 뒤** 결정한다 | 벤치마크에서는 Compiler를 쓴 경우 1.61배로 오히려 이득이 없었다 |
| 6 | 성능 예산을 정하고 배포 전마다 같은 맵으로 잰다: 5,000노드 맵 열기 3초 이내, 노드 선택 0.1초 이내, 분할 보기 열기 1초 이내 | 느려진 곳을 바로 발견한다 |

* * *

### 6\. 최종 의견

`easymindmap` 프로젝트의 Front-end 아키텍처로 React를 선택한 것은 **현명한 선택**입니다.

*   **Angular**를 썼다면 초기에 설정해야 할 규칙이 너무 많아 프로젝트가 무거워졌을 수 있고,
*   **Vue**를 썼다면 마인드맵과 같은 복잡한 커스터마이징이 필요한 부분에서 React만큼의 자유로운 라이브러리 지원을 받기 어려웠을 수 있습니다.

*   **성능**만 놓고 보면 Vue가 약 20% 빠르다. 하지만 EasyMindMap처럼 노드가 수천 개인 맵에서 체감 속도를 정하는 것은 프레임워크보다 **설계(화면 밖 생략, 가상화, 효율적인 계산)**다. 실측 근거는 §5에 있다.

**IT 초보자 관점에서의 핵심 정리:** "React는 마인드맵의 복잡한 움직임을 **부분적으로 빠르게 업데이트**할 수 있고, **부품처럼 쪼개서 관리**하기에 가장 인기 있고 검증된 도구이기 때문에 아주 좋은 설계라고 볼 수 있습니다."
